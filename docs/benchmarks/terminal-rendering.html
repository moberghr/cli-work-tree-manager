A terminal that survives slow tabs, reconnects and a second window

Same machine, same inputs, the commit before the rework against the commit after it. A reattached terminal now comes back as the agent left it, a flooded tab stays responsive, and a dropped connection resumes in 209 bytes. It costs some host memory and CPU, listed below with the same weight as the gains. Those figures come from scripted agents; the first section below is the check against real Claude Code sessions, where two of the gains show up and the speed gains do not.

A tab that cannot keep up

A terminal that prints faster than the tab draws used to queue without limit: in the host, on the socket and inside xterm.js, which throws output away past 50 MB. Now the host paces output to what the tab has drawn. On a fast tab nothing changes; on a slow one (6× CPU throttle here, standing in for a busy browser or an older laptop) it is the difference between a frozen terminal and a working one.

In the app

What it looks like

Scope

What changed in the code

  • The host's screen copy tracks what serialising drops: mouse and keyboard modes, cursor shape and visibility, title, scroll region, and it measures widths with the same Unicode tables as the browser.
  • One answerer for terminal queries, and the host answers when no tab is open.
  • Flow control: tabs acknowledge what they have drawn, the host pauses the PTY above 100,000 unacknowledged characters and sends a slow tab one fresh screen in place of a backlog.
  • Resize once per burst, at the attaching client's own grid, before the first screen is built.
  • Synchronized frames (DEC 2026) travel whole and screens are only taken between frames.
  • Renderer care: hidden terminals release their WebGL context, software rasterizers use the DOM renderer, late fonts are re-measured.
  • Status from the stream: agents without hooks report working / waiting / idle through OSC 7501 and OSC 9;4.
  • Reattach where you left off: a 256 KB tail per terminal and an offset the tab states when it reconnects.
Method

How it was measured, and what was not

  • Both commits were checked out and built the same way, each run against its own PTY host with a temporary home directory. Every figure is the median of 5 runs unless the row says otherwise; rows show the spread.
  • Agents are small scripts that reproduce the terminal traffic in question. Real Claude Code was not run for these rows; the real-session section at the top is the separate check.
  • Browser figures come from a harness page with the app's own xterm.js options and, after, the app's own renderer module. The whole app was not driven end to end in the benchmarks.
  • The window drag is emulated with the app's real scheduling code; no real window was dragged.
  • macOS on Apple silicon only. Windows and Linux read from PTYs differently, which affects the flood and pacing figures most.
  • Not measured: GPU memory, an hours-long soak, test-suite time.
  • An earlier internal figure of "3.7 whole frames a second" compared two versions of the rework's own pacer, not the base. It is not a before number and is not used here.
