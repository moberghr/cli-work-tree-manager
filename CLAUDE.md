## Architecture & CLI Reference

The remainder of this file is the architecture / CLI reference for human readers and agents that need the full picture of module flow, command surface, and the `wd` / `work web` design. The standards above (skill routing, critical rules) are the canonical short list; this section is the long form.

## What This Is

A cross-platform TypeScript CLI (`work`) for managing git worktrees across multiple repositories. Supports single-repo and multi-repo "group" worktrees with automatic Claude Code launching. Installed globally via `npm link`.

## Development

```bash
npm run build          # Bundle with tsup → dist/bin.js
npm run dev            # Run directly via tsx (no build needed)
npm test               # Run all tests with vitest
npm run test:watch     # Watch mode
npx vitest run tests/core/resolve.test.ts  # Single test file
```

After building, `work` is available globally (via `npm link`). Rebuild after source changes.

### Core is a library: two front-ends, one implementation

`src/core` holds every piece of logic; the CLI (`src/commands`) and the HTTP API (`src/server`, its routes in `src/server/routes/`, the backend for the SPA and the desktop app) are thin front-ends that call it. Neither calls the other. Pure pieces that the SPA shares live in core and are re-exported by the SPA: `session-view.ts` (status vocabulary, age sections), `digest-view.ts` (Today windows and Markdown), `saved-prompts.ts`, `attention.ts`, `api-types.ts`.

§ Core never prints (architecture test §2.7): no `chalk`, no `console.*`, no raw stdout/stderr writes under `src/core` or `src/server` (`platform/logger.ts` excepted). Use `report(level, text)` (`core/platform/report.ts`). The reporter is scoped with AsyncLocalStorage (`withReporter`): the CLI shows reports with colors (`commands/shared/console-reporter.ts`: stdout for `work`, stderr for `wd`), servers default to the debug log, and a route can collect them (`collectingReporter`) to return a failure's real reason — `POST /api/worktrees` does.
§ WHEN adding logic, put it in core and call it from both front-ends; a route or command handler only parses input and formats output. `work sessions --json` rows come from `sessionWire` (`core/sessions/session-wire.ts`), the same function as `/api/sessions`; the digest from `createDigestSource` (`core/conversations/digest-source.ts`); cleanup from `scanCleanup` / `applyCleanup` (`core/cleanup/cleanup.ts`, deps in `core/cleanup/cleanup-deps.ts`).

Claude reads this data through the CLI (`--json`), described to every session by the `work-sessions` skill in the plugin (`plugins/work-tree/skills/work-sessions/SKILL.md`).

### Key Design

- **Shared core operations:** `setupWorktree()` and `teardownWorktree()` in `core/worktree/worktree.ts` are the high-level entry points used by both the CLI commands and `work web`. They resolve targets, create/remove worktrees, handle group CLAUDE.md, and manage sessions. Low-level building blocks are `createSingleWorktree()` and `removeSingleWorktree()` which handle one repo with rollback on failure.
- **Resolver pattern:** `resolveProjectTarget()` in `core/worktree/resolve.ts` dispatches a name to either a group or single repo, returning `{ isGroup, name, repoAliases }`. Commands use this to branch into group vs single-repo handlers.
- **Branch resolution order:** local exists → remote exists (creates tracking branch) → neither (creates new branch).
- **Path convention:** Branch directories replace `/` with `-` (e.g., `feature/login` → `feature-login`). Single-repo worktrees at `<worktreesRoot>/<repoFolderName>/<branch-dir>/`, groups at `<worktreesRoot>/<groupName>/<branch-dir>/<repoFolderName>/`.

### `work dash` (removed in 2.0)

`work dash` (the Ink TUI with its own PTYs and http-type hook server) was retired: use `work web` (browser dashboard) + `work attach` (a real terminal on the same PTY-host session). Its leftover http hook entries in `~/.claude/settings.json` are PID-tagged and pruned as stale by the next `work web` hook install.

### Re-entering a worktree (pull + resume)

`work tree` is both "create" and "switch back", and switching back is the common case. Whenever the target checkout already exists — an existing worktree, or the base repo when the branch positional is omitted — two things happen before the AI tool launches:

- **Pull.** `pullLatestForBranch()` (`core/worktree/worktree.ts`) runs fetch + pull in that directory. Best-effort by design: a branch with no upstream returns early (a bare `git pull` there prints a "no tracking information" error that reads as a failure), and a pull blocked by a dirty tree or conflicts only warns. It must never block getting into the worktree. Threaded through `setupWorktree(..., { pull })` → `createSingleWorktree(..., pull)`; `--no-pull` sets it false. A freshly created worktree skips this — it is already at the branch tip.
- **Resume.** `launchTool()` in `commands/tree.ts` passes `resume: true` so the tool gets its resume flag (`--continue` for Claude Code). Gated on `hasClaudeConversation(dir)` (`agents/claude/activity.ts`, a transcript-exists check over `~/.claude/projects/<encoded-cwd>/*.jsonl`) because `--continue` hard-errors with "No conversation found to continue" in a directory Claude has never run in — the same gate `work resume` and the PTY host use. `--fresh` opts out.

§ WHEN adding another launch path, resolve the resume flag through `hasClaudeConversation` rather than passing `--continue` unconditionally.

**A repo's own checkout stays on its branch.** Branches are work's: new work gets a worktree. A session on a repo's own folder (`work tree <repo>`, no branch; `isOwnCheckout`, `core/worktree/own-checkout.ts`) gets `ownCheckoutNote` on every turn start (`runTurnHook`): stay on its branch, don't create, switch or check out branches, don't open PRs from it, ask for a worktree instead. The PR watch never archives one (`ownCheckout`).

### PTY host (sessions that survive restarts)

Claude PTYs are owned by the **PTY host** (`work pty-host`, hidden), a detached localhost process — not by `work web`. `work web` (via `core/pty/pty-pool.ts`) and `work attach` are clients: restarting/rebuilding `work web` or closing a terminal only drops a view. Discovery: `~/.work/pty-host.json` (pid, port, random token; every request carries the token, plus a Host-header check). Live sessions are mirrored to the restore list (state.db `pty_sessions`); on host start they are respawned with `--continue` (the "restored" flag), so a crash, `--restart` or reboot picks up where you were. A PTY that exits on its own is forgotten after 5 s (not immediately — at Windows logoff the children die just before the host); an explicit kill (worktree delete) forgets it at once. Several clients may attach to one PTY; the last resize wins. An explicit kill (`work stop`, archive, delete, idle sleep) tells the attached clients it ended (`kill` keeps the exit subscribers until the process is gone), so a Terminal tab offers Enter to start it again instead of a screen that takes no input; ⋯ → Reconnect terminal (⇧R, `state/terminal-reconnect.ts`) opens a new connection whatever state it's in.

**Idle Claudes sleep** (`core/pty/idle-sleep.ts`, a 5-minute sweep in full-mode `work web`): a host PTY with **no client attached** (`PtyInfo.clients`), that has **printed nothing** for `sleepIdleAfterMinutes` (config, default 120, at least 30 — the Terminal tab reads a Stop in the last 30 min with no PTY as "running elsewhere"; 0 = never; `PtyInfo.lastOutputAt` — an idle Claude prints nothing, a working one redraws its spinner), whose status isn't working/needs_input, and isn't the assistant, is stopped (`disposePty`): it stops holding memory, and opening the session resumes the conversation. The dashboard's terminal deck (`TerminalDeck`) keeps up to 5 terminals connected for instant switching, but one hidden for `DECK_HIDDEN_MS` (10 min) lets go (`pruneDeck`), so its Claude counts as unattended and can sleep — with the app open all day, the five most recent Claudes otherwise never slept. `clients`/`lastOutputAt` are additive: a host from before reports neither, and then nothing sleeps.

**Heartbeat and latency.** The pool's 2 s list request is the host's heartbeat (`hostBeat`, `core/pty/pty-pool.ts`). `core/pty/host-health.ts` (pure) reads it as ok, slow (an answer over 1.5 s) or not answering (none for 11 s; a busy host counts as a host). `GET /api/pty-host/health` serves it, a `host-health` broadcast goes out when it changes, and the dashboard shows `HostHealthBanner` only when it isn't ok, pointing at `work pty-host --restart`. The Terminal tab measures a keystroke's way to the screen and back (`LatencyMeter`: key sent → next output, the median of the last 20) and shows "⌁ 12 ms" in its corner, amber from 100 ms. That's where to look first when typing feels slow. The terminal draws with WebGL; a lost context (GPU reset, sleep/resume) falls back to the DOM renderer, which is slow with a busy Claude, so the corner then says "DOM" and it tries WebGL again after 2 s, 10 s and 60 s (a try that fails counts as a loss), staying on DOM at the fourth loss in 10 min (`WebglRecovery`, `state/webgl-recovery.ts`); each swap refits the grid, since the renderers measure a cell differently. Measured (2026-10): a working Claude sends ~14 frames/s at ~1 KB/s; even 4 MB into five deck terminals at once kept the page at 60 fps with no long task — drawing isn't where time goes.

**The environment of a restored session.** A restore spawns with the host's environment, not the launching shell's: `env` is one-shot and never stored (it can hold secrets). Config `hostEnv` (`["JAVA_HOME", "PATH"]`) names variables to keep: their values from the shell that started the session go into its restore-list entry (`keptEnv`, `keepEnv` in `pty-host-protocol.ts`), and a restore — or a respawn without a shell, from the Terminal tab — runs with the host's environment plus those. Names that look like secrets or carry them (`*TOKEN*`, `*SECRET*`, `*PASS*`, `*KEY*`, `*AUTH*`, `*_PAT`, `DATABASE_URL`, `*_URL`, connection strings, …) and values with a password in a URL (`scheme://user:pass@`) are never kept, whatever the config says.

**Status for a tool with no hooks.** For a session whose PTY runs another tool (`aiCommand`, e.g. opencode; `PtyInfo.tool`, additive), nothing reports turns, so `statusFromOutput` (`core/pty/output-status.ts`, pure) reads one from the host's `lastOutputAt`: working while it printed in the last 10 s, idle after (seen — output can't tell a finished turn from a question). It applies only when no hook status exists, in `/api/sessions` (the pool's refresh) and `work sessions`.

**What corrects the hooks** (an audit found each of these wrong once):
- **Claude Code's own state wins when newer** (`withLiveClaude`, `core/status/session-status.ts`): every running Claude writes `~/.claude/sessions/<pid>.json` with `status: busy|idle|waiting` (+ `waitingFor`, `statusUpdatedAt`; read by `live-agents.ts`). Busy → working, waiting → needs input, idle ends a working / needs-input record — the hooks miss turns (a work web restart, an Esc, a Stop that handed Claude more work), that file doesn't. With no Claude running for a session anywhere (process list read, no PTY of ours), working / needs input is over at once.
- **Notifications by `notification_type`**: `permission_prompt` / `elicitation_dialog` → needs input; `idle_prompt` (a minute after it stopped, with no Stop: an interrupt) ends a working / needs-input record, seen. The message regex is only the fallback.
- **A Stop that delivered comments** (`decision: block`) records `continue` (still working), not a false "Done"; the real Stop comes later. A Stop always starts its own `since`, and one with no prompt hook before it is stored with `prevState: working`, so you are notified.
- **"Answered"** (needs input → working) counts only a turn's transcript entry (`lastTurnEntryMs`: not slash-command echoes, compaction, away summaries or exit lines), and decays after 15 min like working.
- **Seen** only while the window is visible and focused (`useLooking`, `DashboardApp.tsx`).
- **Two sessions on one folder**: `findSessionForCwd` picks the non-archived one, then the one whose branch is checked out, then the latest — not the oldest.

### Ship & archive

`Ship` runs `core/pr/ship.ts` per repo. **Groups ship in parts**: backend may be merged while frontend is in review.
- A repo is **done** when its PR is MERGED or it was never touched (0 commits vs `origin/HEAD`, clean, no PR). Done repos are never blockers and never selectable.
- "Published" means `origin/<branch>` exists — not `@{u}` (`work tree` leaves new branches tracking `origin/main`); ahead/behind are measured against `origin/<branch>`, and push uses `-u origin <branch>` unless tracking already points there.
- **Merge = `mergeSelected`**: the client sends `repos: [{name, headSha}]` — the repos the user ticked and the PR heads it SHOWED. The server re-runs the preflight and refuses the whole call if any selected repo is unknown, done, blocked, or its PR head moved; only then merges each with `gh pr merge N --<method> --match-head-commit <that sha>`, stopping at the first gh failure. Unselected repos are never touched.
- Blockers include: dirty tree, not pushed, unpushed commits, origin ahead of you, PR head ≠ local HEAD, draft, closed, conflicts, behind base, branch protection, failing/pending checks.
- The session is **archived only when the merge merged something AND every repo is done** afterwards.
- **Archive** (`archiveSession`, `core/archive/session-archive.ts` — the one path for the Archive button, Ship's merge, the PR watch and cleanup): first checks nothing is waiting (`archiveWaiting`: reply drafts to post, notes not yet delivered, a Claude working or waiting for an answer) — the button asks and can force it (409 `blocked` → confirm → `force: true`); cleanup waits. **Merged work decides it** (`{ merged: true }`: the PR watch's auto-archive and Ship's merge): drafts, undelivered notes and a finished turn's question for you don't hold it up, and only a Claude in the middle of a turn does (`turnInProgress`: working, or at a permission dialog mid-turn — a needs-input state entered after the last turn ended; stopping it would lose the pending tool call; tried again on the next sweep). Nothing is lost either way: those rows stay in state.db with the session (deleted only with it), so Restore shows the drafts and delivers the notes on its next turn, and `archive.json` lists them (`kept`: each draft's text, each note, the question), shown as "Also kept: …" on the archived session and in the Activity note. Then it stops its Claude and its dev server (and releases watchers) — and from there to the end nothing may start that Claude again: `ensurePty` refuses a session being archived or archived (`core/archive/archiving.ts`), since a Terminal tab still open on it reconnects and would start it (an archived session once kept a live Claude that way, restored after every host restart), records each repo's branch tip, copies every transcript to `~/.work/archive/<id>/transcripts` (Claude Code deletes old ones itself) with `archive.json` (prompts, PRs, last summary), saves its **uncommitted work** (`core/archive/archive-uncommitted.ts`: modified, deleted and new files — not git-ignored ones — snapshotted into a commit on HEAD through a temp index like checkpoints, kept by `refs/work/archive/<id>/<repo>/<time>` in the repo and written as a binary patch to `~/.work/archive/<id>/uncommitted/`; at most 50 MB, else the worktree stays), and removes the worktree **only when cleanup's check says nothing would be lost** (merged, uncommitted files saved; commits not in the main branch still keep it; never a repo's own checkout). Its **git-ignored files that aren't build output** — local settings (`appsettings.Development.json`, `.env.local`), the editor's state (`.vs`, `.idea`) — are copied to `~/.work/archive/<id>/ignored/<repo>/` when the worktree goes (`core/archive/archive-ignored.ts`: at most 5 MB a file, 50 MB a repo; `ArchiveRecord.ignored`), and Restore puts them back over the new checkout (`restoreArchivedIgnored`, once). A kept worktree drops its save, since the changes are still there. **Removed only in part** (`core/worktree/leftover.ts`): `git worktree remove` deletes the files and stops at one in use (Visual Studio's), having dropped the `.git` link and the registration — a folder with no git (`isLeftover`). The archive counts that removed (`halfRemoved`, `ArchiveRecord.leftovers`) and keeps the save; Restore treats a folder with no `.git` as gone (`isWorktreeFolder`, not `existsSync`), and `createSingleWorktree` sets it aside (`<folder>.leftover-<time>`, refused with "close what holds it" while a file is in use), adds the worktree, and `setupWorktree` copies its files back after the save (`putLeftoverBack`: over a clean checkout, else only where nothing is; build output left out), then deletes it. The dashboard shows such a folder as "not a git checkout any more" (`onOtherBranch[].noGit`). Removed: its checkpoint refs stay (deleted with the session, `clearSessionCheckpoints`: Restore puts the worktree back at the same path, so the Diff tab's turns come back), and a local branch already merged into the main branch is deleted (`branchesDeleted`; a squash-merged one stays — nothing else reaches its commits). Kept: the reason is recorded and its git-ignored build output is cleared. Afterwards an internal `claude -p` writes a few sentences on what was done (`summary.written`, `archive-summary.ts`), which the Sessions list shows and the conversation search finds. **Restore** (`work tree` into it, or Restore): `setupWorktree` first recreates a deleted branch at its recorded tip (`recreateArchivedBranches`), then the worktree, and `restoreArchivedTranscripts` puts the conversation back where Claude looks, so it continues. `restoreArchivedUncommitted` (`core/archive/archive-restore.ts`) then applies the saved patch to the new worktree, unstaged, once: it refuses a worktree that already has changes or a patch that no longer applies (the branch moved on), records why, and never tries again, so a later `work tree` can't bring old changes back over newer work; the ref and patch stay for doing it by hand. An archived session shows "· N changes saved" (`SessionArchiveInfo.savedUncommitted`). Deleting the session deletes its refs (`clearSessionCheckpoints` → `dropSessionSaves`). **Retention** (`archive-retention.ts`, daily, in the Activity panel): transcripts of archives older than `archive.compressAfterDays` (default 30) are gzipped — lossless, search and Restore read `.gz` (`readArchivedTranscript`); `archive.dropTranscriptsAfterDays` (default 0 = never) deletes them, keeping the summary. The archive folder goes with the session on delete (`sessionStatePaths`).

§ Restore means "as if it had never been archived": the branch (recreated at its tip), the worktree at its path, the branch it had checked out, uncommitted and untracked files, git-ignored local settings and editor state, the turns, the conversation — `tests/core/archive/restore-roundtrip.test.ts` archives and restores a real session and compares. WHEN archiving drops something new, put it back on Restore and add it there. A Restore that can't make the worktree answers why (500 with the reason), never "unknown session".

### Session Tracking

`core/sessions/history.ts` stores worktree sessions in state.db's `sessions` table (one row per `target + branch`). The `tree` command calls `upsertSession()` before launching Claude; `remove` calls `removeSession()` on success. The `status` command reads history + live git info; `recent` lists sessions sorted by last access.

**Session identity & state.** The id is `sessionIdFor` (`core/sessions/session-id.ts`: sha1(target:branch), 12 hex). The branch is the one it STARTED on, and names its folder; its name is separate — `title` (`--name`, the New worktree dialog's Name, F2 / Rename later), the rail's label when you gave one. Claude (or you) may switch the worktree to another branch: ship, the PR watch and the diffs read the checked-out branch from git; `onOtherBranch` (HEAD files, no git: `core/git/git-head.ts`) shows it; re-entering uses the folder as it is; archive records it (`heads`) so Restore of a removed worktree checks that branch out again. Everything per-session beyond history is a row keyed by that id — `session_status`, `comments` (store = id), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs` — plus the dev log file; `removeSession` (and `work status --prune`) purge it all via `purgeSessionState` (`core/sessions/session-store.ts`) → `purgeSessionRows` (`core/platform/db.ts`), so a re-created session never inherits old state.

§ WHEN adding per-session state, add its table to `purgeSessionRows` (`core/platform/db.ts`), or its file to `sessionStatePaths` (`core/sessions/session-store.ts`). Its diff scope's checkpoints are keyed by the hash of its paths, not its id: `removeSession` clears them (`clearSessionCheckpoints`, from the base checkouts — the worktree may be gone), archive and the dashboard's delete drop the scope's watch (`releaseSessionScope`), and a scope keeps at most `MAX_CHECKPOINTS` (200; the oldest after Initial go, refs too).

**Finding work web.** `core/platform/web-discovery.ts` owns `web.url` / `web.pid`. The files outlive the process and PIDs get reused, so `work web --stop` kills only after `/api/context` answers with the recorded pid (`probeWeb`); `webServerResponds` is liveness only. The PTY host has the same rule (`/health` + token + pid). `/api/context` also carries `build` (`core/platform/build-stamp.ts`: the entry file's mtime): a full `work web` replaces a running server whose build differs from its own, or that predates stamps, since a server that outlived a rebuild reads state and serves routes as they were then (a September dashboard showed no sessions after the SQLite move and 404'd on new routes). `wd` and `--lean` never replace. § Two can still start at once (a restart racing the desktop app's watchdog, which starts one when none answers): every 20 s a work web runs `discoveryCheck` — the one web.pid doesn't name, when the named one answers as itself, stops (leaving the hooks, which are removed by owner and are the other's too, and the discovery files); with nothing live recorded it writes itself back. A duplicate once kept an old build in the desktop app for hours and doubled the GitHub API use.

### Diff Review (`wd`)

Second binary (`dist/wd-bin.js`, shim `wd`) that surfaces a GitHub-PR-style diff in the browser. Two modes, both rendering the same React SPA at `dist/web/`. The SPA reads `/api/context` (or `window.__WD_BOOT__` in static mode) to decide which screen and whether the comment UI is enabled.

**One server, many routes.** `wd` always routes through the singleton `work web`: it reads `~/.work/web.url`, POSTs `/api/scopes`, and opens `<webUrl>/diff/<hash>` (or `/review/<hash>` for `wd -c`). When no work web is running, `wd` auto-spawns one in the background — detached `node <bin> web --lean --no-open` — and waits for `~/.work/web.url` to appear before registering. Lean mode (`startWebServer({lean: true})` in `server/web-server.ts`) skips the dashboard-only `~/.claude/projects` activity watcher + the 10 s session-decay tick, and `commands/web.ts` skips installing Claude `UserPromptSubmit`/`Stop` hooks (no `~/.claude/settings.json` mutation). Net result: a `wd` invocation in a fresh shell costs ~one `work web --lean` startup; subsequent `wd` calls across worktrees register on that same server with no extra processes or ports.

- **Live server (`wd`, default):** `runLauncher` calls `ensureWorkWebRunning` (reads `web.url`, autostarts lean work web on a 5 s wait if absent), POSTs the scope, opens `/diff/<hash>`. There is no per-scope daemon class anymore — the previous `runDaemon` / `spawnDaemon` / per-scope `.pid|.url|.log` files are gone. Live updates via chokidar + SSE are **staged, never auto-applied**: on `diff-changed` the SPA re-fetches in the background (`checkForUpdates` in `hooks/use-deferred-diff-load.ts`) and, only if the payload actually differs, parks it in `pending` and shows a `DiffUpdateChip` ("New changes · N files" + Show / Only new / Reload — Show applies the staged payload keeping scroll; Only new narrows to a checkpoint range from the newest checkpoint taken before the on-screen diff was fetched; Reload is a soft foreground refetch + scroll-to-top, never `location.reload()`) **in the header**. Likewise no in-flight dim or progress bar: the only busy cue is `DiffBusyChip` in the header — the diff itself never moves under a reader mid-scroll, and nothing above it is inserted (a banner would shift every line). § WHEN adding another live-refresh path, stage it the same way; do not write straight into `data`. `wd --stop` de-registers the scope (DELETE `/api/scopes/:hash`); the server itself keeps running.
- **Static (`wd --static`):** `renderStatic()` in `core/diff/static-renderer.ts` reads the SPA shell, inlines its CSS/JS, and injects the diff data as `<script>window.__WD_BOOT__=...;</script>`. Writes to `~/.work/diffs/<hash>.html`, opens via `file://`, exits. Self-contained — survives the CLI, no server. The boot JSON goes through `escapeForScriptTag` (handles `</script`, `<!--`, U+2028/U+2029, raw control chars). The boot-script injection uses a function-callback replacement so JSON values containing `$'` (a real shell-regex hazard) don't trigger `String.replace`'s `$`-magic.
- **Review (`wd -c`):** `tryReviewViaWorkWeb` in `commands/diff.ts` registers a scope on (auto-spawning if needed) work web, opens `/review/<hash>`, then polls `/api/scopes/<hash>/comments` once per second. `core/comments/review-poll.ts::diffReviewSnapshot` is the pure helper that diffs the previous-tick `seen` set against the current snapshot. Exits cleanly when the snapshot returns `ended: true`; the scope and browser tab keep working after the CLI exits. If work web autostart fails entirely (port refused, dist/web missing), `wd -c` falls through to a foreground `startCommentServer` (`server/comment-server.ts`) — a per-invocation Hono sub-app that blocks until "End Review", same shape as before.

**Scope resolution** (`resolveScope` in `core/diff/diff-scope.ts`): walks the cwd against the session history. Inside a single-repo worktree → that repo. Inside any sub-repo of a group worktree → the whole group, with that sub-repo as the initially-active tab. At a group root → all repos, no active tab preselected. Outside any work-managed worktree → falls back to `git rev-parse --show-toplevel` (single repo).

**Renderer:** the React SPA in `src/web/`, built by Vite to `dist/web/`. `ReviewApp.tsx` lays out the sidebar (file tree + comments panel), general-comment pane, and `DiffRepo` (per-file `<article>` with side-by-side `<table>`). When `context.readOnly` is set, composer/draft/submit UI and `ReviewProvider` are suppressed (no `fetch('/api/comments')` over `file://`); the diff and file tree still render. Syntax highlighting is npm-bundled `highlight.js` applied per-cell via `dangerouslySetInnerHTML` during render — not post-paint mutation. Intra-line word diff via `diff` package. Viewed-checkbox state persists per-scope in localStorage.

**Status output convention:** stdout carries data only (the comments markdown payload in review mode). All status messages go to stderr via the `info()` helper in `commands/diff.ts`. `console.error` is reserved for real errors.

**Claude integration:** two paths route review comments to a live Claude in the matching worktree without the user typing —
- **`work web` command hooks** in `~/.claude/settings.json` (installed by `work web` on startup, removed on shutdown via `core/platform/command-hook-installer.ts` + the shared atomic-write `core/platform/settings-editor.ts`). The `UserPromptSubmit` hook prepends pending comments to the next user turn; the `Stop` hook returns `{decision:'block', reason:<comments>}` so Claude addresses them automatically when it finishes any turn. Delivered state is state.db `comment_deliveries` (see `core/comments/pending-delivery.ts`). § Two processes deliver (the hook process and the PTY push), so delivery is a **claim**: `claimForDelivery` inserts the ids with `INSERT OR IGNORE` in one transaction, and only the rows it inserted are its to send. Send only what you claimed; `releaseClaim` if the send fails. Never read pending and mark delivered as two separate steps. **Resolved when addressed**: at a turn's real end (a Stop that hands nothing new on), every top-level comment of yours Claude was given — your review comments and work's own notes (PR feedback, CI, prompts) — is marked resolved (`resolveAddressed`, `pending-delivery.ts`, from `runTurnHook`); the Diff tab's badge (`commentCount`) counts only open threads. Resolved ones stay listed, dimmed, and can be reopened.
- **Owned-PTY push** in `server/routes/session-comment-routes.ts`: when a comment is posted and `work web`'s pool already owns a PTY for that session (the user opened the Terminal tab), the route handler writes the formatted reminder directly to stdin. Idle Claudes in our own PTY get the comment without any hook round-trip.
- For external Claudes that are fully idle, neither path fires — the dashboard shows a purple `→N` "waiting for Claude" badge until the user does anything in that terminal.

The legacy `wd-review` skill at `plugins/work-tree/skills/wd-review/SKILL.md` (shipped via the `work-tree` Claude Code plugin marketplace — see `.claude-plugin/marketplace.json`; registered automatically by `scripts/postinstall.mjs` on npm install) is still used for the `wd -c` foreground flow (stdout marker stream + curl replies via `~/.work/diffs/latest-review.url`). Replies must use `--data-binary "@file"` not inline `-d '...'` to survive apostrophes in the body. In the normal work-web flow, reply to `POST /api/scopes/<hash>/comments` (hash from the `/review/<hash>` URL), NOT `/api/comments`.

### Checkpoint trigger + reload-loop guard

Checkpoints are **authoritatively taken per Claude turn**: `work web` installs a `Stop` hook — the lean `wd` server `work hook checkpoint` (owner `web-checkpoint`, `LEAN_HOOKS`), the full dashboard the same inside `work hook turn-end` which POSTs the cwd to `POST /api/checkpoint`; `scope-routes` maps cwd→scope (`scopesForCwd`) and snapshots (dedup-by-tree makes a no-change turn a no-op). The fs-watch auto-snapshot is now a **fallback that suppresses itself while a Claude session is active** (`activeWithin`, `agentWriteMs`, `agents/claude/activity.ts`) so it can never fire mid-turn before the hook — it only checkpoints manual edits when no Claude is around.

§ WHEN touching the scope diff server, preserve `suppressScopeWatch` (`core/diff/scope-manager.ts`): the `to=working` range diff runs `git add -A`/`write-tree`, whose `.git` churn surfaces as nameless `fs.watch` events that can't be path-filtered. The diff route calls `suppressScopeWatch(hash, 800)` after computing so that self-induced churn doesn't fire `diff-changed` → refetch → recompute → **reload loop**. Real edits land outside the window and still reload. Checkpoint names come from `core/diff/checkpoint-summary.ts` (lazy, cached; written by the summarising agent's one-shot run, `runInternal`, with its small model; one internal run at a time across work web, a timed-out run killed with its tree). Every internal run (`internalClaudeSpawn`) is text-only and starts none of the user's MCP servers (`--strict-mcp-config`). Comment `resolved` (mark-done) and `side:'file'` (whole-file) are routed via `/api/scopes/<hash>/comments/:cid/resolve` and the normal POST with `side:'file'`.

### The Diff tab: commits and turns (`DiffView`)

The standalone review page's shape: one toolbar over the file tree and the diff (`wd-dash-difftoolbar`) — the scope tabs (Uncommitted | Since branch) and **Changes: … ▾** (`HistoryPicker`) on the left, what's shown (files, +/−, "vs origin/main", the update chip) in the middle, Split/Unified on the right; the sidebar keeps only the tree and the comments (folded to one line while there are none). The picker lists the session's history, newest first: the branch's commits since its base (`sessionCommits`, `core/diff/session-history.ts`, served with the turns by `GET /api/sessions/:id/checkpoints` as `commits`; a group lists the repo tab's), Claude's turns, and what is uncommitted (`historyItems`, `state/diff-history.ts`, pure). A click shows that one alone, Shift+click the span from the last click to it, across commits and turns; its shortcuts are Uncommitted, Everything on the branch, Last turn and Since you looked. It is there in either scope, always. A pick is a diff between two points (`core/diff/diff-points.ts`, pure: `cp:<id>`, `c:<repo>:<sha>`, `p:<repo>:<sha>` — the commit's parent —, `head`, `working`; anything else is refused, never handed to git): `GET /api/sessions/:id/diff?from=&to=` (`computeSessionRange` → `rangeRefs`: a commit's range is its repo's alone; a checkpoint or the working tree covers every repo). Loading keeps the diff on screen (dimmed a little after a moment, `wd-diff-stale-soft`) with a thin bar under the toolbar (`wd-diff-progress`), no text; a group opens on the first repo with changes (`preferredRepo`, `state/diff-view.ts`), the empty ones dimmed and last. The standalone page (`ReviewApp`) keeps its checkpoint range picker (`CheckpointStrip`).

§ The session's scope is created by the status hook (a POST); `GET …/checkpoints` reads the manifest from disk by `scopeHashForPaths` and creates nothing (GETs have no side effects, §1.5). Dashboard paths get a session's scope through `sessionScope` (lookup-or-create, `findScope`), never `ensureScope`: ensureScope is what a NEW `wd -c` run does — revive an ended review, clear its comments, relabel — and running that on every Claude hook wiped finished reviews.

A session's turns are its diff scope's checkpoints (one per instruction, taken by the Stop hook — the same scope `wd` registers for those paths), kept across the session's own commits (`sessionOwnsScope`, `rebaselineIfHeadAdvanced`; a session where Claude committed each step was once left with only "Initial"), but re-baselined when HEAD brought in other work since the newest turn — a rebase, a merge, commits already on `origin/HEAD` (`headBroughtInOtherWork`) — or the next turn would show it as Claude's; a scope no session owns (`wd`) re-baselines at every commit, as before. Turns are named by checkpoint id, and one whose predecessor was dropped past `MAX_CHECKPOINTS` isn't listed alone; **Last turn** (the newest alone) is a shortcut in the picker, and the Diff opens on it when asked to (the review queue).

**Since you looked.** You review by looking and then telling Claude in the terminal, not always by submitting a review, so the point to diff from is set by looking: when a session's Diff tab has been on screen, in a visible and focused window, for five seconds (`useLookedFor`, `hooks/use-looked.ts`), the newest checkpoint then is recorded (`POST /api/sessions/:id/diff-seen`, `markDiffSeen`, `core/diff/diff-seen.ts`: state.db `diff_seen`, schema v8, forward only, purged with the session). The next visit reads the mark first and keeps it for the visit; when Claude finished a turn after it (`sinceLooked`, `state/diff-history.ts`), the picker's **Since you looked** shows the range from it to the working tree (`?from=cp:<mark>&to=working`, every turn and commit after it marked) and the Diff opens on it (unless asked to open on the last turn). Viewed ticks are stored with the file's change (`fileSignature`: +/− counts and a hash of its hunks; key `path#signature`, `viewedFrom`), so a file Claude changes again is unticked; a bare `path` tick from before stays. Status hooks also ensure the scope, so turns are recorded for sessions nobody has opened yet. The demo fakes three checkpoints per session with changes.

### Revert + batched review

`POST /api/sessions/:id/revert` (`server/routes/revert-routes.ts` → `core/diff/revert.ts`) undoes an **uncommitted** file or hunk. The server re-computes the session's Uncommitted diff to find the change and its repo root (never trusts a root/patch from the browser). Hunk revert asks git for the raw, byte-exact diff of that file (the pipeline's `-w` diff can't be reverse-applied, and the parser drops CRs) and `git apply -R`s the raw hunks overlapping the picked new-side lines after a `--check`. Then it posts a published general comment ("I reverted … don't reintroduce it"), so delivery reuses the comment path. The SPA only offers Revert in the Uncommitted scope (`RevertContext`). `submit-review` pushes the whole review to an owned PTY as one message, like a single POSTed comment does.

**Bulk actions** (Sessions table, View ▾ → Select several, which shows the checkboxes): tick rows (or "select all shown" per table) and the bar acts on them — Archive / Restore / Snooze / Send a prompt / Delete — each through the same call as the one-session button (`BulkActions`), three at a time (`state/bulk.ts` `runBulk`), with progress in the bar and one outcome line (`bulkSummary`: what was refused, and why). Delete asks first, and a delete is one at a time per session: a second request while one runs (a row's own Delete during the bulk one) gets the first one's answer (one with other options, forced or session-only, is refused instead), and "unknown session" from a delete counts as deleted in the SPA (`removeWorktree`). A prompt goes as a published comment (`sendPromptToSession`), like Prompts ▾ and `work broadcast`.

**Catch me up** (the session header's ⋯ menu, `core/conversations/catch-up.ts`): a few sentences on where a session stands — done, left, anything waiting on you — written by the summarising agent (`runInternal`, no tools: the transcript can contain anything) from its last 7 days of conversation (`catchUpTimeline`: your prompts and Claude's last message before each, the newest ~14k characters), its status and its uncommitted size. Cached in memory until the transcripts grow; `GET /api/sessions/:id/catch-up` only reads the cache (§1.5), `POST` writes it. After two quiet days the status line offers "Away 3d · Catch me up".

**Behind main** (`core/stacks/behind-main.ts`): per session, in the background (`BehindCache`: 10-min TTL, two at a time, a broadcast when it changes), each repo's commits behind `origin/HEAD` and whether merging it would conflict (`git merge-tree --write-tree`: nothing touched), as of the last fetch → `SessionWire.behind` (the furthest repo; any conflict). The session header shows "↓ 34 behind origin/main" from 10 commits, or any conflict, with **Update from main** (`POST /api/sessions/:id/update-from-main`): refused while its Claude works or waits on you, or with uncommitted changes; fetch, then rebase a branch never pushed, or merge main into a pushed one (a rebase would need a force push, which Ship doesn't do); a conflict is aborted at once (the worktree as it was) and "Ask Claude to resolve" sends the session a prompt to do it. (The older `POST …/rebase` rebases on the detected parent without fetching and leaves a conflicted rebase in place; the dashboard no longer uses it.)

**Pins and sections** (rail, `core/rail/rail-layout.ts`, pure, shared with the SPA and demo): pin a few sessions to the top, or put them under your own headings. Right-click a row → Pin to top / Move to “…” / Take out of / New section…, or drag a row into another group or onto a heading. The rail reads Pinned, then your sections in your order (empty ones too, so you can drop into them), then Other. Rows keep the rail order inside each group, and pinned wins over a section. The rail order is your drag order (`applyManualOrder`, `core/rail/session-order.ts`); sessions you haven't dragged come above it, newest created first (they're what you're starting on; by project name, a new one landed below an older one), and with no drag order at all the rail is by project, then most recently entered (`stableSessionOrder`). A pinned session stays visible even when it's older than 14 days. Right-click a heading to rename it, move it up or down, or remove it (its sessions go back to the rest). Folding a heading is per browser (localStorage); everything else is in state.db for every window: the section list in `meta` (`ui:rail-sections`), each session's place in `rail_place` (schema v6, purged with the session). Routes: `GET /api/rail`, `POST /api/rail/sections` (one change, add / rename / move / remove, applied to the list as it is, so two windows never overwrite each other), `PUT /api/sessions/:id/rail`, broadcasting `rail-changed`. An empty Other heading stays as a drop target once everything is placed. The Sessions table shows them too: 📌 or the section name on each row, a Rail filter (in View ▾) (pinned / a section / in none), a "rail section" grouping, and the bulk bar's Rail ▾ (Pin, Unpin, Move to a section, Out of their section). **Alt+1…9** opens the rail's first nine rows as shown, from anywhere, a terminal included (capture phase), but not while typing in a field. j/k walk the rows exactly as the rail shows them (it reports them, `onShownChange`: older ones unfolded, headings folded, a search).

**Fork** (right-click → Fork…, `core/sessions/fork.ts` + `fork-routes.ts`, `POST /api/sessions/:id/fork`): a new branch and worktree from where the session is. Each repo starts from the branch its checkout is on (`forkBases`), from its last commit; uncommitted files stay behind, and the dialog says so. It refuses an archived session, its own branch name, an invalid name, a name that already exists in any repo (that would check out the existing branch rather than fork), or a detached HEAD. The worktree is created first, so a bad name fails before the slow part; then the catch-up summary is written (`catchUp`, cached when fresh), and the new Claude starts with `forkPrompt`: where it came from, "work only in this worktree", the summary, then your instruction. A summary or start that fails is reported, and the fork stays. From a terminal: `work fork <branch>` (the same `forkSession`, then attaches like `work tree`). § The summary is given rather than the conversation: a copied transcript carries the original worktree's absolute paths, and its Claude would go on editing files there.

**Stacked sessions** (`core/stacks/stack.ts`, pure; `stack-sessions.ts`, `stack-sync.ts`): a session made from another live session's branch, by a fork or `work tree … --base feat/x`, is stacked on it. Nothing new is stored: the parent is found from the recorded `baseBranch` / `baseBranches`, in the same project and on that branch. A group counts only when every repo shares the base. Mainline names, `origin/…` refs, archived sessions and a repo's own checkout are never parents. `SessionWire.stackedOn` / `stackedChildren` drive the session strip's `StackChip` ("⤷ on feat/x · 2 stacked on this", which opens the parent) and the rail tooltip. Behind and Update from (`behind-main.ts`) measure a stacked session against the parent's **local** branch (`refs/heads/<parent>`, nothing fetched; `Behind.stacked`), and it is shown from one commit behind. After a turn ends (`onStatusChanged` → idle), the stacked sessions involved (the children of the one that finished, or itself when stacked) are checked. A child is brought up to date (`syncStackChild`: rebase if never pushed, else merge) only when its Claude is neither working nor waiting, nothing is uncommitted in any repo, and merge-tree says it merges cleanly. The status is asked again right before each repo is changed, since a turn may have started while git looked. A group is all or nothing: if a later repo fails, the ones already updated are reset to the commits recorded first (they were clean). Sessions made from each other's branches form a cycle, and none of them gets a parent. The orchestration is `syncStacksAfterTurn`, tested in core, which web-server only wires. Its Claude is told by a published note, since files may have changed under it; a note that fails to post shows as a warning in Activity. Anything else is left alone with the reason in the Activity panel (`stacks`), and the chip offers it. Config `stacks.autoUpdate: false` turns that off. Session actions have CLI twins (§ core is a library): `work update` (`updateSession`), `work catchup`, `work snooze`, `work pin`, `work section`; with no `<target> <branch>` they act on the session for the current folder (`commands/shared/session-arg.ts`). Their writes reach an open dashboard through state.db's change counters (schema v7: snoozes, notes and blocks bump `rev:sessions`; pins and sections `rev:rail` → `rail-changed`). The demo shows a stack by the same rule (`feat/invoice-pdf` stacked on `feat/invoice-export`, and any fork). **When the parent merges** (`stack-retarget.ts`): its session archived, AND its archive says merged (a MERGED PR, or its branch deleted as merged into main; `mergedParent`). An archived parent that never merged doesn't count, since moving onto main would drop its work from the child. The child then shows "⤷ was on feat/x — merged" with **Move onto main** (`POST /api/sessions/:id/retarget`). That runs `git rebase --onto origin/<main> <fork point>`, replaying only the child's own commits: main has the parent's in another form after a squash merge, so a plain rebase would replay them. The fork point (`forkPoint`) is not simply the merge-base with the parent's tip, because a parent rebased or amended before it merged shares only an older commit with the child, and replaying from there would bring its old commits back. If the parent's tip is in main (a real merge), it's a plain `git rebase <main>`. Otherwise it's git's `--fork-point` (the parent branch's reflog, which survives a rewrite), or the tip if the child is built on it (`parentTipFor`: the branch, or the tip its archive recorded). If neither works, it refuses and says so (ask its Claude). Before each repo is changed, the status is asked again (`stillOk`), for the button and for Update from main too. Repos with different mainlines keep per-repo bases (`setSessionBase`). The automatic move needs git 2.40 (`merge-tree --merge-base`); on older git it never runs, and the button still works. The demo shows one (`feat/tax-report` on the merged `feat/tax-rates`). A pushed child isn't rewritten: main is merged in. It's all or nothing across a group, refused while its Claude works or with uncommitted changes, and a conflict is aborted. Afterwards its base is main (`setSessionBase`), so it is no longer stacked. It happens by itself after the child's own turn (`retargetIfMerged`, in `syncStacksAfterTurn`) and when the parent is archived (`onArchived`, a listener in `session-archive.ts` that every archive path calls, then `retargetChildrenOf`), when `merge-tree --merge-base` says it goes cleanly, and its Claude is told. If the parent was rewritten and git can't find the fork point (`handOff`), the child's Claude is asked to do it (`ontoMainPrompt`, once per parent tip), and the button's result offers Ask Claude.

**Time per session** (`core/conversations/work-time.ts`, pure; `work-time-source.ts`; `GET /api/sessions/:id/time`): how long a session's Claude worked, from its transcripts, approximately. The time between two lines counts when the later one is Claude's (its message, or a tool result coming back), at most `STEP_CAP_MS` (15 min) each, so your reading and typing don't count, and neither does a permission prompt left for hours. The source reads each transcript once, then only the bytes appended since, a megabyte at a time with a pause between. A file that shrank, changed without growing, or starts differently was rewritten and is read again; an incomplete last line waits for the next read. At most 400 files are kept, the least recently asked about going first. Several transcripts of one session working at once count that time once (`mergeSteps`). The Timeline tab's `WorkTimeChip` shows "⏱ 1h 20m" with a per-day tooltip and refreshes at most once a minute. With config `jiraWorklog` (`site`, `email`, and an API token in `JIRA_API_TOKEN`, or `tokenEnv` / `token`), **→ PAY-12** next to the chip writes the latest day's work to the session's Jira issue as a worklog through Jira's REST API (`core/jira/jira-worklog.ts`; `acli` has no worklog command). It is rounded up to a quarter hour, and only what isn't logged for that day yet is written: state.db `worklogs` (v7, purged with the session) records it. The token never reaches the SPA. `GET`/`POST /api/sessions/:id/worklog`, `work time --log`. A click copies a worklog line (the latest day's work in the last two weeks, usually today's, rounded up to a quarter hour, with the Jira key; never a lifetime total; a failed copy says so): work can't write Jira worklogs itself, since `acli` has no worklog command. The Today digest counts it too (`DigestSession.workedMs`, "~1h 20m of Claude work", also in `work digest`), from the same transcript reads as its prompts.

**Timeline** (session tab, `core/conversations/timeline.ts`, pure, also used by the demo; `timeline-source.ts`; `GET /api/sessions/:id/timeline`): how a session got where it is, newest first by day. It shows when it started, your prompts (the last 30 days of its transcripts, at most 8 MB each), its turns (checkpoints, with names already written; a size-only name says so), its commits since it left `origin/HEAD` (per repo, at most 100), its PRs (the PR watch's last look) and when it was archived. A read: git log and merge-base, the transcripts, the cache; it runs no Claude and refreshes when the conversation moves.

**Blocked by** (`core/rail/blocks.ts`, pure, also used by the demo; `session-blocks.ts`, `block-routes.ts`): a session waits on another session or a GitHub PR. Set it with right-click → Blocked by… (`BlockedByDialog`), the ⛔ chip in the session strip (× stops waiting on one), or `work block`. While it waits, `inboxRank` puts it in "Waiting on others" (7), out of the Inbox and its count; a question from its Claude (needs input) still shows. A session blocker is done when that session is archived or deleted; a PR blocker when it is merged or closed. Waiting on a session that (perhaps through others) waits on this one is refused (it would never end). The sweep (`sweepBlocks`, every 3 min in full work web, also after an archive and when a block is added; Activity kind `blocks`) asks `gh pr view <url> --json state` about the PRs, clears each block whose blockers are all done (removing only the ones it found done, so one added meanwhile keeps the session waiting), and notifies you by presence like every notification (`notify` from `mountStatusRoutes`, kind `unblocked`). It rests 10 min when gh reports GitHub's limit. It also tells the session's Claude (`unblockedPrompt`, a published comment). State: state.db `session_blocks` (v7, purged with the session), `SessionWire.blockedBy` (only what isn't done), `POST`/`DELETE /api/sessions/:id/blocks`.

**Notes** (`core/rail/session-notes.ts`, `note-routes.ts`): your own scratchpad per session — what you decided, what to tell the reviewer, what's next — not part of Claude's conversation. ⋯ → Notes opens it (and 📝 Notes in the status line, when it has some) (`SessionNotes`: saved after a pause in typing, a pending save kept when it closes), Send to Claude hands it over as a published comment, the rail row's tooltip says it has notes (`SessionWire.hasNote`), and `work note` reads/sets/appends from a terminal. state.db `session_notes` (v7, purged with the session); `GET`/`PUT /api/sessions/:id/note` (at most 20 000 characters).

### Agents (`core/agents/`: Claude Code today, others later)

work talks to a coding agent through an `AgentAdapter` (`agents/types.ts`); Claude's (`agents/claude/adapter.ts`) is the only one, and a tool with no adapter (`aiCommand: opencode`) gets a plain one (`agentById`) that starts and does nothing else. A session runs the agent it recorded when it was created (`WorktreeSession.agent`; `agentFor(config, session)`), so changing the default never changes what an existing session runs. Only an agent work has an adapter for is recorded (`agentToRecord`, `isKnownAgent`): an unknown command follows `aiCommand` as it is, since its binary alone (`node` of `node my-agent.js`) can't start it again.
- **`launch`** (every agent): `tool(config)` (binary + flags; config `aiCommand` / `aiCommandFlags` when they name it), `canResume(cwd)` (the resume gate — Claude's is `hasClaudeConversation`; a plain agent never resumes), `resumeLaunch(session)`, `cleanEnv(env)` (a parent session's variables). `work tree` / `resume` / `recent`, the pool's spawn spec and the PTY host's resume check (`PtyRegistry` by the spawned tool) ask it; the Ctrl+K assistant is always Claude's (its folder holds Claude settings).
- **`conversation`** (optional): `files(session)` (one file per conversation, a JSON value per line — Claude's transcripts, `agents/claude/files.ts`), `entries(lines)` (its lines as `ConversationEntry { at, role: you|agent|tool|tool-result|other, text, tool?, id?, sidechain?, usage?, model? }`: every line gives at least one, `other` keeps the non-messages because work time measures the gaps between all lines; Claude's mapping is `agents/claude/entries.ts`, the one place work reads Claude's line format), `contextWindow(model, used)`, `read(session, {last})`. Context %, title, work time, the digest, the timeline, catch-up, conversation copies and search, the archive's prompts and transcript copy, a session's activity (`core/sessions/session-activity.ts`: the newest write to its files — Active / Open / Stale, "last active") and turn activity (`lastTurnEntryMs`: a turn's message after the turn ended; entries mark the agent's own lines `meta` and a shell command or task result `turn`) all read through it, and the pure parts (`promptsSince`, `workSteps`, `contextUsageFrom`, `catchUpTimeline`, `messageOf`) take `ConversationEntry[]`. An agent without it gets none of these — never Claude's files read as if they were its (`tests/core/agent-readers.test.ts`).
- **`events`** (optional): work's hooks are in work's own terms — an owner and a turn edge (`turn-start`, `turn-end`, `notify`; `FULL_HOOKS` / `LEAN_HOOKS` / `LEGACY_HOOKS` in `commands/web.ts`) — and each agent's adapter installs them in its settings (`install` / `removeSync`; work web does it for every agent with hooks, `installAgentHooks`), reads what it sends them (`read(edge, payload)` → the folder and a `StatusEvent`, `core/status/status-event.ts`), and says how notes are handed back (`handOver`). Claude's (`agents/claude/hooks.ts`) maps the edges to UserPromptSubmit / Stop / Notification and keeps the command `work hook <edge>`; another agent's hooks would say `--agent <id>` (`hookAgentArg`; none = Claude). - **`live`** (optional): its running processes as `LiveAgent` (pid, conversation, folder, busy / idle / waiting) — Claude's from `~/.claude/sessions/<pid>.json` (`agents/claude/live.ts`, believed only for a live Claude pid). `liveAgents(table?)` gathers every known agent's; `live-agents.ts` groups them by session (`agentsBySession`, `summarizeAgents`) for the dashboard, the Terminal tab's "running elsewhere", start / send, the PR watch's wake and build-folder clearing.
- **`input`** (every agent): `submit(write, text)` types into its prompt — text, a pause (`SUBMIT_DELAY_MS`), then Enter as `

- **`oneShot`** (optional): a text-only run for work's own summaries (checkpoint names, catch-up, archive summaries, the Jira watch's choice, a group's instructions file) — prompt on stdin, answer on stdout, no tools, no MCP servers, a neutral folder, env tagged internal so its hooks don't fire into work. Claude's is `claude -p --tools "" --strict-mcp-config` (`internalClaudeSpawn`; `small` → `CLAUDE_SMALL_MODEL`). `runInternal` (`core/diff/checkpoint-summary.ts`) runs config `internalAgent` (default `claude`), one at a time; an agent without it writes none and each feature falls back (a size label, no summary).
- **`instructionsFile`** (every agent: Claude `CLAUDE.md`; one with no adapter `AGENTS.md`, the convention Codex, Copilot and opencode read): a group's combined file is generated from each repo's file of that name (`group-instructions.ts`, written by `runInternal`, kept as `~/.work/<group>.claude.md`) and copied into each group worktree's root under it, removed with the worktree. **`conversation.restoreDir`** (optional): where an archived conversation goes back so the agent resumes it — Claude's projects folder for the folder it runs in; without it Restore starts fresh and the archive keeps the files. **`workspace`** (optional): a folder work runs it in — the Ctrl+K assistant's — gets its settings through `write(dir, {allow, hooks})`: `AllowRule`s (a command, exact or `prefix`) and `WorkHook`s; Claude's writes `.claude/settings.json` (`Bash(cmd)` / `Bash(cmd:*)`, `agents/claude/workspace.ts`). It returns the files it wrote: the assistant keeps the list (`.work-written.json`) and, when its agent changes, removes what it wrote for the last one (instructions, allow rules, hooks) — only listed files inside the folder, never the user's local settings. Without it only the instructions file is written. **`skills`** (optional): `install({skillsDir})` gives it the SKILL.md folders in `plugins/work-tree/skills` (the Agent Skills format); Claude's registers the `work-tree` plugin marketplace (`agents/claude/skills.ts`). `installSkills` (`core/agents/skills.ts`; `scripts/postinstall.mjs` → `dist/install-skills-bin.js`, or `work install-skills`) does every known agent; a missing local folder is each agent's to judge (Claude's come from its marketplace), and a failed `claude plugin install` is reported with how to do it by hand unless `claude plugin list --json` has it already. The skills speak to any agent (a test keeps "Claude" out of them).
**Lookups and the wire.** `agentOf(session)` is `agentFor(agentSettings(), session)`: `agentSettings()` reads config.json's `aiCommand` / `aiCommandFlags` / `internalAgent` / `assistantAgent` once and again only when the file changes (path, size, mtime), since the lookups run per row of every session list. `registerAgent(adapter)` adds one (returns its removal). A new agent (Codex, Copilot) is an adapter in `agents/` plus `registerAgent` (or the built-in table), and that test as its template.

### Driving a session from outside its terminal (`work read / send / wait / …`)

Another Claude (or a script, or you in a shell) can talk to a session: `core/sessions/session-control.ts` is the policy with its I/O passed in, `session-control-routes.ts` the routes in work web (what only it can do — type into a terminal it owns, start a Claude in the PTY host): `POST /api/sessions/:id/send` (`SendWire`: how it went), `POST …/agent/start|stop`, `GET …/screen` (a read: starts nothing). The CLI calls them through `callWorkWeb` (`web-discovery.ts`: a refusal comes back with its reason; status 0 = no work web), and reads the rest itself: `work read` the conversation, through the agent interface (`core/agents/`: `AgentAdapter.conversation.read` → `ConversationEntry { at, role: you|agent|tool, text, tool? }`; Claude's adapter reads the newest transcripts' tails, `claudeEntries` is the pure mapping; `agentFor(config)` gives an adapter with no capabilities for another tool), `work wait` the hook-recorded status (`waitForTurn`: with `after`, only a state entered after the message counts). § A message is a published comment, like every note to a session: the comment route types it into an idle host Claude, the prompt hook hands it over otherwise, and a session not running anywhere is started with `NOTE_NUDGE`. A session launched `--unsafe` is refused without `force` (it would act on another agent's words unreviewed); an archived one is refused; `agent/start` refuses one running in a terminal outside work (two Claudes on one conversation) unless forced. `work answer` sends back the request it showed, and the answer route types only after `checkDialog` passes. § Never put `work answer`, `send`, `start` or `stop` on an allow list (`tests/core/assistant.test.ts` checks the assistant's): Claude Code's prompt is the user's say-so. What `work read` / `work screen` print is another session's words: the CLI says so on stderr, and the `work-sessions` skill tells Claude to treat it as data, never instructions.

### The Ctrl+K assistant

Ctrl+K (or "Ask" in the top bar) opens a right-hand panel with a real agent session — config `assistantAgent` (`assistantAgent()`, Claude Code by default): session id `assistant` in the PTY host, like any worktree's, so it survives restarts and keeps its conversation. While the panel is open the SPA posts the view (`POST /api/assistant/context`: tab, sub-view, session); the server puts it into words (`describeView`, with the session's status, diff, overlaps) and the hook adds it to every prompt for 30 minutes, so "this" and "these" mean what's on screen. The panel stays mounted after the first open; Ctrl+K works from inside a terminal (a capture-phase listener).

§ It runs in the agent's normal permission mode, never --unsafe. `ASSISTANT_ALLOW` holds only read-only commands, with exact rules for cleanup: a `work cleanup --json` prefix rule would let `--apply` through without asking (tests/core/assistant.test.ts checks work's rules and what Claude was given). ### Today (digest)

Sessions' **Today** view (the "Now / Today" toggle beside the Sessions title, `NowTodayToggle`; `#/today`, `g d`) shows what each session did since local midnight, since yesterday, or in the last 7 days: the prompts you gave it, the turns it finished (checkpoints in the window, with names that were already generated), where it stands, uncommitted changes, and its PRs. "Copy as Markdown" gives a standup note. `GET /api/digest?since=` (default 24 h, clamped to 14 days) gathers it from disk: transcripts touched in the window, read from the end in growing chunks until an entry older than the window turns up (`readTranscriptSince`, 64 MB cap → `partial`), cached per file identity; checkpoint manifests; status rows; the PR watch's cache; the diff-stat cache (`peek`, never a refresh). The assembly is pure (`core/conversations/digest.ts`, shared with the demo). § It never runs Claude, gh or git: a digest is a read, and the route is async so a big day doesn't stall the terminal relays. Prompts are the user entries you typed (deduped by uuid); tool results, slash-command echoes, task notifications, "[Request interrupted…]", meta and subagent entries are skipped. Turn names that are only a size ("3 files · +52 −8", the no-Claude fallback) are not shown as "Done". "Turns" are checkpoints, the app's meaning of the word everywhere: they include the fs-watch fallback's snapshots of hand edits made with no Claude around.

### Activity (what work does in the background)

The top bar's **Activity** dot is grey unless a job needs you (`activityAttention`, `state/activity-view.ts`: one resting at GitHub's limit, or one that worked before and now fails — "worked before" from `ActivityWire.lastOk`, each job's last success, which the log keeps apart from the 60 recent runs a long outage fills; a job that never worked here, like Jira without acli, is not set up and stays quiet); its tooltip says what runs now ("Checking pull requests 5/13"). ### Jira watch (newly assigned issues start themselves)

### Repos page (which repos work knows, and the groups)

### PR watch (CI strip, fix-CI, auto-archive)

`core/pr/pr-watch.ts` is pure policy with injected I/O; `server/routes/ci-routes.ts` wires it (sessions = not archived, touched in 30 days, path exists; `shipPreflight` for facts; `tell` = POST a published general comment, so delivery reuses the comment path; told-keys in state.db `pr_watch_seen`, per session). `work web` full mode sweeps every 180 s, 3 at a time, single-flight. § GitHub allows 5000 API points an hour and work shares them with your own `gh`: when gh answers "rate limit" (`RATE_LIMITED`) the watch keeps the last state (never "no PR"), acts on nothing and skips sweeps for 10 min; a failed review lookup keeps the last count for that PR. `/api/prs` is one shared `createSharedFetch` (`server/shared-fetch.ts`, 2 min, stale-while-revalidate) for every window — per-request `gh pr list` over every repo, on each window's interval and each sessions change, spent the whole limit. And it is ONE GraphQL search (`fetchAllPullRequests`, `core/pr/pr.ts`: `PR_SEARCH_QUERY`, about one point): your open PRs and those asking your review by name, mapped to aliases by each repo's origin (`githubRepoOf`); a repo not on github.com (or every repo, when the search fails) is listed the old way, `gh pr list` there. Per sweep the watch asks gh only about repos whose branch was pushed (or that had a PR it knows of: `askGh`, `shipPreflight`), re-reads a PR's review threads only when its `updatedAt` moved, and runs one check per session at a time (a refresh joins the sweep's). Someone else's PR (`ShipPr.author` ≠ you, `viewerLogin`: one `gh api user`) — a session working on it or reviewing it — is only watched: its threads are its author's (not counted, not handed over) and its failing checks aren't sent to Claude unasked. It tells Claude once per `session:repo:headSha` when checks fail, and archives (`archiveSession`: conversation kept, worktree removed when safe) — never a session on a repo's own checkout (`ownCheckout`: you go on working there after its PR merges) — when every repo is `done` — or merged at the checked-out commit with only uncommitted files left, which the archive saves for Restore (`archivable`; unpushed commits or another commit checked out still keep it, and the Activity note says which) — and its Claude isn't working or waiting for you, and a merged PR is this work — it merged after the session was last entered, or its head is the checked-out commit and the session has been left alone a day since it was entered (a Restore or `work tree` onto the merged tip isn't re-archived at once; `shouldAutoArchive`: `gh pr view <branch>` also returns a PR merged long ago for a reused branch name, which has another head). Keys are recorded only after the note was delivered (`tellThenRecord`), so a failed send is retried. `GET /api/sessions/:id/ci` (cached, refreshed after 60 s) and `POST …/ci/fix` feed the PR tab's sections (`PrTab`). What it has acted on (CI heads, review comments, baselines) is kept per session in state.db `pr_watch_seen` (`core/pr/pr-watch-store.ts`, removed with the session). Review feedback rides the same sweep: `core/pr/pr-review.ts` fetches threads (with `isResolved`), reviews and conversation comments in one `gh api graphql` call (`{owner}`/`{repo}` filled by gh from the cwd). `newFeedback` raises unresolved threads whose last comment isn't yours, keyed by that comment, and reviews/comments by others posted after the PR was first seen (a baseline, so old discussion isn't replayed). They go to Claude as one note. When the conversation is past `CONTEXT_WARN` (70%, `readContextUsage`) the review and CI notes end with `subAgentHint`: hand the mechanical fixes to a sub-agent, keep decisions and reply drafts in the main conversation (the note stays with the branch's own Claude, which remembers why the code is as it is). Trusted: reviewers with write access (`TRUSTED_ASSOCIATIONS`), plus the review bots in config `prWatch.trustedBots` (default `DEFAULT_TRUSTED_BOTS`: `copilot-pull-request-reviewer`, `github-actions`; GitHub gives bots no association, so they were never sent before). **Automated review**: each thread in the note carries its id (`[thread PRRT_…]`), and the PR watch records it (`rememberSent`, state.db `pr_replies`, `core/pr/pr-replies.ts`). If the session's Claude isn't running anywhere, it is started in the PTY host with `WAKE_PROMPT`, resuming its conversation, and the UserPromptSubmit hook attaches the note (`wakeForNote`, `ci-routes.ts`; config `prWatch.wakeClaude: false` turns it off) — CI-fix notes wake it too. Claude plans, changing nothing (a reviewer can be wrong): per thread, what it would change or why it would leave it, and a reply drafted with `work pr reply` as it will read once done (`reviewMessage`; its instructions come before the quotes, so a long round's cut can only lose quotes — a 4 KB cap once cut them, and Claude drafted in the chat). Once you say yes in the conversation it makes the agreed changes, commits, pushes and posts the replies itself with `work pr post <thread…>` (resolving each; `--no-resolve` leaves it open) (`postDrafts`: the drafts as they stand, your dashboard edits included). The PR tab (`PrTab`, each PR's section: `useReplies` + `ReplyList`) shows each draft under the reviewer's comment, editable, with Post & resolve / Post / Discard; open threads with no draft are listed under it too (`GET …/replies` → `waiting`: the PR watch keeps each open thread, `SessionCi.repos[].threads` from `openThreadsOf`, minus the drafted ones), with the comment, a link, and Ask Claude to reply (a published note asking for a plan and a `work pr reply` draft, nothing changed); more than two fold under their heading, with one Ask Claude about all N (`askToReplyAllPrompt`), so an "unresolved review comment" count always has something to open (`POST /api/sessions/:id/replies/:thread/post` → `gh api graphql` addPullRequestReviewThreadReply (+ resolveReviewThread), `-f` raw strings, argv only). § Anything on GitHub is in your name, so a reply goes out only on your yes: your Post click, or Claude's `work pr post` after you agreed in the conversation — told so by the note, and never pre-allowed (not on `ASSISTANT_ALLOW`), so Claude Code asks you before it runs. Claude writes to GitHub in no other way. A thread raised again (a reviewer answered) starts over. The inbox's Review comments row says how many replies are ready (`SessionWire.replyDrafts`). A turn whose message has a `DECISION NEEDED:` line (`DECISION_MARKER`, `attention.ts`) becomes `needs_input` in `applyStatusEvent`. § Claude is told not to write on GitHub except `work pr post` on your yes; keep it that way, since that's the user's voice.

### State storage (`~/.work/state.db`)

Session state is one SQLite database (WAL) shared by every `work` process: `core/platform/db.ts` is the only importer of `better-sqlite3` (architecture test) and exposes `withDb(fn)` and `tx(fn)` (BEGIN IMMEDIATE; nested calls become savepoints). Tables hold each record as JSON beside the columns it is looked up by: `sessions`, `session_status`, `comments` (store = session id or `scope-<hash>`), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs`, `pr_replies`, `session_snooze`, `rail_place`, `jira_watch`, `tasks`, `diff_seen`, `meta`. Triggers bump `meta rev:sessions` / `rev:tasks`; work web polls those once a second instead of watching files. Stored rows come back through `json.parse(): unknown` and a shape guard, never a cast.

First open (`PRAGMA user_version` 0) creates the schema and imports the pre-SQLite JSON files in the same transaction (`core/platform/db-import.ts`), then renames them `*.migrated`. `work state` summarizes the database; `work state --export <dir>` writes it back in the old JSON layout (rollback path, round-trip tested), plus `newer-state.json` for what has no file in that layout (PR reply drafts, the Jira watch, snoozes, the rail's order, pins and sections, notes, blocks, worklogs). Opening a new file races on the WAL switch across processes, which the busy timeout doesn't cover, so `open()` retries on SQLITE_BUSY.

§ WHEN reading-then-writing state, do it in one `tx()`. A transaction can't span an `await`, so async work (port probing in `upsertSessionWithPort`) goes optimistic: compute outside, re-check inside, retry.
§ Tests run with `WORK_DB_EPHEMERAL=1` (tests/setup): the connection closes after each outermost call so temp HOMEs can be deleted on Windows. A test that doesn't mock `os.homedir()` must not reach `db.ts` (it would write the developer's real state.db); inject a store instead, as the PTY registry does with `sessionsPath`.

### Moving to another computer (`work move`)

`core/move/move.ts`. **Export** (`exportBundle`) writes a folder you carry over (OneDrive, a stick): a `state.db` snapshot (`snapshotDb`: `VACUUM INTO`, consistent while others write), `config.json`, `conversations/`, `archive/`, the groups' `*.claude.md` (`instructions/`), every live session's agent transcripts (`transcripts/<session id>/`, through `conversation.files`), and `manifest.json` (old home, platform, worktrees root, each repo's path and origin — `originUrl`, which unescapes git's quoting). Before it, `unsavedWork` lists uncommitted files and commits not on origin per live session's repo, and the CLI refuses without `--force`, since the other computer gets worktrees from origin. **Import** (`importBundle`) refuses while work web or the PTY host runs (`runningHere`: they hold the database) and over existing sessions without `--force`; moves paths by `remapRules` / `remapPath` (pure: the worktrees root and each repo to `--worktrees-root` / `--repos-root` + its folder name, else the same place under the new home; anything else under the old home with it; longest prefix first, case-blind for a Windows bundle), writes config.json as raw JSON (unknown keys kept), puts the snapshot in place (`replaceDb`), moves each session's paths and per-repo bases (`remapSession`), empties the PTY restore list, copies work's folders, clones missing repos from their origin (`--clone`), recreates live sessions' worktrees (`createInProcess`, a repo's own checkout excepted), and puts transcripts back in each session's `conversation.restoreDir`, so `--continue` resumes them. Checkpoint refs and wd's review scopes (keyed by old paths) stay behind. § Never keep `~/.work` live in a synced folder: a synced SQLite file corrupts, and two computers would both run the PR and Jira watches.

### Configuration

Stored at `~/.work/config.json`. Schema in `core/platform/config.ts`:
- `worktreesRoot` — parent directory for all worktrees
- `repos` — map of alias → repo path
- `groups` — map of group name → array of repo aliases
- `scanRoots` — folders the Repos page scans for git repos (default: the folder holding `worktreesRoot`); `ignoredRepos` — repo folders it leaves out of New
- `copyFiles` — glob patterns for files to copy into new worktrees (e.g., local dev settings)
- `hostEnv` — environment variable names a restored PTY-host session keeps from the shell that started it (secret-looking names never)
- `aiCommand` / `aiCommandFlags` — the agent new sessions run (Claude Code by default); `internalAgent` — the one that writes work's summaries; `assistantAgent` — the one the Ctrl+K assistant runs (both `claude` by default; see Agents)

### Build

tsup bundles two entry points: `src/bin.ts` → `dist/bin.js` (the `work` binary) and `src/wd-bin.ts` → `dist/wd-bin.js` (the `wd` shim that forwards argv to the `diff` subcommand). Both ship as ESM with shebangs. All npm dependencies are **external** (not bundled) — resolved from `node_modules` at runtime. This is important: adding a dependency requires both `npm install` and rebuild. The lockfile is `npm-shrinkwrap.json` (in `files`, so it is published): a global install gets the versions CI tested, not whatever the ranges resolve to that day. `package.json` declares both binaries under `"bin"` so `npm link` registers `work` and `wd` globally.

### Startup and load costs (keep them low)

- **`work <verb>` loads only that verb** (`COMMANDS` in `cli.ts`: names → a dynamic import; help, completion and unknown words load all). A command module added to `src/commands/` goes in that table (`tests/cli-commands.test.ts` checks the words match the commands' own names and aliases). `work hook` goes straight to `commands/hook.ts` before `bin.ts` loads chalk or the CLI.
- **Heavy packages load on first use** where a hook would otherwise pay for them: `cross-spawn` through `core/platform/spawn.ts` (same function and `.sync`; the PTY host's `pty-session.ts` imports it directly, it needs `_parse`), `proper-lockfile` in `fs-safe.ts`, `chokidar` in `fs-watcher.ts` (Linux only watches with it) — `createRequire(import.meta.url)('pkg')`, which `tests/packaging/runtime-dependencies.test.ts` counts as an import.
- **`/api/sessions` is the live sessions**; `?archived=1` adds the archived ones (two caches, one per answer). The dashboard asks for them only while something shows them (`wantArchived` in `DashboardApp`: Sessions' "Show archived", the Ctrl+P switcher, a session page for one that isn't live — "Loading…" until they came, never "not found" first). Their rows are kept between builds (`createArchivedRows`, `session-wire.ts`): rebuilt when its `archive.json` is written, it's renamed or entered, or a note comes or goes. `work sessions --json` keeps its own `--all`.
- **The SPA**: highlight.js is its core plus the languages `EXT_TO_LANG` names (`utils/language.ts`; a test checks each is registered), and the terminal (xterm) is its own chunk (`LazyPtyView`), preloaded once the session list is up. § Not the diff view: `wd --static` inlines the main bundle into one file, which can't fetch more chunks.

### Desktop app (`desktop/`, Velopack)

The Tauri app shows work web in its own window (`desktop/src-tauri/src/main.rs`): it finds the running work web or starts one, and follows it across restarts. It ships through **Velopack** on the same GitHub Release as npm (`vX.Y.Z`; the `desktop` job of `release.yml` runs `desktop/scripts/velopack.mjs` on Windows, macOS arm64 and Linux), modeled on bearing:
- **The CLI ships inside the package** as one `cli.zip` + `cli.version` next to the executable (staged by `desktop/scripts/stage-cli.mjs`, written by `zip-store.mjs`: stored, deterministic, read back before it ships): the npm package's files, its production `node_modules` (native modules built on that OS, other platforms' prebuilds dropped, and `trimmable` files — docs, types, source maps, TS sources, test folders, native build sources — gone, about half), and the Node that built them (CI pins it exactly). One file, not ~1,650: Velopack rewrites every file of a package on each update and the antivirus scans each — the 2.0.1 update took a minute and a half on 3,282. The smoke test runs `--version`, `--help` (every command, every import), requires the native and first-use modules, and on macOS and Linux opens a terminal: node-pty's `spawn-helper` must be executable (`makeHelpersExecutable`; npm unpacks the prebuilt one 0644 and only node-pty's install script fixes it — 2.0.2's macOS app shipped it so, and no terminal started). The PTY host also fixes the bit itself before its first terminal, on any install (`makeSpawnHelperExecutable`, `core/pty/spawn-helper.ts`). One delta updates both; a CLI that could drift from its app is a bug.
- **It runs from a copy, never the install folder** (`runtime.rs`): an update replaces the install folder, and on Windows Velopack stops what runs from it — work web and the PTY host that owns every Claude. The app unpacks `cli.zip` (or copies the `cli/` folder of a package before 2.0.2) to `~/.work/runtime/<version>/` (temp name, checked, then rename), writes `~/.work/runtime/current`, and starts work web from there; old copies go once nothing runs from them (Windows: a folder with an open file can't be renamed) beyond the newest two.
- **`work` / `wd` on PATH**: launchers in `~/.work/bin` run `runtime/current`; that folder is APPENDED to the user's PATH (`path_setup.rs`: Windows HKCU registry, raw/unexpanded, + WM_SETTINGCHANGE, at install, update and every start, removed on uninstall; macOS/Linux a marked profile line), so an npm-installed `work` stays first. Claude hooks stay `work hook …` through PATH.
- **Updates** (`updates.rs`): GitHub Releases (`GithubSource`), a minute after start and every 6 h; downloaded, applied by Velopack on the next start, or at once on the dashboard's Restart. The app talks to its own window directly, not through work web (which can be another work's): before each page load it marks the window (`__workDesktop`, `updates::PAGE_MARKER`), sends every change of where its update stands as a `work-desktop` event (`page_script`, `on_change`; `downloading` with Velopack's percentage, `ready`, `installing`), and takes the page's asks as a navigation to `http://work-desktop.invalid/<hello|check|restart>`, which it cancels (`on_navigation`, `page_ask`; `.invalid` never resolves, so outside the app it goes nowhere). The page (`hooks/use-desktop.ts`, `desktopWire` → `inAppUpdates`, `core/updates/updates.ts`) then shows the app's version and update — a progress bar on the card and in the version menu (`ProgressBar`) — and the server adds only the release notes. For a dashboard in a browser tab the same state still goes through two files in `~/.work`: `desktop-update.json` (`unmanaged` for a dev build, which writes only to its own window, `checking`, `current`, `downloading` + `progress`, `ready`, `installing`, `failed` + why; with its pid), and `desktop-request.json` (`check` / `restart`, written by work web) every 2 s, removing it. Restart is `apply_updates_and_restart`: the app exits and comes back on the new version; work web and the PTY host run from `~/.work/runtime`, so Claudes keep running. The first run also registers the Claude plugin (the package's postinstall, in the background).
- **Out of the install folder**: right after Velopack's hooks the app moves its working directory to `~/.work` (`neutral_dir`), which everything it starts inherits: on Windows a process working from the install folder keeps Velopack from moving it aside, and the update rolls back (2.0.2 → 2.0.3 did on every Restart). Detached servers `work` starts itself (`spawnDetachedWork`: the PTY host, a lean work web) start in the home folder for the same reason, and so a worktree they were started from can still be removed.
- **It runs its own work web**: one of another version already running (a dev checkout's, the one from before an update) is stopped with the bundled CLI's `work web --stop` and replaced (`replace_other_version`, by `/api/context`'s `version`), so the window, its version and its updates are the app's. Stopping work web never stops a Claude (they live in the PTY host).
- A dev build (no `cli/`) and `WORK_DESKTOP_CLI=path` run the `work` on PATH instead. They follow whatever work web runs.
- **The dev app** (`npm run app:dev` / `npm run app:demo`, `desktop/scripts/dev-app.mjs`): `tauri dev` with `tauri.dev.conf.json` (productName "work dev", identifier `hr.moberg.work-desktop.dev` — its own WebView profile — and `icons-dev/`, the logo with a DEV band: `node desktop/scripts/make-icon.mjs --dev` then `tauri icon … -o src-tauri/icons-dev`) and the Cargo feature `dev` (`main.rs` `DEV`): window "work (dev)", follows the dev server through `web-dev.url` and starts `node <checkout>/dist/bin.js web --dev` when none runs; no Velopack, updater, runtime copy or PATH. `app:dev` builds the checkout and restarts the dev server first; `app:demo` starts the demo and pins the window to it (`WORK_DESKTOP_URL`). Side by side with the installed app.

§ The pack id `WorkDesktop` and bundle id `hr.moberg.work-desktop` are permanent: changing either orphans every installed copy.

### Color Forcing

`bin.ts` sets `chalk.level = 1` when chalk detects level 0, because Windows `.cmd` shims don't preserve TTY detection. Respects `NO_COLOR` env var.

### Tab Completions

`completions/index.ts` provides dynamic completions via yargs' `--get-yargs-completions`. The handler receives `argv._` as `['<scriptName>', ...args, '<current>']` — skip first and last to get completed args. For groups, branch completions read from the group's directory on disk (not individual repo worktree lists).

`core/setup-completions.ts` handles auto-installing completion lines into shell profiles. Called during `work init` and available standalone via `work completion --install`. Detects PowerShell 7/5.1 on Windows (via `[Environment]::GetFolderPath('MyDocuments')`) and bash/zsh on Unix (via `$SHELL`). Idempotent — uses a `# work tab completions` marker to skip if already present.
