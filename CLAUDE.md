## Critical Rules (Always Apply)

The highest-impact rules. Full standards in `.claude/rules/`.

- **§0.1** YOU MUST suffix relative imports with `.js` even though sources are `.ts` (`npm run typecheck` rejects one without: NodeNext resolution). Extensionless relative imports break at runtime under Node ESM (136 `.js` imports, 0 extensionless). See `.claude/rules/architecture.md` §2.5.
- **§0.2** Session state lives in `~/.work/state.db` (SQLite, `src/core/platform/db.ts`). Files that stay files (`config.json`, `~/.claude/settings.json` edits) keep `withFileLock` + `atomicWriteFile`. See `.claude/rules/data-layer.md` §5.

- **§0.4** WHEN building git/shell commands, use `cross-spawn` with an argv array — DO NOT interpolate branch names or paths into a shell string (command-injection risk). See `.claude/rules/security.md` §1.1.

## Architecture & CLI Reference

The remainder of this file is the architecture / CLI reference for human readers and agents that need the full picture of module flow, command surface, and the `wd` / `work web` design. The standards above (skill routing, critical rules) are the canonical short list; this section is the long form.

## What This Is

A cross-platform TypeScript CLI (`work`) for managing git worktrees across multiple repositories. Supports single-repo and multi-repo "group" worktrees with automatic Claude Code launching. Installed globally via `npm link`.

## Development

```bash
npm run build          # Bundle with tsup → dist/bin.js
npm run dev            # Run directly via tsx (no build needed)
npm test               # Run all tests with vitest
npm run test:watch     # Watch mode
npx vitest run tests/core/resolve.test.ts  # Single test file
```

After building, `work` is available globally (via `npm link`). Rebuild after source changes.

§ Dependency direction: `commands/` and `server/` call `core/`; core never imports either (architecture tests). Among commands, only `web.ts` (starts work web) and `diff.ts` (the foreground `wd -c` server) import `src/server`; logic a command needs from a route lives in core (`*-deps.ts`, `session-start.ts`). Within core, a feature imports another's module directly — the folders group by feature, they are not layers.
§ WHEN adding a module, put it in the feature folder it belongs to (a new folder for a new feature, not core's root); routes go in `src/server/routes/`, and their test in the mirrored `tests/` folder.

### Core is a library: two front-ends, one implementation

`src/core` holds every piece of logic; the CLI (`src/commands`) and the HTTP API (`src/server`, its routes in `src/server/routes/`, the backend for the SPA and the desktop app) are thin front-ends that call it. Neither calls the other. Pure pieces that the SPA shares live in core and are re-exported by the SPA: `session-view.ts` (status vocabulary, age sections), `digest-view.ts` (Today windows and Markdown), `saved-prompts.ts`, `attention.ts`, `api-types.ts`.

§ Core never prints (architecture test §2.7): no `chalk`, no `console.*`, no raw stdout/stderr writes under `src/core` or `src/server` (`platform/logger.ts` excepted). Use `report(level, text)` (`core/platform/report.ts`). The reporter is scoped with AsyncLocalStorage (`withReporter`): the CLI shows reports with colors (`commands/shared/console-reporter.ts`: stdout for `work`, stderr for `wd`), servers default to the debug log, and a route can collect them (`collectingReporter`) to return a failure's real reason — `POST /api/worktrees` does.
§ WHEN adding logic, put it in core and call it from both front-ends; a route or command handler only parses input and formats output. `work sessions --json` rows come from `sessionWire` (`core/sessions/session-wire.ts`), the same function as `/api/sessions`; the digest from `createDigestSource` (`core/conversations/digest-source.ts`); cleanup from `scanCleanup` / `applyCleanup` (`core/cleanup/cleanup.ts`, deps in `core/cleanup/cleanup-deps.ts`).

Claude reads this data through the CLI (`--json`), described to every session by the `work-sessions` skill in the plugin (`plugins/work-tree/skills/work-sessions/SKILL.md`).

### Key Design

- **Shared core operations:** `setupWorktree()` and `teardownWorktree()` in `core/worktree/worktree.ts` are the high-level entry points used by both the CLI commands and `work web`. They resolve targets, create/remove worktrees, handle group CLAUDE.md, and manage sessions. Low-level building blocks are `createSingleWorktree()` and `removeSingleWorktree()` which handle one repo with rollback on failure.
- **Resolver pattern:** `resolveProjectTarget()` in `core/worktree/resolve.ts` dispatches a name to either a group or single repo, returning `{ isGroup, name, repoAliases }`. Commands use this to branch into group vs single-repo handlers.
- **Branch resolution order:** local exists → remote exists (creates tracking branch) → neither (creates new branch). A new branch made without `--base` comes from the repo's own checkout, and that branch is recorded as the session's base (`created.from` → `baseBranch` / `baseBranches`), so "Since branch" doesn't guess. A recorded base is read at its freshest (`recordedBase`: the branch or `origin/<it>`, whichever shares the later commit with HEAD — the local one is pulled only when a worktree is made from it), and one that's gone (merged and deleted) leaves it to detection; a group gets one `baseBranch` only when every repo has that base. When it must guess (`findParent`, `core/diff/diff-scope.ts`: the candidate with the newest merge-base), a candidate containing HEAD is skipped — a `dev` this branch was merged into — unless the branch has no commits of its own yet (`stillAtCreation`: its reflog says it was made here from HEAD or a mainline and HEAD hasn't moved — not one made from its own `origin/` copy, a PR, or at a commit, Restore), when that's where it came from: skipping it showed a branch just made from dev with all of dev since main.
- **Path convention:** Branch directories replace `/` with `-` (e.g., `feature/login` → `feature-login`). Single-repo worktrees at `<worktreesRoot>/<repoFolderName>/<branch-dir>/`, groups at `<worktreesRoot>/<groupName>/<branch-dir>/<repoFolderName>/`; with `sessionFolders` on, every new session (a single repo's too) is a folder session at `<worktreesRoot>/<branch-dir>-<id6>/<repoFolderName>/` (`session-folder.ts`: `flatFolderName` — the branch, then the first six characters of `sessionIdFor`, so one branch name in two projects gets two folders; fixed for the session, so Restore puts it back where Claude Code finds its conversation; `sessionFolderPath` keeps an existing session's layout, recorded in its folder's name; `flatFolderOwner` lets hydrate find a flat folder's project).

### `work dash` (removed in 2.0)

`work dash` (the Ink TUI with its own PTYs and http-type hook server) was retired: use `work web` (browser dashboard) + `work attach` (a real terminal on the same PTY-host session). Its leftover http hook entries in `~/.claude/settings.json` are PID-tagged and pruned as stale by the next `work web` hook install.

### Re-entering a worktree (pull + resume)

`work tree` is both "create" and "switch back", and switching back is the common case. Whenever the target checkout already exists — an existing worktree, or the base repo when the branch positional is omitted — two things happen before the AI tool launches:

- **Pull.** `pullLatestForBranch()` (`core/worktree/worktree.ts`) runs fetch + pull in that directory. Best-effort by design: a branch with no upstream returns early (a bare `git pull` there prints a "no tracking information" error that reads as a failure), and a pull blocked by a dirty tree or conflicts only warns. It must never block getting into the worktree. Threaded through `setupWorktree(..., { pull })` → `createSingleWorktree(..., pull)`; `--no-pull` sets it false. A freshly created worktree skips this — it is already at the branch tip.
- **Resume.** `launchTool()` in `commands/tree.ts` passes `resume: true` so the tool gets its resume flag (`--continue` for Claude Code). Gated on `hasClaudeConversation(dir)` (`agents/claude/activity.ts`, a transcript-exists check over `~/.claude/projects/<encoded-cwd>/*.jsonl`) because `--continue` hard-errors with "No conversation found to continue" in a directory Claude has never run in — the same gate `work resume` and the PTY host use. `--fresh` opts out.

§ WHEN adding another launch path, resolve the resume flag through `hasClaudeConversation` rather than passing `--continue` unconditionally.

**A repo's own checkout stays on its branch.** Branches are work's: new work gets a worktree. A session on a repo's own folder (`work tree <repo>`, no branch; `isOwnCheckout`, `core/worktree/own-checkout.ts`) gets `ownCheckoutNote` on every turn start (`runTurnHook`): stay on its branch, don't create, switch or check out branches, don't open PRs from it, ask for a worktree instead. The PR watch never archives one (`ownCheckout`).

### PTY host (sessions that survive restarts)

Claude PTYs are owned by the **PTY host** (`work pty-host`, hidden), a detached localhost process — not by `work web`. `work web` (via `core/pty/pty-pool.ts`) and `work attach` are clients: restarting/rebuilding `work web` or closing a terminal only drops a view. Discovery: `~/.work/pty-host.json` (pid, port, random token; every request carries the token, plus a Host-header check). **The Terminal tab connects straight to the host** (reported: typing lagged in the app while `work attach` in Windows Terminal — the same host, no work web — was smooth; every keystroke and echo waited on work web's event loop, which stalls now and then): it asks work web `POST /api/terminals/:id/ticket` (`terminal-routes.ts`: the "running elsewhere" check unless `force`, `ensurePty`, then `terminalTicketUrl` → the client's `ticketUrl` → the host's token-authed `POST /tickets`), and connects to the host's attach address with a **one-time ticket** (`core/pty/terminal-tickets.ts`: for that one terminal, from the page's own origin — only a page on this machine, `isLoopbackOrigin` —, within `TICKET_TTL_MS` (30 s), used once and burnt on any mismatch); the token never leaves work web. `openTerminalSocket` (`api/terminal-socket.ts`) is the tab's socket either way: a host from before tickets (`HOST_FEATURES` `tickets`; `work pty-host --restart` gives it), an older work web, the demo (`{fallback: true}`), a failed request or a direct connection the host turned down go through work web's relay (`/ws/sessions/:id/terminal`, `terminal-ws.ts`) as before; "elsewhere" and a refused start reach the tab as the relay would have said them. The corner's tooltip says which way it connected (`cornerBadge`'s `route`). Live sessions are mirrored to the restore list (state.db `pty_sessions`); on host start they are respawned with `--continue` (the "restored" flag), so a crash, `--restart` or reboot picks up where you were. A PTY that exits on its own is forgotten after 5 s (not immediately — at Windows logoff the children die just before the host); an explicit kill (worktree delete) forgets it at once. Several clients may attach to one PTY; the one used last sets its size — resized or typed in (tmux's `window-size latest`; each connection keeps its own grid, `pty-host.ts`; a terminal's own replies — focus in/out, answers to queries — aren't typing, `isTerminalReply`, or every attached client answering a query would pull the size its way): with the last resize alone, opening a session in the app shrank the PTY to the app's grid and a terminal attached by `work tree` stayed drawn for that size while you typed in it. An explicit kill (`work stop`, archive, delete, idle sleep) tells the attached clients it ended (`kill` keeps the exit subscribers until the process is gone), so a Terminal tab offers Enter to start it again instead of a screen that takes no input; a start that fails (the connection closes before the screen came, the server's error said) shows why and tries again after 3, 10, 30 and 60 s, with Try now (`state/terminal-start.ts`), never a "Starting Claude…" left for good; ⋯ → Reconnect terminal (⇧R, `state/terminal-reconnect.ts`) opens a new connection whatever state it's in.

**Idle Claudes sleep** (`core/pty/idle-sleep.ts`, a 5-minute sweep in full-mode `work web`): a host PTY with **no client attached** (`PtyInfo.clients`), that has **printed nothing** for `sleepIdleAfterMinutes` (config, default 10, at least 5; 0 = never; `PtyInfo.lastOutputAt` — an idle Claude prints nothing, a working one redraws its spinner), and isn't the assistant, is stopped (`disposePty`) — only when it is truly idle (`stillAtWork`, `sleepPlan`; the I/O in `core/pty/sleep-checks.ts`): the status the dashboard shows isn't working or waiting on you, Claude Code's own state for the process isn't busy (a background agent) or waiting, no background command its conversation started since the process began is still running (`backgroundCommands`, Claude's `openBackgroundCommands`: a `run_in_background` call with no `<task-notification>` — read from any line, queued or delivered — nor `TaskStop`), and nothing runs from its folders (`runningFromNames`: a dev server, a watcher); a check that can't tell keeps it awake, and the Activity panel says why each one stayed. Stopping a Claude stops what it started. It stops holding memory, and opening the session resumes the conversation: the stop is recorded (`markAgentStopped` → `SessionStatus.stoppedAt`, also by `work stop`), so the Terminal tab's "running in another terminal" check (`claudeElsewhere`, `lastStop`) ignores the turn that ended just before — what held the minimum at 30 minutes. The dashboard's terminal deck (`TerminalDeck`) keeps up to 5 terminals connected for instant switching, but one hidden for `DECK_HIDDEN_MS` (10 min) lets go (`pruneDeck`), so its Claude counts as unattended and can sleep — with the app open all day, the five most recent Claudes otherwise never slept. `clients`/`lastOutputAt` are additive: a host from before reports neither, and then nothing sleeps.

**Heartbeat and latency.** The pool's 2 s list request is the host's heartbeat (`hostBeat`, `core/pty/pty-pool.ts`). `core/pty/host-health.ts` (pure) reads it as ok, slow (an answer over 1.5 s) or not answering (none for 11 s; a busy host counts as a host). `GET /api/pty-host/health` serves it, a `host-health` broadcast goes out when it changes, and the dashboard shows `HostHealthBanner` only when it isn't ok. The host outlives updates, so `/health` also says which release it runs (`work`, `PtyHostClient.workVersion`, read once per host; `''` from a host from before): one other than this work web's (`HostHealth.outdated`; dev builds never compare) shows too. A host that's older or not answering gets **Restart it** (`hostNeedsRestart`; `POST /api/pty-host/restart`, `pty-host-routes.ts` → `restartHost`, the `--restart --force` path: stop — killed when hung and still ours —, then start; sessions come back with `--continue`; refused on the dev server). Each terminal start is timed (node-pty's spawn is synchronous and holds the whole host): over 5 s is a warning. Config `useBundledConpty` (Windows) starts terminals on the ConPTY node-pty ships (`conpty.dll` + `OpenConsole.exe`, Windows Terminal's) instead of Windows' own, whose start hung a host once (`conptyOptions`, read at each start; off by default, node-pty calls it experimental; the desktop app's staged CLI keeps both files). The Terminal tab measures a keystroke in two parts (`LatencyMeter`, `state/keystroke-latency.ts`): its echo arriving (key sent → next output: browser → work web → PTY host → ConPTY → Claude and back) and its redraw on screen (key sent → the last frame xterm drew of the redraw it caused — Claude Code redraws its prompt in several chunks — once nothing came in or was drawn for `SETTLE_MS`; reported: "29 ms" and typing still felt laggy), each the median of the last 20 and the slowest of most of them (the 90th percentile, so a stall shows). The corner shows the on-screen time — "⌁ 41 ms", "(210 ms)" beside it when the slow ones are much slower — with both parts in its tooltip (`cornerBadge`), amber from 100 ms. That's where to look first when typing feels slow. The terminal draws with WebGL; a lost context (GPU reset, sleep/resume) falls back to the DOM renderer, which is slow with a busy Claude, so the corner then says "DOM" and it tries WebGL again after 2 s, 10 s and 60 s (a try that fails counts as a loss), staying on DOM at the fourth loss in 10 min (`WebglRecovery`, `state/webgl-recovery.ts`); each swap refits the grid, since the renderers measure a cell differently. Measured (2026-10): a working Claude sends ~14 frames/s at ~1 KB/s; even 4 MB into five deck terminals at once kept the page at 60 fps with no long task — drawing isn't where time goes.

**The environment of a restored session.** A restore spawns with the host's environment, not the launching shell's: `env` is one-shot and never stored (it can hold secrets). Config `hostEnv` (none by default; e.g. `["JAVA_HOME", "PATH"]`) names variables to keep: their values from the shell that started the session go into its restore-list entry (`keptEnv`, `keepEnv` in `pty-host-protocol.ts`), and a restore — or a respawn without a shell, from the Terminal tab — runs with the host's environment plus those. Names that look like secrets or carry them (`*TOKEN*`, `*SECRET*`, `*PASS*`, `*KEY*`, `*AUTH*`, `*_PAT`, `DATABASE_URL`, `*_URL`, connection strings, …) and values with a password in a URL (`scheme://user:pass@`) are never kept, whatever the config says.

**Status for a tool with no hooks.** For a session whose PTY runs another tool (`aiCommand`, e.g. opencode; `PtyInfo.tool`, additive), nothing reports turns, so `statusFromOutput` (`core/pty/output-status.ts`, pure) reads one from the host's `lastOutputAt`: working while it printed in the last 10 s, idle after (seen — output can't tell a finished turn from a question). It applies only when no hook status exists, in `/api/sessions` (the pool's refresh) and `work sessions`.

**Restarting agents** (`core/pty/agent-restart.ts`; `agent-restart-routes.ts`, `work restart`): a Claude keeps the binary it started with, so after Claude Code updates itself the running ones are on the old version. One whose process started before its tool's file was installed (`installedAt`: the file its command runs on PATH, `findOnPath`, through links; the newest of mtime and ctime, since npm unpacks with an old mtime) is outdated (`outdatedPtys`; a host from before `tool`, or a tool not on PATH: never). `GET /api/agents` lists them; the dashboard says so in the version menu (a dot on it) and a card in the update card's corner (`AgentsRestartCard`; Later per install time), both naming the sessions (`outdatedNames`: as the rail names them, the waiting ones last and marked "after its turn"; a name opens its session), and `POST /api/agents/restart` (`{outdated}` / `{ids}` / `{all}`) restarts them: idle ones at once, one working or waiting on you when its turn ends (`createRestarter`: `turnEnded` from the status hook, after `TURN_END_GRACE_MS` — the Stop's own hooks run as its children —, and every `QUEUE_RECHECK_MS` while anything waits; busy = Claude Code's own state for the process (busy / waiting: a permission dialog prints nothing; the assistant has no hook status), `shownState`, or a terminal that printed in the last 10 s; one restart per session at a time, shared (the route counts one mid-restart as running); one Activity run per request, kind `agents`, and a schedule while anything waits; wording in `restart-view.ts`; the dev server lists but restarts nothing). An old process that won't stop within 3 s ends the session as a stop does, never a second agent beside it. It runs with the environment the session started with (`Entry.env`, the host's memory only; never in the restore list). Install time (`installTime`): the later of the file's mtime and creation, npm's fixed 1985 date counting as neither (its change time then), never the change time alone (a chmod). A restart is the host's `POST /ptys/:id/restart` (`registry.restart`): the process stopped and started again in place with `--continue`, the attached terminals kept (not told the old one ended), so a Terminal tab or `work attach` carries on. Additive, no protocol bump: an older host answers 404 and the pool stops and starts it instead (`restartPty`).

**Halt and resume** (`registry.halt` / `resume`; `POST /ptys/:id/halt` | `/resume`, additive, an older host answers 404): halt stops the agent but keeps the session — its entry, restore record and attached terminals (not told it ended) — so something can change under it before it starts again; resume starts it in place with `--continue` and an optional `agentEnv` (`EnvDelta`), so the terminals carry on. A halted session is resumed by itself after `HALT_RESUME_MS` (5 min: a move of a big folder across volumes takes a while; said at warn) on its pre-halt spec should nobody ask, and a host restart restores it as any session (on its old spec too). A switch of Claude account is the user: halt → move the conversation folders → record the account → resume on its environment; when the resume finds it no longer halted (started again meanwhile, by the timer or a restore), the switch restarts it in place on the new environment (`client.restart(id, {agentEnv})`; not running: started fresh; an older host: stopped and started) and says so in its outcome (`RESTARTED_AFTER_AUTO_RESUME`; see Accounts, under Agents). **Host features**: `/health` answers `features` (`HOST_FEATURES`: `agentEnv`, `halt`; additive, a host from before answers none), which the client asks once per host (`PtyHostClient.features`); the pool refuses what an older host would silently drop (`OLD_HOST_ACCOUNTS`: "the PTY host is from before Claude accounts: run `work pty-host --restart`") — a spawn of a session on a named account (one already running there is only attached to; the Terminal tab shows the reason), a resume carrying an environment, and a switch of account before anything is halted (`accountSwitchRefusal`). A host that can't be asked in time is given the benefit of the doubt.

### Attention inbox

`work web` (full mode, owner `web-status`) installs its Claude hooks in one write (`FULL_HOOKS`, `commands/web.ts`): one per turn edge — UserPromptSubmit → `work hook turn-start`, Stop → `work hook turn-end` (`runTurnHook`: pending comments for Claude first, then the checkpoint nudge and the status record, side by side — one `work` start per turn edge instead of three, for every Claude on the machine) — plus Notification → `work hook status-notify`; the old separate hooks (`LEGACY_HOOKS`) are removed. The status part maps the cwd to a session (`findSessionForCwd`, group-root aware), apply the event (`applyStatusEvent`: prompt → working+seen; stop → idle+unseen with the transcript's last assistant line; a Notification matching `permission|approval` → needs_input) to state.db `session_status`, then nudge `POST /api/status-changed`. The server notifies only on a real transition (`notifyKindForTransition`) and broadcasts `sessions-changed`. ### Ship & archive

`Ship` runs `core/pr/ship.ts` per repo. **Groups ship in parts**: backend may be merged while frontend is in review.
- A repo is **done** when its PR is MERGED or it was never touched (0 commits vs `origin/HEAD`, clean, no PR). Done repos are never blockers and never selectable.
- "Published" means `origin/<branch>` exists — not `@{u}` (`work tree` leaves new branches tracking `origin/main`); ahead/behind are measured against `origin/<branch>`, and push uses `-u origin <branch>` unless tracking already points there.
- **Merge = `mergeSelected`**: the client sends `repos: [{name, headSha}]` — the repos the user ticked and the PR heads it SHOWED. The server re-runs the preflight and refuses the whole call if any selected repo is unknown, done, blocked, or its PR head moved; only then merges each with `gh pr merge N --<method> --match-head-commit <that sha>`, stopping at the first gh failure. Unselected repos are never touched.
- Blockers include: dirty tree, not pushed, unpushed commits, origin ahead of you, PR head ≠ local HEAD, draft, closed, conflicts, behind base, branch protection, failing/pending checks.
- The session is **archived only when the merge merged something AND every repo is done** afterwards.
- **Archive** (`archiveSession`, `core/archive/session-archive.ts` — the one path for the Archive button, Ship's merge, the PR watch and cleanup): first checks nothing is waiting (`archiveWaiting`: reply drafts to post, notes not yet delivered, a Claude working or waiting for an answer) — the button asks and can force it (409 `blocked` → confirm → `force: true`); cleanup waits. **Merged work decides it** (`{ merged: true }`: the PR watch's auto-archive and Ship's merge): drafts, undelivered notes and a finished turn's question for you don't hold it up, and only a Claude in the middle of a turn does (`turnInProgress`: working, or at a permission dialog mid-turn — a needs-input state entered after the last turn ended; stopping it would lose the pending tool call; tried again on the next sweep). Nothing is lost either way: those rows stay in state.db with the session (deleted only with it), so Restore shows the drafts and delivers the notes on its next turn, and `archive.json` lists them (`kept`: each draft's text, each note, the question), shown as "Also kept: …" on the archived session and in the Activity note. Then it stops its Claude, its dev server and whatever else still runs from its folders (`stopRunningFrom`, `core/platform/running-from.ts`: a process whose program is in them — an executable, or an interpreter's script, like the `vite` a Claude started in the background, which held a file in `node_modules` so git removed the worktree only in part; never one that only names the folder, like an editor open on it, nor an editor's language server running the worktree's own copy (`isEditorHelper`: tsserver, `--useNodeIpc`, `--clientProcessId`…); said in the outcome) (and releases watchers) — and from there to the end nothing may start that Claude again: `ensurePty` refuses a session being archived or archived (`core/archive/archiving.ts`), since a Terminal tab still open on it reconnects and would start it (an archived session once kept a live Claude that way, restored after every host restart), records each repo's branch tip, copies every transcript to `~/.work/archive/<id>/transcripts` (Claude Code deletes old ones itself) with `archive.json` (prompts, PRs, last summary), saves its **uncommitted work** (`core/archive/archive-uncommitted.ts`: modified, deleted and new files — not git-ignored ones — snapshotted into a commit on HEAD through a temp index like checkpoints, kept by `refs/work/archive/<id>/<repo>/<time>` in the repo and written as a binary patch to `~/.work/archive/<id>/uncommitted/`; at most 50 MB, else the worktree stays), and removes the worktree **only when cleanup's check says nothing would be lost** (merged, uncommitted files saved; commits not in the main branch still keep it; never a repo's own checkout). Its **git-ignored files that aren't build output** — local settings (`appsettings.Development.json`, `.env.local`), the editor's state (`.vs`, `.idea`) — are copied to `~/.work/archive/<id>/ignored/<repo>/` when the worktree goes (`core/archive/archive-ignored.ts`: async, smallest first, at most 5 MB a file, 50 MB a repo and 5,000 files looked at; environments and package caches — `.venv`, `packages` — left out like build output; only folders `git check-ignore` confirms are walked; `ArchiveRecord.ignored`), and Restore puts them back over the new checkout (`restoreArchivedIgnored`, once per repo, recorded even when one fails). They can hold secrets: `work move export` leaves them behind and retention deletes them after `archive.compressAfterDays` (`ignoredDroppedAt`). A kept worktree drops its save, since the changes are still there. **Removed only in part** (`core/worktree/leftover.ts`): `git worktree remove` deletes the files and stops at one in use (Visual Studio's), having dropped the `.git` link and the registration — a folder with no git (`isLeftover`). The archive counts that removed (`halfRemoved`, `ArchiveRecord.leftovers`) and keeps the save; Restore treats a folder with no `.git` as gone (`isWorktreeFolder`, not `existsSync`); before making it again, Restore looks for what still runs from that folder and refuses naming it (409 `holders`; the dashboard asks "Stop it and restore?" and sends `stopHolders`), and a creation that fails with the folder in use names what has it open (an editor: yours to close), and `createSingleWorktree` sets it aside (`<folder>.leftover-<time>`, refused with "close what holds it" while a file is in use), adds the worktree, and `setupWorktree` copies its files back after the save (`putLeftoverBack`: over a clean checkout, else only where nothing is; build output left out), then deletes it; a creation that fails puts it back where it was. Over the checkout only while the branch is at the archive's recorded tip: on a branch that moved since, it fills in only what's missing. A group where one repo is half-removed and another kept whole is kept (and keeps its saves). The dashboard shows such a folder as "not a git checkout any more" (`onOtherBranch[].noGit`). Removed: its checkpoint refs stay (deleted with the session, `clearSessionCheckpoints`: Restore puts the worktree back at the same path, so the Diff tab's turns come back), and a local branch already merged into the main branch is deleted (`branchesDeleted`; a squash-merged one stays — nothing else reaches its commits). Kept: the reason is recorded and its git-ignored build output is cleared. Afterwards an internal `claude -p` writes a few sentences on what was done (`summary.written`, `archive-summary.ts`), which the Sessions list shows and the conversation search finds. **Restore** (`work tree` into it, or Restore): `setupWorktree` first recreates a deleted branch at its recorded tip (`recreateArchivedBranches`), then the worktree, and `restoreArchivedTranscripts` puts the conversation back where Claude looks, so it continues. `restoreArchivedUncommitted` (`core/archive/archive-restore.ts`) then applies the saved patch to the new worktree, unstaged, once: it refuses a worktree that already has changes or a patch that no longer applies (the branch moved on), records why, and never tries again, so a later `work tree` can't bring old changes back over newer work; the ref and patch stay for doing it by hand. An archived session shows "· N changes saved" (`SessionArchiveInfo.savedUncommitted`). Deleting the session deletes its refs (`clearSessionCheckpoints` → `dropSessionSaves`). **Retention** (`archive-retention.ts`, daily, in the Activity panel): transcripts of archives older than `archive.compressAfterDays` (default 30) are gzipped — lossless, search and Restore read `.gz` (`readArchivedTranscript`); `archive.dropTranscriptsAfterDays` (default 0 = never) deletes them, keeping the summary. The archive folder goes with the session on delete (`sessionStatePaths`).

### Session Tracking

`core/sessions/history.ts` stores worktree sessions in state.db's `sessions` table (one row per `target + branch`). The `tree` command calls `upsertSession()` before launching Claude; `remove` calls `removeSession()` on success. The `status` command reads history + live git info; `recent` lists sessions sorted by last access.

**Session identity & state.** The id is `sessionIdFor` (`core/sessions/session-id.ts`: sha1(target:branch), 12 hex). The branch is the one it STARTED on, and names its folder; its name is separate — `title` (`--name`, the New worktree dialog's Name, F2 / Rename later), the rail's label when you gave one. Claude (or you) may switch the worktree to another branch: ship, the PR watch and the diffs read the checked-out branch from git; `onOtherBranch` (HEAD files, no git: `core/git/git-head.ts`) shows it; re-entering uses the folder as it is; archive records it (`heads`) so Restore of a removed worktree checks that branch out again. **A session's branches** (`core/sessions/session-branches.ts`; reported: a PR merged, Claude made two new branches from origin/dev in the same worktree with a commit each, and the session showed only the one checked out — the webhook work looked gone): every branch each repo has been on is recorded per session in state.db `session_branches` (schema v12, purged with the session; `{repo, name, firstSeen, lastSeen, from?, gone?, merged?, pushed?}`, shape-checked by `cleanBranches`), so nothing asks git each time. Written in one `tx()` at each turn's end (`runTurnHook` → `recordBranchesFor`: HEAD files, no git — `checkedOutBranch`; a branch new to the record gets `from` from its own reflog's first line, `branch: Created from origin/dev`, `core/git/reflog.ts`), when work checks a branch out (`setupWorktree`, re-entry, Restore, Update), and once for a session from before (`backfilled`: `backfillSessionBranches` reads each checkout's `logs/HEAD` — `checkout: moving from X to Y` — with the session's own branch, in the background, `createSessionBranches`); lastSeen is rewritten only when it moved 10 min (`LAST_SEEN_STEP_MS`), at most 30 kept per repo. **Facts** per branch (`core/stacks/branch-facts.ts`: exists, its tip, `origin/<name>` there, commits its base — origin/HEAD — lacks, commits origin lacks, merged = pushed with none of its own) are read in the background beside behind-main (`BranchFactsCache`: 5-min TTL, two sessions at a time, a broadcast on change; never on /api/sessions' path); what they find is kept (`noteBranchFacts`: `gone` from when it was first seen deleted, `merged`, `pushed` once). A merged branch deleted `GONE_SHOWN_MS` (3 days) ago drops out of what's shown (`branchHidden`), kept in the record. `SessionWire.branches` (`branchesWire`: the checked-out ones first, then newest; each with its facts and its PR from the PR watch's last check) only when a repo has been on more than one; the header's **N branches ▾** chip (`BranchesChip`, `branchesChip`: amber while one holds work not pushed; its list is `BranchesLine`, `state/branches.ts`: commits, not pushed, the PR pill — a click shows that branch in the Diff tab — and the way to the **Branches** tab, `BranchesTab`, `#/s/<id>/branches`, key 5, there only with more than one branch: per repo each branch with what's known of it, the turns taken on it and when, its commits folded, Show in Diff — `branchTabRows`; reported: three header lines before the tabs), `work sessions --json` and `work status` (`sessionBranchesNow`: looked at with git there and then), and the Ctrl+K description (`branchesText`, `core/sessions/branch-view.ts`). `prsForSession` matches the dashboard's PR list on any recorded branch. **A session's repos.** A session owns its repo list: `WorktreeSession.repos` (aliases, one per `paths` entry, same order), recorded when it is made and by Add a repo. Everything that acts on an existing session — teardown, archive, Restore, fork, clean-up, branch tidy, move, the dev server, checkpoint clean-up, stack retarget, the Repos page's live counts — reads it through `sessionRepos` / `sessionAliases` (`core/sessions/session-repos.ts`), never the group's config, so a session can hold a repo its group doesn't name and keep one its group lost. A row from before (no `repos`) is read as it always was: a group's from config `groups[target]` matched by folder name (else the folder's own name, `guessed`), a single repo's by its target — and it stays such a row: re-entering or restoring it writes no list (it goes on following its group's config, a repo the group gets later set up as before); only Add a repo records one, and refuses a row with a `guessed` folder. A list that is there but doesn't line up with the paths (a damaged row) is matched by folder name, never replaced by the group's config. A recorded repo no longer in the config isn't set up, is said, and stays on the row with its folder (teardown leaves it, `false`); a fork of such a session is refused. § A writer never drops a repo added meanwhile: `upsertSession*` apply the caller's folders over the row as it is in their transaction (`setOwnRepos`: recorded pairs the caller didn't know of stay; `upsertSessionWithPort` too, re-entry's writer), and `work resume` / `work recent` only mark the session used (`touchSession`), never writing back a list read before their picker waited. A group is only the starting set of repos. A **folder session** is `isGroup` (a group's, or a new session made with `sessionFolders`, recorded as `isGroup` with `repos: [alias]`): Claude runs in the folder (`dirname(paths[0])`), every group code path applies. The wire carries both (`SessionWire.repos` via `wireRepos` — config read only for a group's row from before, cached by the file's stat —, `SessionWire.folder`; both absent from an older server): the session header shows a folder's repos ("backend · frontend · docs", `headerRepos`, `state/add-repo.ts`) and `prsForSession` matches the session's own repos when the row has them (else the configured group members, as before).

**Add a repo** (⋯ → Add a repo…, `⇧A`, also the rail's right-click menu — a folder session not archived, `canAddRepo`; `AddRepoDialog`: your enrolled repos from `/api/projects` not in it yet, `addableRepos`, an optional base; `work add-repo`): `addRepoToSession` (`core/worktree/add-repo.ts`) checks the repo out into the session folder on the session's branch (the branch the repo has, else a new one from the base, else from the repo's own checkout's branch, as `work tree` makes one), records it (`appendSessionRepo`: `paths`, `repos`, `baseBranches`, in one `tx()`), rewrites the folder's instructions block (`writeSessionInstructions`, one import per repo in the agent's own syntax — `AgentAdapter.instructionsImport`, Claude's `@<repo>/CLAUDE.md`; an agent without one keeps its file as it is) and carries the Diff tab's turn history over (`migrateScope`, `core/diff/scope-migrate.ts`: the checkpoint manifest, `refs/wd/<old>/*` in every old repo and the `scope-<old>` comment store move to the new paths' hash; an old turn reads the new repo as its HEAD). § The move loses nothing: under both manifests' locks, refs are copied in one `git update-ref --stdin` transaction per repo (undone everywhere if one fails), the manifest written, and only then the old refs and manifest deleted; turns the new scope took meanwhile give way to the old ones (a checkpoint is a whole snapshot); an unreadable manifest or a comment id clash is left as it is, and said (`problems`). A checkout that can't be recorded is removed again, branch and all. What went wrong once the repo was in (the checkout's own warnings, the turns, the instructions file, telling its Claude) is `AddRepoResult.warnings` / `AddRepoWire.warnings`, shown in the toast; the add stands. An add records how the folder's file is made (`instructions`: `summary+imports` for a group's copied summary with the block after it, else `imports`), so a Restore — whose worktree went with its file — makes it the same way. Refused, changing nothing (`addRepoRefusal`, `core/worktree/add-repo-rules.ts`: pure, shared with the route, the CLI and the demo): an unknown session (404), an invalid alias or base (400, one starting with `-` too), an unknown alias (400), an archived session, a single repo's worktree in the old layout, a row from before with a folder no repo of its group has, a repo already in it, a folder of that name already in the session folder (409). `POST /api/sessions/:id/repos` (`session-repo-routes.ts`, `AddRepoWire`) answers the quick refusals itself, lets go of the old scope's watch before the add and again after it (a status hook meanwhile may have opened it under the old paths), runs git in a child (`addRepoInChild`, `core/worktree/add-repo-child.ts`, over `runWorkChild` like `createInChild`: `work add-repo … --session-id= --in-process --json`, its refusals with their status; one add per session at a time, and in the same queue as creations keyed by the repo's alias, `keyedQueue`; killed after 5 min with `git worktree prune`, the answer naming what it left), broadcasts `sessions-changed`, and tells the session's Claude by a published note (`addedRepoNote`, through `noteThroughComments`, `server/session-note.ts`) — nothing restarts: it already sees the folder. `work tree --here` from a folder session's checkout (an added repo too) resolves to that session (`folderSessionAt`, `resolve.ts`). The demo has the same route (`scenario.addRepo`).

Everything per-session beyond history is a row keyed by that id — `session_status`, `comments` (store = id), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs` — plus the dev log file; `removeSession` (and `work status --prune`) purge it all via `purgeSessionState` (`core/sessions/session-store.ts`) → `purgeSessionRows` (`core/platform/db.ts`), so a re-created session never inherits old state.

§ WHEN adding per-session state, add its table to `purgeSessionRows` (`core/platform/db.ts`), or its file to `sessionStatePaths` (`core/sessions/session-store.ts`). Its diff scope's checkpoints are keyed by the hash of its paths, not its id: `removeSession` clears them (`clearSessionCheckpoints`, from the base checkouts — the worktree may be gone), archive and the dashboard's delete drop the scope's watch (`releaseSessionScope`), and a scope keeps at most `MAX_CHECKPOINTS` (200; the oldest after Initial go, refs too).

**Finding work web.** `core/platform/web-discovery.ts` owns `web.url` / `web.pid`. The files outlive the process and PIDs get reused, so `work web --stop` kills only after `/api/context` answers with the recorded pid (`probeWeb`); `webServerResponds` is liveness only. The PTY host has the same rule (`/health` + token + pid). `/api/context` also carries `build` (`core/platform/build-stamp.ts`: the entry file's mtime): a full `work web` replaces a running server whose build differs from its own, or that predates stamps, since a server that outlived a rebuild reads state and serves routes as they were then (a September dashboard showed no sessions after the SQLite move and 404'd on new routes). `wd` and `--lean` never replace. § Two can still start at once (a restart racing the desktop app's watchdog, which starts one when none answers): every 20 s a work web runs `discoveryCheck` — the one web.pid doesn't name, when the named one answers as itself, stops (leaving the hooks, which are removed by owner and are the other's too, and the discovery files); with nothing live recorded it writes itself back. A duplicate once kept an old build in the desktop app for hours and doubled the GitHub API use. **How it ended** (`core/platform/web-life.ts`): a work web writes `~/.work/web-life.json` (pid, version, start, a 20 s beat) and, on every way out it sees (a signal, `--stop`, a duplicate retiring, `exit`), how it ended. The next start finds one that vanished without saying (`previousEnd`: killed, a crash below Node, the machine) and logs it with its last beat; the desktop app logs each child's exit status (`spawn_collected_as`, `desktop.log`).

### Diff Review (`wd`)

Second binary (`dist/wd-bin.js`, shim `wd`) that surfaces a GitHub-PR-style diff in the browser. Two modes, both rendering the same React SPA at `dist/web/`. The SPA reads `/api/context` (or `window.__WD_BOOT__` in static mode) to decide which screen and whether the comment UI is enabled.

**One server, many routes.** `wd` always routes through the singleton `work web`: it reads `~/.work/web.url`, POSTs `/api/scopes`, and opens `<webUrl>/diff/<hash>` (or `/review/<hash>` for `wd -c`). When no work web is running, `wd` auto-spawns one in the background — detached `node <bin> web --lean --no-open` — and waits for `~/.work/web.url` to appear before registering. Lean mode (`startWebServer({lean: true})` in `server/web-server.ts`) skips the dashboard-only `~/.claude/projects` activity watcher + the 10 s session-decay tick, and `commands/web.ts` skips installing Claude `UserPromptSubmit`/`Stop` hooks (no `~/.claude/settings.json` mutation). Net result: a `wd` invocation in a fresh shell costs ~one `work web --lean` startup; subsequent `wd` calls across worktrees register on that same server with no extra processes or ports.

- **Live server (`wd`, default):** `runLauncher` calls `ensureWorkWebRunning` (reads `web.url`, autostarts lean work web on a 5 s wait if absent), POSTs the scope, opens `/diff/<hash>`. There is no per-scope daemon class anymore — the previous `runDaemon` / `spawnDaemon` / per-scope `.pid|.url|.log` files are gone. Live updates via chokidar + SSE are **staged, never auto-applied**: on `diff-changed` the SPA re-fetches in the background (`checkForUpdates` in `hooks/use-deferred-diff-load.ts`) and, only if the payload actually differs, parks it in `pending` and shows a `DiffUpdateChip` ("New changes · N files" + Show / Only new / Reload — Show applies the staged payload keeping scroll; Only new narrows to a checkpoint range from the newest checkpoint taken before the on-screen diff was fetched (the session Diff tab too: `onlyNew`, `state/diff-history.ts`, a pick from that turn to the working tree); Reload is a soft foreground refetch + scroll-to-top, never `location.reload()`) **in the header**. Likewise no in-flight dim or progress bar: the only busy cue is `DiffBusyChip` in the header — the diff itself never moves under a reader mid-scroll, and nothing above it is inserted (a banner would shift every line). § WHEN adding another live-refresh path, stage it the same way; do not write straight into `data`. `wd --stop` de-registers the scope (DELETE `/api/scopes/:hash`); the server itself keeps running.
- **Static (`wd --static`):** `renderStatic()` in `core/diff/static-renderer.ts` reads the SPA shell, inlines its CSS/JS, and injects the diff data as `<script>window.__WD_BOOT__=...;</script>`. Writes to `~/.work/diffs/<hash>.html`, opens via `file://`, exits. Self-contained — survives the CLI, no server. The boot JSON goes through `escapeForScriptTag` (handles `</script`, `<!--`, U+2028/U+2029, raw control chars). The boot-script injection uses a function-callback replacement so JSON values containing `$'` (a real shell-regex hazard) don't trigger `String.replace`'s `$`-magic.
- **Review (`wd -c`):** `tryReviewViaWorkWeb` in `commands/diff.ts` registers a scope on (auto-spawning if needed) work web, opens `/review/<hash>`, then polls `/api/scopes/<hash>/comments` once per second. `core/comments/review-poll.ts::diffReviewSnapshot` is the pure helper that diffs the previous-tick `seen` set against the current snapshot. Exits cleanly when the snapshot returns `ended: true`; the scope and browser tab keep working after the CLI exits. If work web autostart fails entirely (port refused, dist/web missing), `wd -c` falls through to a foreground `startCommentServer` (`server/comment-server.ts`) — a per-invocation Hono sub-app that blocks until "End Review", same shape as before.

**Scope resolution** (`resolveScope` in `core/diff/diff-scope.ts`): walks the cwd against the session history. Inside a single-repo worktree → that repo. Inside any sub-repo of a group worktree → the whole group, with that sub-repo as the initially-active tab. At a group root → all repos, no active tab preselected. Outside any work-managed worktree → falls back to `git rev-parse --show-toplevel` (single repo).

**Renderer:** the React SPA in `src/web/`, built by Vite to `dist/web/`. `ReviewApp.tsx` lays out the sidebar (file tree + comments panel), general-comment pane, and `DiffRepo` (per-file `<article>` with side-by-side `<table>`). When `context.readOnly` is set, composer/draft/submit UI and `ReviewProvider` are suppressed (no `fetch('/api/comments')` over `file://`); the diff and file tree still render. Syntax highlighting is npm-bundled `highlight.js` applied per-cell via `dangerouslySetInnerHTML` during render — not post-paint mutation. Intra-line word diff via `diff` package. Viewed-checkbox state persists per-scope in localStorage.

**Status output convention:** stdout carries data only (the comments markdown payload in review mode). All status messages go to stderr via the `info()` helper in `commands/diff.ts`. `console.error` is reserved for real errors.

**Claude integration:** two paths route review comments to a live Claude in the matching worktree without the user typing —
- **`work web` command hooks** in `~/.claude/settings.json` (installed by `work web` on startup, removed on shutdown via `core/platform/command-hook-installer.ts` + the shared atomic-write `core/platform/settings-editor.ts`). The `UserPromptSubmit` hook prepends pending comments to the next user turn; the `Stop` hook returns `{decision:'block', reason:<comments>}` so Claude addresses them automatically when it finishes any turn. Delivered state is state.db `comment_deliveries` (see `core/comments/pending-delivery.ts`). § Two processes deliver (the hook process and the PTY push), so delivery is a **claim**: `claimForDelivery` inserts the ids with `INSERT OR IGNORE` in one transaction, and only the rows it inserted are its to send. Send only what you claimed; `releaseClaim` if the send fails. Never read pending and mark delivered as two separate steps. **Resolved when addressed**: at a turn's real end (a Stop that hands nothing new on), every top-level comment of yours Claude was given — your review comments and work's own notes (PR feedback, CI, prompts) — is marked resolved (`resolveAddressed`, `pending-delivery.ts`, from `runTurnHook`); the Diff tab's badge (`commentCount`) counts only open threads. Resolved ones stay listed, dimmed, and can be reopened.
- **Owned-PTY push** in `server/routes/session-comment-routes.ts`: when a comment is posted and `work web`'s pool already owns a PTY for that session (the user opened the Terminal tab), the route handler writes the formatted reminder directly to stdin. Idle Claudes in our own PTY get the comment without any hook round-trip.
- For external Claudes that are fully idle, neither path fires — the dashboard shows a purple `→N` "waiting for Claude" badge until the user does anything in that terminal.

**One worktree, two stores, one list** (`core/comments/linked-stores.ts`): the Diff tab posts to the session's store, the browser diff page (`/diff/<hash>`) to its scope's (`scope-<hash>`). Each view lists its own and the other's (`GET /api/sessions/:id/comments`; `GET /api/scopes/:hash/comments?linked=1` — without it the scope's alone, which `wd -c` polls and prints), the other's drafts left out. A resolve, delete or reply acts on the store that holds the comment (`storeHolding`; a reply there is published), and both views are told (`announceChange`, one fan-out for both routes; session routes reach scope streams through `notifyScope`); a reply that lands in the session's store is typed into its idle Claude from either view (`ownedPtyDelivery` counts what the hooks hand over, `readPendingForWorktree`). The badge and the waiting-for-Claude count cover both. A view reads its stores in one query (`readStoresComments`, cached nowhere: `/api/sessions` asks per row). The stores are never merged: a new `wd -c` run clears its scope's.

The legacy `wd-review` skill at `plugins/work-tree/skills/wd-review/SKILL.md` (shipped via the `work-tree` Claude Code plugin marketplace — see `.claude-plugin/marketplace.json`; registered automatically by `scripts/postinstall.mjs` on npm install) is still used for the `wd -c` foreground flow (stdout marker stream + curl replies via `~/.work/diffs/latest-review.url`). Replies must use `--data-binary "@file"` not inline `-d '...'` to survive apostrophes in the body. In the normal work-web flow, reply to `POST /api/scopes/<hash>/comments` (hash from the `/review/<hash>` URL), NOT `/api/comments`.

### Checkpoint trigger + reload-loop guard

Checkpoints run their git off the event loop (`runGitAsync`; only `clearCheckpoints` stays synchronous): a turn's checkpoint once held up every request — terminals and status hooks — while git ran. `mountScopeRoutes` tracks the work it starts without waiting (`settled()`, for tests). Checkpoints are **authoritatively taken per Claude turn**: `work web` installs a `Stop` hook — the lean `wd` server `work hook checkpoint` (owner `web-checkpoint`, `LEAN_HOOKS`), the full dashboard the same inside `work hook turn-end` which POSTs the cwd to `POST /api/checkpoint`; `scope-routes` maps cwd→scope (`scopesForCwd`) and snapshots (dedup-by-tree makes a no-change turn a no-op). The fs-watch auto-snapshot is now a **fallback that suppresses itself while a Claude session is active** (`activeWithin`, `agentWriteMs`, `agents/claude/activity.ts`) so it can never fire mid-turn before the hook — it only checkpoints manual edits when no Claude is around.

§ WHEN touching the scope diff server, preserve `suppressScopeWatch` (`core/diff/scope-manager.ts`): the `to=working` range diff runs `git add -A`/`write-tree`, whose `.git` churn surfaces as nameless `fs.watch` events that can't be path-filtered. The diff route calls `suppressScopeWatch(hash, 800)` after computing so that self-induced churn doesn't fire `diff-changed` → refetch → recompute → **reload loop**. Real edits land outside the window and still reload. Checkpoint names come from `core/diff/checkpoint-summary.ts` (lazy, cached; written by the summarising agent's one-shot run, `runInternal`, with its small model; one internal run at a time in its lane across work web, a timed-out run killed with its tree). Every internal run (`internalClaudeSpawn`) is text-only and starts none of the user's MCP servers (`--strict-mcp-config`). Comment `resolved` (mark-done) and `side:'file'` (whole-file) are routed via `/api/scopes/<hash>/comments/:cid/resolve` and the normal POST with `side:'file'`.

### The Diff tab: commits and turns (`DiffView`)

The standalone review page's shape: one toolbar over the file tree and the diff (`wd-dash-difftoolbar`) — the scope tabs (Uncommitted | Since branch) and **Changes: … ▾** (`HistoryPicker`) on the left, what's shown (files, +/−, "vs origin/main", the update chip) in the middle, Split/Unified on the right; the sidebar keeps only the tree and the comments (folded to one line while there are none). A group's repos are a switch at the toolbar's start, always there and in the session's order with each one's file count (`repoSwitch`, `state/diff-view.ts`; none above the diff): a commit's pick is that repo's alone, so moving to another repo from it shows that one's Since branch rather than leaving you in the commit's repo. The picker lists the session's history, newest first: the branch's commits since its base (`sessionCommits`, `core/diff/session-history.ts`, served with the turns by `GET /api/sessions/:id/checkpoints` as `commits`; a group lists the repo tab's), Claude's turns, and what is uncommitted (`historyItems`, `state/diff-history.ts`, pure). A click shows that one alone, Shift+click the span from the last click to it, across commits and turns; its shortcuts are Uncommitted, Everything on the branch, Last turn and Since you looked. It is there in either scope, always. A pick is a diff between two points (`core/diff/diff-points.ts`, pure: `cp:<id>`, `c:<repo>:<sha>`, `p:<repo>:<sha>` — the commit's parent —, `head`, `working`; anything else is refused, never handed to git): `GET /api/sessions/:id/diff?from=&to=` (`computeSessionRange` → `rangeRefs`: a commit's range is its repo's alone; a checkpoint or the working tree covers every repo). Loading keeps the diff on screen (dimmed a little after a moment, `wd-diff-stale-soft`) with a thin bar under the toolbar (`wd-diff-progress`), no text; a group opens on the first repo with changes (`preferredRepo`, `state/diff-view.ts`), the empty ones dimmed and last. The standalone page (`ReviewApp`) keeps its checkpoint range picker (`CheckpointStrip`). Both have the arrows between hunks (`ExpandProvider`, `GapRegion`): the Diff tab reads the lines through the session's scope (the hash its diff-page POST gives) at the version the newer side is (`linesRef`, `state/diff-history.ts`: the working tree, `HEAD`, a commit, a turn's snapshot — `GET /api/scopes/:hash/file-lines?ref=`). The toolbar's right end has **Open in browser ↗** — the session's diff on the page `wd` opens (`/diff/<hash>`), in your browser (a `target=_blank` link; the desktop app sends new windows there): the tab asks `POST /api/sessions/:id/diff-page` (`diff-page-routes.ts`) when it opens, which sets the session's scope up (gone after a restart until a hook ran) and answers the address, so the link is plain by the time it's clicked — and **Full screen** (`SessionDetail` `diffFull`: the diff over the top bar, rail, header and tabs; Esc or the button leaves — not an Esc a picker used or a menu or dialog takes; leaving the tab or the session ends it).

§ The session's scope is created by the status hook (a POST); `GET …/checkpoints` reads the manifest from disk by `scopeHashForPaths` and creates nothing (GETs have no side effects, §1.5). Dashboard paths get a session's scope through `sessionScope` (lookup-or-create, `findScope`), never `ensureScope`: ensureScope is what a NEW `wd -c` run does — revive an ended review, clear its comments, relabel — and running that on every Claude hook wiped finished reviews.

A session's turns are its diff scope's checkpoints (one per instruction, taken by the Stop hook — the same scope `wd` registers for those paths), kept across the session's own commits (`sessionOwnsScope`, `rebaselineIfHeadAdvanced`; a session where Claude committed each step was once left with only "Initial"), but re-baselined when HEAD brought in other work since the newest turn on the same branch — a rebase, a merge, commits already on `origin/HEAD` (`headBroughtInOtherWork`) — or the next turn would show it as Claude's; another branch checked out since the newest turn (`switchedBranch`: the turn recorded its branch; branch to branch only — a detached HEAD on either side isn't a switch, and mid-rebase the branch being rebased is the one on (`workingBranch`, `git-head.ts`: `rebase-merge/head-name`), so a rebase onto main that stops on a conflict across a turn end still re-baselines) keeps the history — the next turn is marked as the switch (reported: a session that worked on three branches started over at "Initial" on each switch, losing its turns, Since you looked and its looks); a scope no session owns (`wd`) re-baselines at every commit, as before. **Every branch the session worked on** (session-branches.ts; reported: a branch's work vanished from the Diff once it merged): `GET …/checkpoints` (`sessionHistory`, over `historyBranchRefs`: every recorded branch of each repo but the one it is on (`workingBranch`; detached otherwise, the one it was on last), merged and deleted ones too, at most `MAX_HISTORY_BRANCHES` per repo; async git — finding the base too, `resolveRepoDiffAsync`: the parent lookup is one generator of git steps, run synchronously for the CLI and diff routes or async here —, and while nothing moved no git at all: the answer is kept by each HEAD and branch tip read from the repo's files, `refShaFromFiles`; the route is `sessionHistoryWire`, `core/diff/session-history-wire.ts`) lists each other branch's own work in `commits` (`SessionCommit.branch`): from where its own work begins (`startFromReflog`, `branchStart`: the newest point its own reflog says it was put onto from outside — made, fast-forwarded, reset, or the `onto` of a rebase; a merge of its base into it isn't one, nor a move within its own work — a reset or rebase onto a commit it was itself at since its start (a squash, `reset --soft HEAD~1`), a fast-forward from its own copy (`merge origin/<name>`, `pull --quiet origin <name>` — options aren't refs —, or a pull naming no ref whose upstream is its own name, `branchUpstream`: `branch.<name>.merge` read from the config file); a pull that rebased (`pull --quiet (finish): … onto <sha>`, pull.rebase set) moves it like a rebase; read live while the branch is there, and kept as `RecordedBranch.start` at each turn's end (read only when its reflog was written since the record last saw it, `branchLogChangedSince`: a stat) and by the backfill for once it is deleted; reported: a branch fast-forwarded and rebased onto dev before its first commit listed dev's merges as its work) to its tip along its own line (`--first-parent`), merged or not — its tip the branch, or once deleted the tip the branch facts kept while it was there (`RecordedBranch.tip`, `noteBranchFacts`), while the repo still has it; with no start known, its commits that neither HEAD, origin/HEAD nor what it was made from has, as before. `branchSpans` gives each one's whole change (`SessionBranchSpan`: from the last base it took in — the newest first-parent merge whose other parent holds none of its own line (`lastBaseTakenIn`: a `pull --no-ff` of its own copy, or of a branch made from it, isn't a base) — else its start (no start known: the parent of the oldest of ALL its own commits, not only the 50 listed), to its tip; a branch with no commits of its own too, base = tip, so the turns taken on it are diffed from the commit it was at). The picker shows this branch's history, then a section per other branch with its commits and the turns taken on it (`turnBranchFor`, `branchAt`: a turn whose recorded branch for the repo on screen isn't the checked-out one; the same rule for every list, so a pick means the same in each), what's known of it ("merged", "1 commit · not pushed", "no commits") and **All of it** (`branchSelection` with the span: `c:<repo>:<base>` → its last item, a turn taken on it after its newest commit included; no span — an older server — from its first item, a first turn that was the switch left out); the toolbar's **Branch** select (`BranchSwitch`, when the repo on screen has another branch) switches between the checked-out branch (Since branch) and each other one's whole change (`shownBranchOf` says which is on screen). A click diffs one commit or turn, a span never crosses branches (`span`), "Everything on the branch" stays the checked-out one's, and the header's branches chip and the Branches tab open a branch's whole change (`DiffView`'s `showBranch`). Each checkpoint records each repo's checked-out branch (`CheckpointEntry.branches`, `branchesOf`: HEAD files), and a turn whose branch differs from the one before it is marked "branch switched: fix/a → fix/b" (`branchSwitch`, `HistoryItem.switched`; in a group every repo that switched, named, the repo on screen first — "web: feat/x → feat/x-ui · api: feat/x → fix/y": a turn's diff covers every repo): its big −N is the switch, not a revert. Another branch's commit has its own key (`c:<sha>@<branch>`): a branch made from another has that one's commits in its own history too. `tests/core/diff/multi-branch-session.test.ts` runs all of it on one hard session built with real git (`tests/functional/fixtures/multi-branch-session.ts`: two repos, six branches, six turns, a branch merged and deleted, one with only an uncommitted turn), and the same fixture can be put under a scratch HOME to look at in a browser. Turns are named by checkpoint id, and one whose predecessor was dropped past `MAX_CHECKPOINTS` isn't listed alone; **Last turn** (the newest alone: the highest checkpoint id, never an older turn of another branch listed after this branch's) is a shortcut in the picker, and the Diff opens on it when asked to (the review queue).

**Since you looked.** You review by looking and then telling Claude in the terminal, not always by submitting a review, so the point to diff from is set by looking: when a session's Diff tab has been on screen, in a visible and focused window, for five seconds (`useLookedFor`, `hooks/use-looked.ts`), the newest checkpoint then is recorded (`POST /api/sessions/:id/diff-seen`, `markDiffSeen`, `core/diff/diff-seen.ts`: state.db `diff_seen`, schema v8, forward only, purged with the session). The next visit reads the mark first and keeps it for the visit; when Claude finished a turn after it (`sinceLooked`, `state/diff-history.ts`), the picker's **Since you looked** shows the range from it to the working tree (`?from=cp:<mark>&to=working`, every turn and commit after it marked) and the Diff opens on it (unless asked to open on the last turn). **Your looks**: each time the mark moves forward, the move is kept in the same record (`DiffSeen.looks`, `nextSeen`, `core/diff/diff-looks.ts`, pure, shared with the demo; no schema change): from the turn it was at to the one it moved to — what Since you looked showed — as pointers to checkpoints, never snapshots of their own (checkpoints are Claude's turns everywhere else: the picker's list, the digest, the timeline). Moves within 15 min of each other are one sitting (the look grows); 20 kept; the first look of a session records none. The mark and each look keep their turns' own times (`DiffSeen.ts`, `DiffLook.fromTs`/`toTs`): a re-baselined scope counts turns from 1 again, so a reused number is told from the turn you saw — the mark starts over, a look or Since you looked whose turn is now another is left out. The page also says what its list has for the mark's turn (`marked`: its time, or none), so a new numbering already past the mark is caught too; stored rows are shape-checked (`cleanSeen`). The picker shows **Last look** with its shortcuts and a **Your looks** section above the history (five, then Show all; `yourLooks`: one whose turns were dropped past `MAX_CHECKPOINTS` is left out), so a diff you reviewed can be seen again after you leave. Viewed ticks are stored with the file's change (`fileSignature`: +/− counts and a hash of its hunks; key `path#signature`, `viewedFrom`), so a file Claude changes again is unticked; a bare `path` tick from before stays. A right-click on a folder or file in the tree (both diff pages) marks every file under it viewed or not viewed (`viewedMenuItems`, `state/tree-viewed.ts`: only what would change something; `useViewedFiles().setMany`). Status hooks also ensure the scope, so turns are recorded for sessions nobody has opened yet. The demo fakes three checkpoints per session with changes.

### Revert + batched review

`POST /api/sessions/:id/revert` (`server/routes/revert-routes.ts` → `core/diff/revert.ts`) undoes an **uncommitted** file or hunk. The server re-computes the session's Uncommitted diff to find the change and its repo root (never trusts a root/patch from the browser). Hunk revert asks git for the raw, byte-exact diff of that file (the pipeline's `-w` diff can't be reverse-applied, and the parser drops CRs) and `git apply -R`s the raw hunks overlapping the picked new-side lines after a `--check`. Then it posts a published general comment ("I reverted … don't reintroduce it"), so delivery reuses the comment path. The SPA offers Revert per file ("Revert file" on its header), only in the Uncommitted scope (`RevertContext`); a hunk has no Revert or reviewed checkbox of its own, as on GitHub (the route still takes a line range). `submit-review` pushes the whole review to an owned PTY as one message, like a single POSTed comment does.

**Stacked sessions** (`core/stacks/stack.ts`, pure; `stack-sessions.ts`, `stack-sync.ts`): a session made from another live session's branch, by a fork or `work tree … --base feat/x`, is stacked on it. Nothing new is stored: the parent is found from the recorded `baseBranch` / `baseBranches`, in the same project and on that branch. A group counts only when every repo shares the base. Mainline names, `origin/…` refs, archived sessions and a repo's own checkout are never parents. `SessionWire.stackedOn` / `stackedChildren` drive the session strip's `StackChip` ("⤷ on feat/x · 2 stacked on this", which opens the parent) and the rail tooltip. Behind and Update from (`behind-main.ts`) measure a stacked session against the parent's **local** branch (`refs/heads/<parent>`, nothing fetched; `Behind.stacked`), and it is shown from one commit behind. After a turn ends (`onStatusChanged` → idle), the stacked sessions involved (the children of the one that finished, or itself when stacked) are checked. A child is brought up to date (`syncStackChild`: rebase if never pushed, else merge) only when its Claude is neither working nor waiting, nothing is uncommitted in any repo, and merge-tree says it merges cleanly. The status is asked again right before each repo is changed, since a turn may have started while git looked. A group is all or nothing: if a later repo fails, the ones already updated are reset to the commits recorded first (they were clean). Sessions made from each other's branches form a cycle, and none of them gets a parent. The orchestration is `syncStacksAfterTurn`, tested in core, which web-server only wires. Its Claude is told by a published note, since files may have changed under it; a note that fails to post shows as a warning in Activity. Anything else is left alone with the reason in the Activity panel (`stacks`), and the chip offers it. Config `stacks.autoUpdate: false` turns that off. An archived parent that never merged doesn't count, since moving onto main would drop its work from the child. The child then shows "⤷ was on feat/x — merged" with **Move onto main** (`POST /api/sessions/:id/retarget`). That runs `git rebase --onto origin/<main> <fork point>`, replaying only the child's own commits: main has the parent's in another form after a squash merge, so a plain rebase would replay them. The fork point (`forkPoint`) is not simply the merge-base with the parent's tip, because a parent rebased or amended before it merged shares only an older commit with the child, and replaying from there would bring its old commits back. If the parent's tip is in main (a real merge), it's a plain `git rebase <main>`. Otherwise it's git's `--fork-point` (the parent branch's reflog, which survives a rewrite), or the tip if the child is built on it (`parentTipFor`: the branch, or the tip its archive recorded). If neither works, it refuses and says so (ask its Claude). Before each repo is changed, the status is asked again (`stillOk`), for the button and for Update from main too. Repos with different mainlines keep per-repo bases (`setSessionBase`). The automatic move needs git 2.40 (`merge-tree --merge-base`); on older git it never runs, and the button still works. The demo shows one (`feat/tax-report` on the merged `feat/tax-rates`). A pushed child isn't rewritten: main is merged in. It's all or nothing across a group, refused while its Claude works or with uncommitted changes, and a conflict is aborted. Afterwards its base is main (`setSessionBase`), so it is no longer stacked. It happens by itself after the child's own turn (`retargetIfMerged`, in `syncStacksAfterTurn`) and when the parent is archived (`onArchived`, a listener in `session-archive.ts` that every archive path calls, then `retargetChildrenOf`), when `merge-tree --merge-base` says it goes cleanly, and its Claude is told. If the parent was rewritten and git can't find the fork point (`handOff`), the child's Claude is asked to do it (`ontoMainPrompt`, once per parent tip), and the button's result offers Ask Claude.

**Time per session** (`core/conversations/work-time.ts`, pure; `work-time-source.ts`; `GET /api/sessions/:id/time`): how long a session's Claude worked, from its transcripts, approximately. The time between two lines counts when the later one is Claude's (its message, or a tool result coming back), at most `STEP_CAP_MS` (15 min) each, so your reading and typing don't count, and neither does a permission prompt left for hours. The source reads each transcript once, then only the bytes appended since, a megabyte at a time with a pause between. ### Usage (plan limits and tokens)

The top bar's **Usage** meter (`UsageMeter`, left of the Activity dot) shows the window nearest its limit across every agent and account ("Claude wk 18%": `meterView`, `state/usage-view.ts`; amber from 70%, red from 90%; only the percent below 900 px; "Usage" with no reading; the tooltip has the reset and the age). The hook always exits 0 and runs the original from that file itself, so the right side runs only when `work` is gone (uninstalled, off PATH) — the user's line still shows. A wrap over a line that is ours re-writes its fallback from the saved original; a line the user set since (`/statusline`) isn't ours, so it is saved fresh with a new fallback. The hook's half — what runs on each refresh: `readSaved`, `originalStatusLine`, `shellFor`, `runStatusLineCommand`, `isOurs` — is `claude/statusline-run.ts`, and the hook itself `claude/statusline-hook.ts` (with `claude/rate-limits.ts`: `parseClaudeRateLimits` and `accountOf`, Claude's account from `CLAUDE_CONFIG_DIR`; `core/usage/` stays agent-neutral). A command that already runs work's hook (`… hook statusline` under any path, with or without its `||` fallback) is taken as ours and never saved as the original — it would run itself; the user's command runs with `WORK_STATUSLINE_NESTED=1`, and the hook run with it records but runs nothing more. **The wrapper stays when work web stops** (a plain CLI call; a missing work web changes nothing about it). To give it back: config `usage.statusLine: false` (applied at the next work web start), or `work usage --restore` now (each adapter's `usage.restore?()`). Settings that an edit leaves as they were aren't written (`applyEdit`: no rewrite, no backup — the file is often synced or in a dotfiles repo). Unwrapping puts the saved original back only when `statusline.json` reads (`readSaved`: an original, or an explicit none); missing or damaged, work's line stays and a warning names the file — dropping it would lose the user's. The saved file is deleted only after the settings were written and a re-read shows the status line is no longer work's. **A session's PR list** (`core/pr/session-prs.ts`; reported: a branch made, pushed and left within one turn was never recorded, so its PR never showed — nor one Claude opened on the docs repo — and a failing PR on a branch not checked out was never fixed): every PR a session made or worked on, kept in state.db `session_prs` (schema v13, purged with the session; `{prs: [{url, number, repoId, branch?, sources, firstSeen, final?}], scanned?}`, `cleanSessionPrs`). Sources: the agent's conversation (`AgentConversation.prLinks`: Claude Code writes a `pr-link` line for each PR its session makes or looks at, `agents/claude/pr-links.ts`), read from the new lines the conversation copy appends (`syncConversation`, a line split across its 4 MB chunks carried over) and once over the whole kept copy for a session from before (`scanned`); and every PR the watch finds on a branch (`withListedPrs` → `sightings`). The watch's preflight (`watchPreflight`, `pr-watch-hosts.ts`, what ci-routes wires) looks each listed PR its branches didn't find up by its link (`GitHost.prForRef`: `gh pr view <url>`; Azure DevOps `az repos pr show --id` on the link's org, refused when #N is another repo's) — in its repo (`RepoShipState.listedPrs`, read as `otherPrs` by `otherPrsOf`) or, when the session doesn't have the repo, `ShipPreflight.elsewhere` / `SessionCi.elsewhere` (the stage and the PR tab read it as a repo of its own, `stageInputOf`; labelled "another repo"). A merged or closed one keeps that last look (`final`) and is asked no more; a host that rests or fails keeps the watch's last look, else `unknownPrs` (holds the archive, never read as gone — a resting host with no last look too). **The watch acts on every open PR** (`prsOfPreflight` / `prsOfCheck`): failing CI, conflicts and review feedback for the checked-out branch's PR, the other branches' and listed ones, and those in other repos (no review read there: no folder to read it in); yours or theirs per PR (`prKey`: repo + link). A note about a PR on a branch not checked out names it ("PR #3657 on fix/culture (not checked out: fix/probe is)") and says how to get there (`placeOf`, `placeLines`: stash, `git switch`, push, switch back; another repo: its own checkout); the CI note also says a check failing outside the code (a 5xx, a dead runner) is run again, not fixed. The PR tab shows each PR's branch when its repo has two open (`branchShown`).

**Which failed checks count** (`core/pr/required-checks.ts`; a repo's list is set in its settings, Repos → Settings…): the host's own list wins — GitHub's required checks (`gh pr checks --required`, asked only when a check failed; `blockingChecks`, `pr-ops.ts`), Azure DevOps' blocking build policies (`checksOf`) — marked `ShipPr.checksRequiredByHost`. Where the host requires none, config `prWatch.requiredChecks` (repo alias or `owner/name` → check names, `cleanRequiredChecks`) names them (`countedChecks`, applied in Ship's preflight and to the listed PRs: `withRequiredChecks`); with neither, every check counts. A failed check that doesn't count is `ShipPr.optionalFailing`: not red, not in the Inbox, never asked of Claude, shown grey in the PR tab ("1 optional check failed: …", `OptionalFailing`).

### State storage (`~/.work/state.db`)

Session state is one SQLite database (WAL) shared by every `work` process: `core/platform/db.ts` is the only importer of `better-sqlite3` (architecture test) and exposes `withDb(fn)` and `tx(fn)` (BEGIN IMMEDIATE; nested calls become savepoints). Tables hold each record as JSON beside the columns it is looked up by: `sessions`, `session_status`, `comments` (store = session id or `scope-<hash>`), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs`, `pr_replies`, `session_snooze`, `rail_place`, `jira_watch`, `tasks`, `diff_seen`, `pr_watch_state`, `session_branches`, `session_prs`, `meta`. Triggers bump `meta rev:sessions` / `rev:tasks`; work web polls those once a second instead of watching files. Stored rows come back through `json.parse(): unknown` and a shape guard, never a cast.

First open (`PRAGMA user_version` 0) creates the schema and imports the pre-SQLite JSON files in the same transaction (`core/platform/db-import.ts`), then renames them `*.migrated`. `work state` summarizes the database; `work state --export <dir>` writes it back in the old JSON layout (rollback path, round-trip tested), plus `newer-state.json` for what has no file in that layout (PR reply drafts, the Jira watch, snoozes, the rail's order, pins and sections, notes, blocks, worklogs). Opening a new file races on the WAL switch across processes, which the busy timeout doesn't cover, so `open()` retries on SQLITE_BUSY.

§ WHEN reading-then-writing state, do it in one `tx()`. A transaction can't span an `await`, so async work (port probing in `upsertSessionWithPort`) goes optimistic: compute outside, re-check inside, retry.
§ Tests run with `WORK_DB_EPHEMERAL=1` (tests/setup): the connection closes after each outermost call so temp HOMEs can be deleted on Windows. A test that doesn't mock `os.homedir()` must not reach `db.ts` (it would write the developer's real state.db); inject a store instead, as the PTY registry does with `sessionsPath`.

### Moving to another computer (`work move`)

`core/move/move.ts`. **Export** (`exportBundle`) writes a folder you carry over (OneDrive, a stick): a `state.db` snapshot (`snapshotDb`: `VACUUM INTO`, consistent while others write), `config.json`, `conversations/`, `archive/`, the groups' `*.claude.md` (`instructions/`), every live session's agent transcripts (`transcripts/<session id>/`, through `conversation.files`), and `manifest.json` (old home, platform, worktrees root, each repo's path and origin — `originUrl`, which unescapes git's quoting). Before it, `unsavedWork` lists uncommitted files and commits not on origin per live session's repo, and the CLI refuses without `--force`, since the other computer gets worktrees from origin. **Import** (`importBundle`) refuses while work web or the PTY host runs (`runningHere`: they hold the database) and over existing sessions without `--force`; moves paths by `remapRules` / `remapPath` (pure: the worktrees root and each repo to `--worktrees-root` / `--repos-root` + its folder name, else the same place under the new home; anything else under the old home with it; longest prefix first, case-blind for a Windows bundle), writes config.json as raw JSON (unknown keys kept), puts the snapshot in place (`replaceDb`), moves each session's paths and per-repo bases (`remapSession`), empties the PTY restore list, copies work's folders, clones missing repos from their origin (`--clone`), recreates live sessions' worktrees (`createInProcess`, a repo's own checkout excepted), and puts transcripts back in each session's `conversation.restoreDir`, so `--continue` resumes them. Checkpoint refs and wd's review scopes (keyed by old paths) stay behind. § Never keep `~/.work` live in a synced folder: a synced SQLite file corrupts, and two computers would both run the PR and Jira watches.

### Configuration

Stored at `~/.work/config.json`. Schema in `core/platform/config.ts`:
- `worktreesRoot` — parent directory for all worktrees
- `repos` — map of alias → repo path
- `groups` — map of group name → array of repo aliases
- `scanRoots` — folders the Repos page scans for git repos (default: the folder holding `worktreesRoot`); `ignoredRepos` — repo folders it leaves out of New
- `copyFiles` — glob patterns for files to copy into new worktrees (e.g., local dev settings)
- `sessionFolders` — opt in (default off, experimental): every new session is a folder of repos, a single repo too (`<worktreesRoot>/<branch-dir>-<id6>/<repo-folder>/`, recorded as a folder session with `repos: [alias]`), so Add a repo works on it; its instructions file imports each repo's own (`core/worktree/session-instructions.ts`: a `<!-- work:repos -->` block, the rest of the file kept; a file that can't be read is never overwritten), and a group made with it on gets the same instead of the generated `~/.work/<group>.claude.md` — recorded on the session (`instructions: 'imports'`), so a Restore makes it the same way whatever the switch says then. Re-entry follows the session's row, not the switch: existing sessions keep their layout and their copied summary
- `reviews` — automatic PR reviews: `projects` (alias or group → `all` | `asked` | `off`), `maxPerDay`, `maxLines`, `rules` (see Reviews)
- `prWatch.requiredChecks` — per repo (by alias — a group session's folders matched to it — or the host's `owner/name`), the checks that count where the host requires none (see PR watch, Which failed checks count)
- `gitHosts` — an origin hostname → the git host it is, for an origin no adapter claims by its URL (see Git hosts; GitHub Enterprise needs no entry)
- `hostEnv` — environment variable names a restored PTY-host session keeps from the shell that started it (secret-looking names never)
- `useBundledConpty` — Windows: terminals start on node-pty's bundled ConPTY instead of Windows' own (see PTY host)
- `aiCommand` / `aiCommandFlags` — the agent new sessions run (Claude Code by default); `internalAgent` — the one that writes work's summaries; `assistantAgent` — the one the Ctrl+K assistant runs (both `claude` by default; see Agents)

### Build

tsup bundles two entry points: `src/bin.ts` → `dist/bin.js` (the `work` binary) and `src/wd-bin.ts` → `dist/wd-bin.js` (the `wd` shim that forwards argv to the `diff` subcommand). Both ship as ESM with shebangs. All npm dependencies are **external** (not bundled) — resolved from `node_modules` at runtime. This is important: adding a dependency requires both `npm install` and rebuild. The lockfile is `npm-shrinkwrap.json` (in `files`, so it is published): a global install gets the versions CI tested, not whatever the ranges resolve to that day. `package.json` declares both binaries under `"bin"` so `npm link` registers `work` and `wd` globally.

### Startup and load costs (keep them low)

- **`work <verb>` loads only that verb** (`COMMANDS` in `cli.ts`: names → a dynamic import; help, completion and unknown words load all). A command module added to `src/commands/` goes in that table (`tests/cli-commands.test.ts` checks the words match the commands' own names and aliases). `work hook` goes straight to `commands/hook.ts` before `bin.ts` loads chalk or the CLI.
- **Heavy packages load on first use** where a hook would otherwise pay for them: `cross-spawn` through `core/platform/spawn.ts` (same function and `.sync`; the PTY host's `pty-session.ts` imports it directly, it needs `_parse`), `proper-lockfile` in `fs-safe.ts`, `chokidar` in `fs-watcher.ts` (Linux only watches with it) — `createRequire(import.meta.url)('pkg')`, which `tests/packaging/runtime-dependencies.test.ts` counts as an import.
- **`/api/sessions` is the live sessions**; `?archived=1` adds the archived ones (two caches, one per answer). The dashboard asks for them only while something shows them (`wantArchived` in `DashboardApp`: Sessions' Archived or All, the Ctrl+P switcher, a session page for one that isn't live — "Loading…" until they came, never "not found" first). Their rows are kept between builds (`createArchivedRows`, `session-wire.ts`): rebuilt when its `archive.json` is written, it's renamed or entered, or a note comes or goes. `work sessions --json` keeps its own `--all`.
- **The SPA**: highlight.js is its core plus the languages `EXT_TO_LANG` names (`utils/language.ts`; a test checks each is registered), and the terminal (xterm) is its own chunk (`LazyPtyView`), preloaded once the session list is up. § Not the diff view: `wd --static` inlines the main bundle into one file, which can't fetch more chunks.

### Desktop app (`desktop/`, Velopack)

The Tauri app shows work web in its own window (`desktop/src-tauri/src/main.rs`): it finds the running work web or starts one, and follows it across restarts. It ships through **Velopack** on the same GitHub Release as npm (`vX.Y.Z`; the `desktop` job of `release.yml` runs `desktop/scripts/velopack.mjs` on Windows, macOS arm64 and Linux), modeled on bearing:
- **The CLI ships inside the package** as one `cli.zip` + `cli.version` next to the executable (staged by `desktop/scripts/stage-cli.mjs`, written by `zip-store.mjs`: stored, deterministic, read back before it ships): the npm package's files, its production `node_modules` (native modules built on that OS, other platforms' prebuilds dropped, and `trimmable` files — docs, types, source maps, TS sources, test folders, native build sources — gone, about half), and the Node that built them (CI pins it exactly). One file, not ~1,650: Velopack rewrites every file of a package on each update and the antivirus scans each — the 2.0.1 update took a minute and a half on 3,282. The smoke test runs `--version`, `--help` (every command, every import), requires the native and first-use modules, and on macOS and Linux opens a terminal: node-pty's `spawn-helper` must be executable (`makeHelpersExecutable`; npm unpacks the prebuilt one 0644 and only node-pty's install script fixes it — 2.0.2's macOS app shipped it so, and no terminal started). The PTY host also fixes the bit itself before its first terminal, on any install (`makeSpawnHelperExecutable`, `core/pty/spawn-helper.ts`). One delta updates both; a CLI that could drift from its app is a bug.
- **It runs from a copy, never the install folder** (`runtime.rs`): an update replaces the install folder, and on Windows Velopack stops what runs from it — work web and the PTY host that owns every Claude. The app unpacks `cli.zip` (or copies the `cli/` folder of a package before 2.0.2) to `~/.work/runtime/<version>/` (temp name, checked, then rename), writes `~/.work/runtime/current`, and starts work web from there; old copies go once nothing runs from them (Windows: a folder with an open file can't be renamed) beyond the newest two.
- **`work` / `wd` on PATH**: launchers in `~/.work/bin` run `runtime/current`; that folder is APPENDED to the user's PATH (`path_setup.rs`: Windows HKCU registry, raw/unexpanded, + WM_SETTINGCHANGE, at install, update and every start, removed on uninstall; macOS/Linux a marked profile line), so an npm-installed `work` stays first. Claude hooks stay `work hook …` through PATH.
- **Updates** (`updates.rs`): GitHub Releases (`GithubSource`), a minute after start and every 6 h; downloaded, applied by Velopack on the next start, or at once on the dashboard's Restart. The app talks to its own window directly, not through work web (which can be another work's): before each page load it marks the window (`__workDesktop`, `updates::PAGE_MARKER`), sends every change of where its update stands as a `work-desktop` event (`page_script`, `on_change`; `downloading` with Velopack's percentage, `ready`, `installing`), and takes the page's asks as a navigation to `http://work-desktop.invalid/<hello|check|restart>`, which it cancels (`on_navigation`, `page_ask`; `.invalid` never resolves, so outside the app it goes nowhere). The page (`hooks/use-desktop.ts`, `desktopWire` → `inAppUpdates`, `core/updates/updates.ts`) then shows the app's version and update — a progress bar on the card and in the version menu (`ProgressBar`) — and the server adds only the release notes. For a dashboard in a browser tab the same state still goes through two files in `~/.work`: `desktop-update.json` (`unmanaged` for a dev build, which writes only to its own window, `checking`, `current`, `downloading` + `progress`, `ready`, `installing`, `failed` + why; with its pid), and `desktop-request.json` (`check` / `restart`, written by work web) every 2 s, removing it. Restart is `apply_updates_and_restart`: the app exits and comes back on the new version; work web and the PTY host run from `~/.work/runtime`, so Claudes keep running. The first run also registers the Claude plugin (the package's postinstall, in the background).
- **The Inbox count on the taskbar** (`badge.rs`): the page asks `badge/<n>` (the Inbox count, `useTaskbar`, `state/taskbar.ts`) on every change and `attention` when a session newly waits on you (`waitsOnYou`, the Inbox's first section; `newlyNeedingYou`: not the ones waiting when the list first came — nothing is asked before it has, `ready`; switch in the version menu, per browser), every ask through one queue, one at a time (`desktop-asks.ts`: two navigations in one task can replace each other in the WebView), over the same cancelled navigation as the update asks (`page_ask`: digits only, at most four). Windows gets an overlay icon drawn in Rust (a red disc with 1–9 or 9+ in a built-in 3×5 digit font, `overlay_rgba`, no image files), macOS and Linux the badge count; the flash is `request_user_attention`, skipped while the window is in front. The marker (`__workDesktopTaskbar`) is injected in the dev app too, so `npm run app:dev` shows it.
- **Out of the install folder**: right after Velopack's hooks the app moves its working directory to `~/.work` (`neutral_dir`), which everything it starts inherits: on Windows a process working from the install folder keeps Velopack from moving it aside, and the update rolls back (2.0.2 → 2.0.3 did on every Restart). Detached servers `work` starts itself (`spawnDetachedWork`: the PTY host, a lean work web) start in the home folder for the same reason, and so a worktree they were started from can still be removed.
- **It runs its own work web**: one of another version already running (a dev checkout's, the one from before an update) is stopped with the bundled CLI's `work web --stop` and replaced (`replace_other_version`, by `/api/context`'s `version`), so the window, its version and its updates are the app's. Stopping work web never stops a Claude (they live in the PTY host).
- **The login shell's PATH** (`core/platform/shell-path.ts`, `core/agents/agent-path.ts`): an app started from the Dock or Finder gets the system's minimal PATH, which it hands to work web, the PTY host and every Claude — `claude` wasn't found and each session "exited with code 1" (node-pty's child exits 1 when exec fails). `ensureAgentPath` runs in full `work web` before the PTY pool (not wd's lean server: it starts no agent) and in the PTY host once it holds the singleton lock, before the restore: on macOS and Linux, when one of the agents' commands (`agentCommands`, from the registry: new sessions', the assistant's, the summaries') isn't on PATH, the login shell is asked (`$SHELL -ilc`, between markers) and its PATH goes first. § The shell is killed with SIGKILL at 5 s (an interactive bash or zsh ignores SIGTERM, and spawnSync then waits for it) and started detached on POSIX (else it keeps the terminal's foreground group and Ctrl+C no longer reaches work web) — `shellPathSpawnOptions`. What it did goes to the debug log too (the app discards work web's output). Found already (started from a terminal): nothing is asked. A host started before keeps its PATH: `work pty-host --restart` from a terminal.
- A dev build (no `cli/`) and `WORK_DESKTOP_CLI=path` run the `work` on PATH instead. They follow whatever work web runs.
- **The dev app** (`npm run app:dev` / `npm run app:demo`, `desktop/scripts/dev-app.mjs`): `tauri dev` with `tauri.dev.conf.json` (productName "work dev", identifier `hr.moberg.work-desktop.dev` — its own WebView profile — and `icons-dev/`, the logo with a DEV band: `node desktop/scripts/make-icon.mjs --dev` then `tauri icon … -o src-tauri/icons-dev`) and the Cargo feature `dev` (`main.rs` `DEV`): window "work (dev)", follows the dev server through `web-dev.url` and starts `node <checkout>/dist/bin.js web --dev` when none runs; no Velopack, updater, runtime copy or PATH. `app:dev` builds the checkout and restarts the dev server first; `app:demo` starts the demo and pins the window to it (`WORK_DESKTOP_URL`). Side by side with the installed app.

§ The pack id `WorkDesktop` and bundle id `hr.moberg.work-desktop` are permanent: changing either orphans every installed copy.

### Color Forcing

`bin.ts` sets `chalk.level = 1` when chalk detects level 0, because Windows `.cmd` shims don't preserve TTY detection. Respects `NO_COLOR` env var.

### Tab Completions

`completions/index.ts` provides dynamic completions via yargs' `--get-yargs-completions`. The handler receives `argv._` as `['<scriptName>', ...args, '<current>']` — skip first and last to get completed args. For groups, branch completions read from the group's directory on disk (not individual repo worktree lists).

`core/setup-completions.ts` handles auto-installing completion lines into shell profiles. Called during `work init` and available standalone via `work completion --install`. Detects PowerShell 7/5.1 on Windows (via `[Environment]::GetFolderPath('MyDocuments')`) and bash/zsh on Unix (via `$SHELL`). Idempotent — uses a `# work tab completions` marker to skip if already present.
