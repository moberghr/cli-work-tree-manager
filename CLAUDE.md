## Architecture & CLI Reference

The remainder of this file is the architecture / CLI reference for human readers and agents that need the full picture of module flow, command surface, and the `wd` / `work web` design. The standards above (skill routing, critical rules) are the canonical short list; this section is the long form.

## What This Is

A cross-platform TypeScript CLI (`work`) for managing git worktrees across multiple repositories. Supports single-repo and multi-repo "group" worktrees with automatic Claude Code launching. Installed globally via `npm link`.

## Development

```bash
npm run build          # Bundle with tsup → dist/bin.js
npm run dev            # Run directly via tsx (no build needed)
npm test               # Run all tests with vitest
npm run test:watch     # Watch mode
npx vitest run tests/core/resolve.test.ts  # Single test file
```

After building, `work` is available globally (via `npm link`). Rebuild after source changes.

### Core is a library: two front-ends, one implementation

`src/core` holds every piece of logic; the CLI (`src/commands`) and the HTTP API (`src/core/*-routes.ts`, the backend for the SPA and a future desktop app) are thin front-ends that call it. Neither calls the other. Pure pieces that the SPA shares live in core and are re-exported by the SPA: `session-view.ts` (status vocabulary, age sections), `digest-view.ts` (Today windows and Markdown), `saved-prompts.ts`, `attention.ts`, `api-types.ts`.

§ Core never prints (architecture test §2.7): no `chalk`, no `console.*`, no raw stdout/stderr writes under `src/core` (logger.ts excepted). Use `report(level, text)` (`core/report.ts`). The reporter is scoped with AsyncLocalStorage (`withReporter`): the CLI shows reports with colors (`commands/shared/console-reporter.ts`: stdout for `work`, stderr for `wd`), servers default to the debug log, and a route can collect them (`collectingReporter`) to return a failure's real reason — `POST /api/worktrees` does.
§ WHEN adding logic, put it in core and call it from both front-ends; a route or command handler only parses input and formats output. `work sessions --json` rows come from `sessionWire` (`core/session-wire.ts`), the same function as `/api/sessions`; the digest from `createDigestSource` (`core/digest-source.ts`); cleanup from `scanCleanup` / `applyCleanup` (`core/cleanup.ts`, deps in `core/cleanup-deps.ts`).

Claude reads this data through the CLI (`--json`), described to every session by the `work-sessions` skill in the plugin (`plugins/work-tree/skills/work-sessions/SKILL.md`).

### Key Design

- **Shared core operations:** `setupWorktree()` and `teardownWorktree()` in `core/worktree.ts` are the high-level entry points used by both the CLI commands and `work web`. They resolve targets, create/remove worktrees, handle group CLAUDE.md, and manage sessions. Low-level building blocks are `createSingleWorktree()` and `removeSingleWorktree()` which handle one repo with rollback on failure.
- **Resolver pattern:** `resolveProjectTarget()` in `core/resolve.ts` dispatches a name to either a group or single repo, returning `{ isGroup, name, repoAliases }`. Commands use this to branch into group vs single-repo handlers.
- **Branch resolution order:** local exists → remote exists (creates tracking branch) → neither (creates new branch).
- **Path convention:** Branch directories replace `/` with `-` (e.g., `feature/login` → `feature-login`). Single-repo worktrees at `<worktreesRoot>/<repoFolderName>/<branch-dir>/`, groups at `<worktreesRoot>/<groupName>/<branch-dir>/<repoFolderName>/`.

### `work dash` (removed in 2.0)

`work dash` (the Ink TUI with its own PTYs and http-type hook server) was retired: use `work web` (browser dashboard) + `work attach` (a real terminal on the same PTY-host session). Its leftover http hook entries in `~/.claude/settings.json` are PID-tagged and pruned as stale by the next `work web` hook install.

### Re-entering a worktree (pull + resume)

`work tree` is both "create" and "switch back", and switching back is the common case. Whenever the target checkout already exists — an existing worktree, or the base repo when the branch positional is omitted — two things happen before the AI tool launches:

- **Pull.** `pullLatestForBranch()` (`core/worktree.ts`) runs fetch + pull in that directory. Best-effort by design: a branch with no upstream returns early (a bare `git pull` there prints a "no tracking information" error that reads as a failure), and a pull blocked by a dirty tree or conflicts only warns. It must never block getting into the worktree. Threaded through `setupWorktree(..., { pull })` → `createSingleWorktree(..., pull)`; `--no-pull` sets it false. A freshly created worktree skips this — it is already at the branch tip.
- **Resume.** `launchTool()` in `commands/tree.ts` passes `resume: true` so the tool gets its resume flag (`--continue` for Claude Code). ### PTY host (sessions that survive restarts)

Claude PTYs are owned by the **PTY host** (`work pty-host`, hidden), a detached localhost process — not by `work web`. `work web` (via `core/pty-pool.ts`) and `work attach` are clients: restarting/rebuilding `work web` or closing a terminal only drops a view. Discovery: `~/.work/pty-host.json` (pid, port, random token; every request carries the token, plus a Host-header check). Live sessions are mirrored to the restore list (state.db `pty_sessions`); on host start they are respawned with `--continue` (the "restored" flag), so a crash, `--restart` or reboot picks up where you were. A PTY that exits on its own is forgotten after 5 s (not immediately — at Windows logoff the children die just before the host); an explicit kill (worktree delete) forgets it at once. Several clients may attach to one PTY; the last resize wins.

**Idle Claudes sleep** (`core/idle-sleep.ts`, a 5-minute sweep in full-mode `work web`): a host PTY with **no client attached** (`PtyInfo.clients`), that has **printed nothing** for `sleepIdleAfterMinutes` (config, default 120, at least 30 — the Terminal tab reads a Stop in the last 30 min with no PTY as "running elsewhere"; 0 = never; `PtyInfo.lastOutputAt` — an idle Claude prints nothing, a working one redraws its spinner), whose status isn't working/needs_input, and isn't the assistant, is stopped (`disposePty`): it stops holding memory, and opening the session resumes the conversation. The dashboard's terminal deck (`TerminalDeck`) keeps up to 5 terminals connected for instant switching, but one hidden for `DECK_HIDDEN_MS` (10 min) lets go (`pruneDeck`), so its Claude counts as unattended and can sleep — with the app open all day, the five most recent Claudes otherwise never slept. Idle headless chats sleep by the same rule (`idleChats`: idle, no chat view open; the next message resumes), and a chat's kept history is capped by size (`MAX_HISTORY_BYTES`, never below the last 50 messages). `clients`/`lastOutputAt` are additive: a host from before reports neither, and then nothing sleeps.

§ A probe that times out is a BUSY host, never a missing one: `findHost` retries with a longer timeout, then throws `PtyHostBusyError`, and every "should I start one?" path treats that as running (a second host restores every session again).
§ WHEN changing the host wire format, bump `PROTOCOL_VERSION` (now 2: the restore list moved into state.db; a v2 host adopts a `pty-sessions.json` written by a v1 host that outlived the upgrade — `adoptLegacyRestoreList`) — the host outlives rebuilds, so clients must detect an old one and tell the user to `work pty-host --restart` rather than misbehave.
§ WHEN spawning into a PTY, let `resolvePtyCommand` (`tui/session.ts`) build the command — never `cmd.exe /c <tool> <args>`: unescaped, `&`/`|`/`%` in a prompt or path run as commands on Windows.
§ WHEN adding a path that spawns Claude for a session, go through `spawnSpecFor` + the host, not `new PtySession` — otherwise that session won't survive restarts or be attachable.
§ A Claude launched directly in a terminal (`--no-host`, config `launchViaHost: false`, or from before 2.0 made host launches the default) is invisible to the host, and the Terminal tab must not put a second one on its conversation: `claudeElsewhere` (`core/terminal-ws.ts`) infers one from a transcript write in the last 5 min, a working/blocked status, or a Stop in the last 30 min, and the tab then explains (with the `--host` hint) instead of spawning; `?force=1` spawns anyway. Quiet longer than that is unknown, and spawning — which resumes the conversation — is what the tab is for.

**Status icons.** Every view shows a session's status as one icon per `DisplayKind` (`StatusIcon.tsx`: "!" disc = needs input, check disc = done, turning arc = working, speech bubble = review comments, ring = idle, pulse = active, ring + dot = open, moon = stale), coloured as the old dots were; it keeps the `wd-rail-dot wd-rail-dot-<kind>` class names views and tests find a status by. The rail's right-hand slot says only how long / how many.

**Status without hooks.** A session whose Claude has not taken a turn since the dashboard's hooks went in shows transcript activity only (`displayStatus`, `state/session-display.ts`): Active ≤ 30 s, Open ≤ 5 min, Idle within a day (`recent`), Stale after that. "Last active" everywhere is `lastActiveAt`: the newest of the hook update, Claude's last write and the `work tree` entry.

### Attention inbox

`work web` (full mode, owner `web-status`) installs its Claude hooks in one write (`FULL_HOOKS`, `commands/web.ts`): one per turn edge — UserPromptSubmit → `work hook turn-start`, Stop → `work hook turn-end` (`runTurnHook`: pending comments for Claude first, then the checkpoint nudge and the status record, side by side — one `work` start per turn edge instead of three, for every Claude on the machine) — plus Notification → `work hook status-notify`; the old separate hooks (`LEGACY_HOOKS`) are removed. The status part maps the cwd to a session (`findSessionForCwd`, group-root aware), apply the event (`applyStatusEvent`: prompt → working+seen; stop → idle+unseen with the transcript's last assistant line; a Notification matching `permission|approval` → needs_input) to state.db `session_status`, then nudge `POST /api/status-changed`. The server notifies only on a real transition (`notifyKindForTransition`) and broadcasts `sessions-changed`. Where it notifies follows presence (`core/presence.ts`): each dashboard tab POSTs `/api/presence` (session shown, visible, focused, may notify) on change + a 15 s heartbeat (45 s TTL, `sendBeacon` goodbye). A focused tab on that session → nothing; a tab that can notify → SSE `notify` (browser Notification, click-to-jump, `use-presence.ts`); otherwise the desktop toast. `statusHooks` always run. Read-side `effectiveStatus` decays a 15-min-quiet "working" to idle and treats transcript activity after a permission prompt as answered (no hook fires on approve), and an idle session whose transcript has a turn's message (yours, a `!` command or its output, Claude's, a tool result — `lastTurnEntryMs`, not Claude Code's own durations/away summaries/PR links) after its last turn ended (`turnEndedAt`, set by Stop) as working: `!` commands and Claude's turn on their output fire no prompt hook, so such a session read grey while it worked. `sessionStatusView` (`core/turn-activity.ts`) is what every caller uses; it reads the transcript tail only when it was written after the turn ended, cached by size + mtime. Opening a finished session marks it seen. Inbox order (`core/attention.ts` `inboxRank`/`compareInbox`): needs input (oldest first) → done-unseen (oldest first) → review comments → working (newest first) → quiet. **Review comments**: a session whose open PRs have unresolved review threads whose last word isn't yours (the PR watch's `openThreads`, summed into `SessionWire.openReviewThreads` by `reviewThreadsOf`) shows as `review` (pink speech-bubble icon, the count on the right of its rail row) unless its Claude needs input, is working or finished unseen, and counts in the Inbox badge (`wantsYou`). A change in that count broadcasts `sessions-changed`.

**What corrects the hooks** (an audit found each of these wrong once):
- **Claude Code's own state wins when newer** (`withLiveClaude`, `core/session-status.ts`): every running Claude writes `~/.claude/sessions/<pid>.json` with `status: busy|idle|waiting` (+ `waitingFor`, `statusUpdatedAt`; read by `live-claudes.ts`). Busy → working, waiting → needs input, idle ends a working / needs-input record — the hooks miss turns (a work web restart, an Esc, a Stop that handed Claude more work), that file doesn't. With no Claude running for a session anywhere (process list read, no PTY or chat of ours), working / needs input is over at once.
- **Notifications by `notification_type`**: `permission_prompt` / `elicitation_dialog` → needs input; `idle_prompt` (a minute after it stopped, with no Stop: an interrupt) ends a working / needs-input record, seen. The message regex is only the fallback.
- **A Stop that delivered comments** (`decision: block`) records `continue` (still working), not a false "Done"; the real Stop comes later. A Stop always starts its own `since`, and one with no prompt hook before it is stored with `prevState: working`, so you are notified.
- **"Answered"** (needs input → working) counts only a turn's transcript entry (`lastTurnEntryMs`: not slash-command echoes, compaction, away summaries or exit lines), and decays after 15 min like working.
- **Seen** only while the window is visible and focused (`useLooking`, `DashboardApp.tsx`).
- **Two sessions on one folder**: `findSessionForCwd` picks the non-archived one, then the one whose branch is checked out, then the latest — not the oldest.

**Getting a status on screen, always.** Three independent paths, so none gates it:
- **The hook's nudge**: `POST /api/status-changed`, which broadcasts `sessions-changed` FIRST and does its bookkeeping (diff stats, scope, conversation copy) after replying (`setImmediate`).
- **The change counter**: `session_status` writes bump `rev:sessions` (db triggers, schema v3), and the 1 s poll broadcasts even when no nudge arrived.
- **File watches**: transcripts and `~/.claude/sessions` (Claude Code's own state). Plus the 10 s tick for time-based changes.

Every broadcast drops the sessions cache. The SPA refetches at most 400 ms after the first event of a burst (`coalesce` throttles: a debounce kept the list stale while any Claude wrote), and again whenever its event stream (re)connects. `watchLoop` (`core/loop-watch.ts`) reports a blocked event loop (≥ 1 s) with the slowest request, in the log and the Activity panel (`server`).

§ Keep `/api/sessions` and `/api/status-changed` free of slow synchronous work: everything, statuses included, waits behind a blocked loop.

§ WHEN adding an attention state or signal, extend `applyStatusEvent`/`effectiveStatus` and `core/attention.ts` — the SPA imports the latter directly, so keep it free of imports.

**Snooze.** "Not now" for a session that wants you (`core/snooze.ts`, pure; per session in state.db `session_snooze`, schema v5, purged with the session): 2 hours, until tomorrow 9:00 (this morning when it's still before 6), or until its status changes (`statusKey`: Claude's state + since, and the waiting review threads). While it holds (`snoozeActive`, applied in `sessionWire` → `SessionWire.snoozed`), `inboxRank` puts it in a last section of its own (6), so it leaves the Inbox, its count, `n` and Review all; a timed one also holds its notifications. From the rail's right-click menu and a Snooze button on each Inbox row that wants you (`POST`/`DELETE /api/sessions/:id/snooze`).

**Review queue.** "Review all" on the inbox's Done section walks the finished, unseen sessions one by one (`state/review-queue.ts`). The order is fixed when the queue starts, since opening a session marks it seen and would otherwise reshuffle the rest. Each opens on its **Last turn** diff (`DiffView startOnLastTurn`, applied once per session), a done row opened from the inbox does too, and `n` means "next in the queue" while you're in it (`ReviewQueueBar`).

**Kept conversations + search.** Claude Code deletes its transcripts after `cleanupPeriodDays` (30 by default); work keeps its own copy in `~/.work/conversations/<session id>/` (`core/conversation-store.ts`) for as long as the session exists, so "what did we do about X?" reaches back as far as you like. Disk only — nothing of it is held in memory. A transcript only grows, so a sync copies just the new bytes, written at the source's own offsets (two syncs at once — a turn's and the sweep's, or `work search` beside work web — write the same bytes to the same place); a source smaller than the copy was replaced and is copied whole; a copy is never deleted when its source goes. Syncs: a session 5 s after its status hook (`onStatusChanged`), and every live session a minute after start and every 30 minutes (Activity panel, kind `conversations`). Archived sessions aren't synced (their Claude is stopped; the archive has the rest). `searchConversations`: every word in one message (yours or Claude's) or an archive's written summary; an archived session reads its archive first (from before the store too), a live one its copy, each falling back to the other; most recently active first, 20 sessions, 3 snippets each. The Sessions tab shows hits while you filter ("In conversations": open, or Restore an archived one). The folder goes with the session on delete (`sessionStatePaths`).

**Overlap warning.** Two live sessions that change the same file of the same repository will conflict when the second merges; the dashboard says so while both are in progress ("⚠ Same files as chore/deps-update", in the session header, inbox and Sessions table). The diff-stat cache's background pass (`computeChanges`, `core/diff-stat.ts`) also collects each repo's touched files since the fork from `origin/HEAD` (committed + uncommitted + untracked), keyed by `--git-common-dir` so every worktree of a repo shares one key. `/api/sessions` pairs them with the pure `findOverlaps` (`core/overlap.ts`), which costs no git of its own. The demo uses the same function on its diffs.

**Context per session.** "Context 62%" in the session header and Sessions table: how full the session's Claude conversation is, from the newest main-thread assistant message's `usage` in its newest transcript (prompt = input + cache reads + cache writes, plus the reply; `core/context-usage.ts`). The window is 200k, or 1M for a `[1m]` model id or usage past 200k. It re-reads a transcript's 64 KB tail only when its size/mtime changed. Amber from 70% and red from 90%, with a hint to start fresh. Token counts only: cost is left out because prices aren't in the transcript.

**Answering permission prompts from the inbox.** The Notification hook stores the tool call the prompt is about (`request`: the transcript's newest unanswered `tool_use`, `core/permission-request.ts`), and the inbox shows it (`Bash npm test`) with Allow / Deny for sessions running in the PTY host. `POST /api/sessions/:id/answer` types Enter (Yes) or Esc (No) into the PTY, and records an `answered` event. § It only types after `checkDialog` passes on the host's plain-text screen (`GET /ptys/:id/screen`, `PtySession.screenText`): the permission dialog is showing, it is about the request the user was shown (command start or file name), and "1. Yes" is highlighted. Otherwise it refuses with the reason and types nothing. Keep that check in front of any new keystroke path. The screen route is additive, so there's no protocol bump: an older host answers 404, which shows as "answer it in its terminal".

### Ship & archive

`Ship` runs `core/ship.ts` per repo. **Groups ship in parts**: backend may be merged while frontend is in review.
- A repo is **done** when its PR is MERGED or it was never touched (0 commits vs `origin/HEAD`, clean, no PR). Done repos are never blockers and never selectable.
- "Published" means `origin/<branch>` exists — not `@{u}` (`work tree` leaves new branches tracking `origin/main`); ahead/behind are measured against `origin/<branch>`, and push uses `-u origin <branch>` unless tracking already points there.
- **Merge = `mergeSelected`**: the client sends `repos: [{name, headSha}]` — the repos the user ticked and the PR heads it SHOWED. The server re-runs the preflight and refuses the whole call if any selected repo is unknown, done, blocked, or its PR head moved; only then merges each with `gh pr merge N --<method> --match-head-commit <that sha>`, stopping at the first gh failure. Unselected repos are never touched.
- Blockers include: dirty tree, not pushed, unpushed commits, origin ahead of you, PR head ≠ local HEAD, draft, closed, conflicts, behind base, branch protection, failing/pending checks.
- The session is **archived only when the merge merged something AND every repo is done** afterwards.
- **Archive** (`archiveSession`, `core/session-archive.ts` — the one path for the Archive button, Ship's merge, the PR watch and cleanup): first checks nothing is waiting (`archiveWaiting`: reply drafts to post, notes not yet delivered, a Claude working or waiting for an answer) — the button asks and can force it (409 `blocked` → confirm → `force: true`); auto-archive, Ship and cleanup wait. Then it stops its Claude and its dev server (and releases watchers / a chat) — and from there to the end nothing may start that Claude again: `ensurePty` refuses a session being archived or archived (`core/archiving.ts`), since a Terminal tab still open on it reconnects and would start it (an archived session once kept a live Claude that way, restored after every host restart), records each repo's branch tip, copies every transcript to `~/.work/archive/<id>/transcripts` (Claude Code deletes old ones itself) with `archive.json` (prompts, PRs, last summary), and removes the worktree **only when cleanup's check says nothing would be lost** (merged + clean; never a repo's own checkout). Removed: its checkpoint refs go, and a local branch already merged into the main branch is deleted (`branchesDeleted`; a squash-merged one stays — nothing else reaches its commits). Kept: the reason is recorded and its git-ignored build output is cleared. Afterwards an internal `claude -p` writes a few sentences on what was done (`summary.written`, `archive-summary.ts`), which the Sessions list shows and the conversation search finds. **Restore** (`work tree` into it, or Restore): `setupWorktree` first recreates a deleted branch at its recorded tip (`recreateArchivedBranches`), then the worktree, and `restoreArchivedTranscripts` puts the conversation back where Claude looks, so it continues. **Retention** (`archive-retention.ts`, daily, in the Activity panel): transcripts of archives older than `archive.compressAfterDays` (default 30) are gzipped — lossless, search and Restore read `.gz` (`readArchivedTranscript`); `archive.dropTranscriptsAfterDays` (default 0 = never) deletes them, keeping the summary. The archive folder goes with the session on delete (`sessionStatePaths`).

§ WHEN adding a ship action, route git/gh through `CommandRunner` (argv, no shell) and re-check preconditions server-side — the client's preflight may be stale.

### Session Tracking

`core/history.ts` stores worktree sessions in state.db's `sessions` table (one row per `target + branch`). The `tree` command calls `upsertSession()` before launching Claude; `remove` calls `removeSession()` on success. The `status` command reads history + live git info; `recent` lists sessions sorted by last access.

**Session identity & state.** The id is `sessionIdFor` (`core/session-id.ts`: sha1(target:branch), 12 hex). The branch is the one it STARTED on, and names its folder; its name is separate — `title` (`--name`, the New worktree dialog's Name, F2 / Rename later), the rail's label when you gave one. Claude (or you) may switch the worktree to another branch: ship, the PR watch and the diffs read the checked-out branch from git; `onOtherBranch` (HEAD files, no git: `core/git-head.ts`) shows it; re-entering uses the folder as it is; archive records it (`heads`) so Restore of a removed worktree checks that branch out again. Everything per-session beyond history is a row keyed by that id — `session_status`, `comments` (store = id), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs` — plus the dev log file; `removeSession` (and `work status --prune`) purge it all via `purgeSessionState` (`core/session-store.ts`) → `purgeSessionRows` (`core/db.ts`), so a re-created session never inherits old state.

§ WHEN adding per-session state, add its table to `purgeSessionRows` (`core/db.ts`), or its file to `sessionStatePaths` (`core/session-store.ts`). Its diff scope's checkpoints are keyed by the hash of its paths, not its id: `removeSession` clears them (`clearSessionCheckpoints`, from the base checkouts — the worktree may be gone), archive and the dashboard's delete drop the scope's watch (`releaseSessionScope`), and a scope keeps at most `MAX_CHECKPOINTS` (200; the oldest after Initial go, refs too).

**Finding work web.** `core/web-discovery.ts` owns `web.url` / `web.pid`. The files outlive the process and PIDs get reused, so `work web --stop` kills only after `/api/context` answers with the recorded pid (`probeWeb`); `webServerResponds` is liveness only. The PTY host has the same rule (`/health` + token + pid). `/api/context` also carries `build` (`core/build-stamp.ts`: the entry file's mtime): a full `work web` replaces a running server whose build differs from its own, or that predates stamps, since a server that outlived a rebuild reads state and serves routes as they were then (a September dashboard showed no sessions after the SQLite move and 404'd on new routes). `wd` and `--lean` never replace. § Two can still start at once (a restart racing the desktop app's watchdog, which starts one when none answers): every 20 s a work web runs `discoveryCheck` — the one web.pid doesn't name, when the named one answers as itself, stops (leaving the hooks, which are removed by owner and are the other's too, and the discovery files); with nothing live recorded it writes itself back. A duplicate once kept an old build in the desktop app for hours and doubled the GitHub API use.

### Diff Review (`wd`)

Second binary (`dist/wd-bin.js`, shim `wd`) that surfaces a GitHub-PR-style diff in the browser. Two modes, both rendering the same React SPA at `dist/web/`. The SPA reads `/api/context` (or `window.__WD_BOOT__` in static mode) to decide which screen and whether the comment UI is enabled.

**One server, many routes.** `wd` always routes through the singleton `work web`: it reads `~/.work/web.url`, POSTs `/api/scopes`, and opens `<webUrl>/diff/<hash>` (or `/review/<hash>` for `wd -c`). When no work web is running, `wd` auto-spawns one in the background — detached `node <bin> web --lean --no-open` — and waits for `~/.work/web.url` to appear before registering. Lean mode (`startWebServer({lean: true})` in `core/web-server.ts`) skips the dashboard-only `~/.claude/projects` activity watcher + the 10 s session-decay tick, and `commands/web.ts` skips installing Claude `UserPromptSubmit`/`Stop` hooks (no `~/.claude/settings.json` mutation). Net result: a `wd` invocation in a fresh shell costs ~one `work web --lean` startup; subsequent `wd` calls across worktrees register on that same server with no extra processes or ports.

- **Live server (`wd`, default):** `runLauncher` calls `ensureWorkWebRunning` (reads `web.url`, autostarts lean work web on a 5 s wait if absent), POSTs the scope, opens `/diff/<hash>`. There is no per-scope daemon class anymore — the previous `runDaemon` / `spawnDaemon` / per-scope `.pid|.url|.log` files are gone. Live updates via chokidar + SSE are **staged, never auto-applied**: on `diff-changed` the SPA re-fetches in the background (`checkForUpdates` in `hooks/use-deferred-diff-load.ts`) and, only if the payload actually differs, parks it in `pending` and shows a `DiffUpdateChip` ("New changes · N files" + Show / Only new / Reload — Show applies the staged payload keeping scroll; Only new narrows to a checkpoint range from the newest checkpoint taken before the on-screen diff was fetched; Reload is a soft foreground refetch + scroll-to-top, never `location.reload()`) **in the header**. Likewise no in-flight dim or progress bar: the only busy cue is `DiffBusyChip` in the header — the diff itself never moves under a reader mid-scroll, and nothing above it is inserted (a banner would shift every line). § WHEN adding another live-refresh path, stage it the same way; do not write straight into `data`. `wd --stop` de-registers the scope (DELETE `/api/scopes/:hash`); the server itself keeps running.
- **Static (`wd --static`):** `renderStatic()` in `core/static-renderer.ts` reads the SPA shell, inlines its CSS/JS, and injects the diff data as `<script>window.__WD_BOOT__=...;</script>`. Writes to `~/.work/diffs/<hash>.html`, opens via `file://`, exits. Self-contained — survives the CLI, no server. The boot JSON goes through `escapeForScriptTag` (handles `</script`, `<!--`, U+2028/U+2029, raw control chars). The boot-script injection uses a function-callback replacement so JSON values containing `$'` (a real shell-regex hazard) don't trigger `String.replace`'s `$`-magic.
- **Review (`wd -c`):** `tryReviewViaWorkWeb` in `commands/diff.ts` registers a scope on (auto-spawning if needed) work web, opens `/review/<hash>`, then polls `/api/scopes/<hash>/comments` once per second. `core/review-poll.ts::diffReviewSnapshot` is the pure helper that diffs the previous-tick `seen` set against the current snapshot. Exits cleanly when the snapshot returns `ended: true`; the scope and browser tab keep working after the CLI exits. If work web autostart fails entirely (port refused, dist/web missing), `wd -c` falls through to a foreground `startCommentServer` (`core/comment-server.ts`) — a per-invocation Hono sub-app that blocks until "End Review", same shape as before.

**Scope resolution** (`resolveScope` in `core/diff-scope.ts`): walks the cwd against the session history. Inside a single-repo worktree → that repo. Inside any sub-repo of a group worktree → the whole group, with that sub-repo as the initially-active tab. At a group root → all repos, no active tab preselected. Outside any work-managed worktree → falls back to `git rev-parse --show-toplevel` (single repo).

**Renderer:** the React SPA in `src/web/`, built by Vite to `dist/web/`. `ReviewApp.tsx` lays out the sidebar (file tree + comments panel), general-comment pane, and `DiffRepo` (per-file `<article>` with side-by-side `<table>`). When `context.readOnly` is set, composer/draft/submit UI and `ReviewProvider` are suppressed (no `fetch('/api/comments')` over `file://`); the diff and file tree still render. Syntax highlighting is npm-bundled `highlight.js` applied per-cell via `dangerouslySetInnerHTML` during render — not post-paint mutation. Intra-line word diff via `diff` package. Viewed-checkbox state persists per-scope in localStorage.

**Status output convention:** stdout carries data only (the comments markdown payload in review mode). All status messages go to stderr via the `info()` helper in `commands/diff.ts`. `console.error` is reserved for real errors.

**Claude integration:** two paths route review comments to a live Claude in the matching worktree without the user typing —
- **`work web` command hooks** in `~/.claude/settings.json` (installed by `work web` on startup, removed on shutdown via `core/command-hook-installer.ts` + the shared atomic-write `core/settings-editor.ts`). The `UserPromptSubmit` hook prepends pending comments to the next user turn; the `Stop` hook returns `{decision:'block', reason:<comments>}` so Claude addresses them automatically when it finishes any turn. Delivered state is state.db `comment_deliveries` (see `core/pending-delivery.ts`). § Two processes deliver (the hook process and the PTY push), so delivery is a **claim**: `claimForDelivery` inserts the ids with `INSERT OR IGNORE` in one transaction, and only the rows it inserted are its to send. Send only what you claimed; `releaseClaim` if the send fails. Never read pending and mark delivered as two separate steps.
- **Owned-PTY push** in `core/session-comment-routes.ts`: when a comment is posted and `work web`'s pool already owns a PTY for that session (the user opened the Terminal tab), the route handler writes the formatted reminder directly to stdin. Idle Claudes in our own PTY get the comment without any hook round-trip.
- For external Claudes that are fully idle, neither path fires — the dashboard shows a purple `→N` "waiting for Claude" badge until the user does anything in that terminal.

The legacy `wd-review` skill at `plugins/work-tree/skills/wd-review/SKILL.md` (shipped via the `work-tree` Claude Code plugin marketplace — see `.claude-plugin/marketplace.json`; registered automatically by `scripts/postinstall.mjs` on npm install) is still used for the `wd -c` foreground flow (stdout marker stream + curl replies via `~/.work/diffs/latest-review.url`). Replies must use `--data-binary "@file"` not inline `-d '...'` to survive apostrophes in the body. ### Checkpoint trigger + reload-loop guard

Checkpoints are **authoritatively taken per Claude turn**: `work web` installs a `Stop` hook — the lean `wd` server `work hook checkpoint` (owner `web-checkpoint`, `LEAN_HOOKS`), the full dashboard the same inside `work hook turn-end` which POSTs the cwd to `POST /api/checkpoint`; `scope-routes` maps cwd→scope (`scopesForCwd`) and snapshots (dedup-by-tree makes a no-change turn a no-op). The fs-watch auto-snapshot is now a **fallback that suppresses itself while a Claude session is active** (`claudeActiveWithin`, `core/claude-activity.ts`) so it can never fire mid-turn before the hook — it only checkpoints manual edits when no Claude is around.

§ WHEN touching the scope diff server, preserve `suppressScopeWatch` (`core/scope-manager.ts`): the `to=working` range diff runs `git add -A`/`write-tree`, whose `.git` churn surfaces as nameless `fs.watch` events that can't be path-filtered. The diff route calls `suppressScopeWatch(hash, 800)` after computing so that self-induced churn doesn't fire `diff-changed` → refetch → recompute → **reload loop**. Real edits land outside the window and still reload. Checkpoint names come from `core/checkpoint-summary.ts` (lazy `claude -p`, cached; the small `LABEL_MODEL`, one internal run at a time across work web, a timed-out run killed with its tree). Every internal run (`internalClaudeSpawn`) is text-only and starts none of the user's MCP servers (`--strict-mcp-config`). Comment `resolved` (mark-done) and `side:'file'` (whole-file) are routed via `/api/scopes/<hash>/comments/:cid/resolve` and the normal POST with `side:'file'`.

### "Last turn" (session diffs by turn)

§ The session's scope is created by the status hook (a POST); `GET …/checkpoints` reads the manifest from disk by `scopeHashForPaths` and creates nothing (GETs have no side effects, §1.5). Dashboard paths get a session's scope through `sessionScope` (lookup-or-create, `findScope`), never `ensureScope`: ensureScope is what a NEW `wd -c` run does — revive an ended review, clear its comments, relabel — and running that on every Claude hook wiped finished reviews.

The dashboard's Diff tab has a **Last turn** scope next to Uncommitted / Since branch. A session's turns are its diff scope's checkpoints (one per instruction, taken by the Stop hook): `GET /api/sessions/:id/checkpoints` creates the scope on demand (`ensureScope`, returned by `mountScopeRoutes` — the same scope `wd` registers for those paths) and `GET /api/sessions/:id/diff?from=&to=` serves a checkpoint range (delegates to `/api/scopes/:hash/diff`). Status hooks also ensure the scope, so turns are recorded for sessions nobody has opened yet. The demo fakes three checkpoints per session with changes.

### Revert + batched review

`POST /api/sessions/:id/revert` (`core/revert-routes.ts` → `core/revert.ts`) undoes an **uncommitted** file or hunk. The server re-computes the session's Uncommitted diff to find the change and its repo root (never trusts a root/patch from the browser). Hunk revert asks git for the raw, byte-exact diff of that file (the pipeline's `-w` diff can't be reverse-applied, and the parser drops CRs) and `git apply -R`s the raw hunks overlapping the picked new-side lines after a `--check`. Then it posts a published general comment ("I reverted … don't reintroduce it"), so delivery reuses the comment path. The SPA only offers Revert in the Uncommitted scope (`RevertContext`). `submit-review` pushes the whole review to an owned PTY as one message, like a single POSTed comment does.

### Today (digest)

The **Today** tab (`#/today`, `g d`) shows what each session did since local midnight, since yesterday, or in the last 7 days: the prompts you gave it, the turns it finished (checkpoints in the window, with names that were already generated), where it stands, uncommitted changes, and its PRs. "Copy as Markdown" gives a standup note. `GET /api/digest?since=` (default 24 h, clamped to 14 days) gathers it from disk: transcripts touched in the window, read from the end in growing chunks until an entry older than the window turns up (`readTranscriptSince`, 64 MB cap → `partial`), cached per file identity; checkpoint manifests; status rows; the PR watch's cache; the diff-stat cache (`peek`, never a refresh). The assembly is pure (`core/digest.ts`, shared with the demo). § It never runs Claude, gh or git: a digest is a read, and the route is async so a big day doesn't stall the terminal relays. Prompts are the user entries you typed (deduped by uuid); tool results, slash-command echoes, task notifications, "[Request interrupted…]", meta and subagent entries are skipped. "Turns" are checkpoints, the app's meaning of the word everywhere: they include the fs-watch fallback's snapshots of hand edits made with no Claude around.

### Activity (what work does in the background)

### Jira watch (newly assigned issues start themselves)

Off until you turn it on in the Jira tab ("Start new issues automatically"; `PUT /api/jira/watch`). ### PR watch (CI strip, fix-CI, auto-archive)

`core/pr-watch.ts` is pure policy with injected I/O; `core/ci-routes.ts` wires it (sessions = not archived, touched in 30 days, path exists; `shipPreflight` for facts; `tell` = POST a published general comment, so delivery reuses the comment path; told-keys in state.db `pr_watch_seen`, per session). `work web` full mode sweeps every 180 s, 3 at a time, single-flight. § GitHub allows 5000 API points an hour and work shares them with your own `gh`: when gh answers "rate limit" (`RATE_LIMITED`) the watch keeps the last state (never "no PR"), acts on nothing and skips sweeps for 10 min; a failed review lookup keeps the last count for that PR. `/api/prs` is one shared `createSharedFetch` (`core/shared-fetch.ts`, 2 min, stale-while-revalidate) for every window — per-request `gh pr list` over every repo, on each window's interval and each sessions change, spent the whole limit. Per sweep the watch asks gh only about repos whose branch was pushed (or that had a PR it knows of: `askGh`, `shipPreflight`), re-reads a PR's review threads only when its `updatedAt` moved, and runs one check per session at a time (a refresh joins the sweep's). It tells Claude once per `session:repo:headSha` when checks fail, and archives (`archiveSession`: conversation kept, worktree removed when safe) when every repo is `done`, nothing is uncommitted, and its Claude isn't working or waiting for you, and a merged PR is this work — it merged after the session was last entered, or its head is the checked-out commit and the session has been left alone a day since it was entered (a Restore or `work tree` onto the merged tip isn't re-archived at once; `shouldAutoArchive`: `gh pr view <branch>` also returns a PR merged long ago for a reused branch name, which has another head). Keys are recorded only after the note was delivered (`tellThenRecord`), so a failed send is retried. `GET /api/sessions/:id/ci` (cached, refreshed after 60 s) and `POST …/ci/fix` feed `CiStrip`. What it has acted on (CI heads, review comments, baselines) is kept per session in state.db `pr_watch_seen` (`core/pr-watch-store.ts`, removed with the session). Review feedback rides the same sweep: `core/pr-review.ts` fetches threads (with `isResolved`), reviews and conversation comments in one `gh api graphql` call (`{owner}`/`{repo}` filled by gh from the cwd). `newFeedback` raises unresolved threads whose last comment isn't yours, keyed by that comment, and reviews/comments by others posted after the PR was first seen (a baseline, so old discussion isn't replayed). They go to Claude as one note. When the conversation is past `CONTEXT_WARN` (70%, `readContextUsage`) the review and CI notes end with `subAgentHint`: hand the mechanical fixes to a sub-agent, keep decisions and reply drafts in the main conversation (the note stays with the branch's own Claude, which remembers why the code is as it is). Trusted: reviewers with write access (`TRUSTED_ASSOCIATIONS`), plus the review bots in config `prWatch.trustedBots` (default `DEFAULT_TRUSTED_BOTS`: `copilot-pull-request-reviewer`, `github-actions`; GitHub gives bots no association, so they were never sent before). **Automated review**: each thread in the note carries its id (`[thread PRRT_…]`), and the PR watch records it (`rememberSent`, state.db `pr_replies`, `core/pr-replies.ts`). If the session's Claude isn't running anywhere, it is started in the PTY host with `WAKE_PROMPT`, resuming its conversation, and the UserPromptSubmit hook attaches the note (`wakeForNote`, `ci-routes.ts`; config `prWatch.wakeClaude: false` turns it off) — CI-fix notes wake it too. Claude fixes, pushes, drafts an answer per thread with `work pr reply` and shows you the drafts; once you say yes in the conversation it posts them itself with `work pr post <thread…> [--resolve]` (`postDrafts`: the drafts as they stand, your dashboard edits included). The session header's **Replies to post** (`ReplyDrafts`) shows each draft under the reviewer's comment, editable, with Post & resolve / Post / Discard (`POST /api/sessions/:id/replies/:thread/post` → `gh api graphql` addPullRequestReviewThreadReply (+ resolveReviewThread), `-f` raw strings, argv only). § Anything on GitHub is in your name, so a reply goes out only on your yes: your Post click, or Claude's `work pr post` after you agreed in the conversation — told so by the note, and never pre-allowed (not on `ASSISTANT_ALLOW`), so Claude Code asks you before it runs. Claude writes to GitHub in no other way. A thread raised again (a reviewer answered) starts over. The inbox's Review comments row says how many replies are ready (`SessionWire.replyDrafts`). A turn whose message has a `DECISION NEEDED:` line (`DECISION_MARKER`, `attention.ts`) becomes `needs_input` in `applyStatusEvent`. § Claude is told not to write on GitHub except `work pr post` on your yes; keep it that way, since that's the user's voice.

### State storage (`~/.work/state.db`)

Session state is one SQLite database (WAL) shared by every `work` process: `core/db.ts` is the only importer of `better-sqlite3` (architecture test) and exposes `withDb(fn)` and `tx(fn)` (BEGIN IMMEDIATE; nested calls become savepoints). Tables hold each record as JSON beside the columns it is looked up by: `sessions`, `session_status`, `comments` (store = session id or `scope-<hash>`), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs`, `tasks`, `meta`. Triggers bump `meta rev:sessions` / `rev:tasks`; work web polls those once a second instead of watching files. Stored rows come back through `json.parse(): unknown` and a shape guard, never a cast.

First open (`PRAGMA user_version` 0) creates the schema and imports the pre-SQLite JSON files in the same transaction (`core/db-import.ts`), then renames them `*.migrated`. `work state` summarizes the database; `work state --export <dir>` writes it back in the old JSON layout (rollback path, round-trip tested). Opening a new file races on the WAL switch across processes, which the busy timeout doesn't cover, so `open()` retries on SQLITE_BUSY.

§ WHEN reading-then-writing state, do it in one `tx()`. A transaction can't span an `await`, so async work (port probing in `upsertSessionWithPort`) goes optimistic: compute outside, re-check inside, retry.
§ Tests run with `WORK_DB_EPHEMERAL=1` (tests/setup): the connection closes after each outermost call so temp HOMEs can be deleted on Windows. A test that doesn't mock `os.homedir()` must not reach `db.ts` (it would write the developer's real state.db); inject a store instead, as the PTY registry does with `sessionsPath`.

### Build

tsup bundles two entry points: `src/bin.ts` → `dist/bin.js` (the `work` binary) and `src/wd-bin.ts` → `dist/wd-bin.js` (the `wd` shim that forwards argv to the `diff` subcommand). Both ship as ESM with shebangs. All npm dependencies are **external** (not bundled) — resolved from `node_modules` at runtime. This is important: adding a dependency requires both `npm install` and rebuild. `package.json` declares both binaries under `"bin"` so `npm link` registers `work` and `wd` globally.

### Desktop app (`desktop/`, Velopack)

The Tauri app shows work web in its own window (`desktop/src-tauri/src/main.rs`): it finds the running work web or starts one, and follows it across restarts. It ships through **Velopack** on the same GitHub Release as npm (`vX.Y.Z`; the `desktop` job of `release.yml` runs `desktop/scripts/velopack.mjs` on Windows, macOS arm64 and Linux), modeled on bearing:
- **The CLI ships inside the package** (`cli/` next to the executable, staged by `desktop/scripts/stage-cli.mjs`): the npm package's files, its production `node_modules` (native modules built on that OS, other platforms' prebuilds dropped), and the Node that built them (CI pins it exactly). One delta updates both; a CLI that could drift from its app is a bug.
- **It runs from a copy, never the install folder** (`runtime.rs`): an update replaces the install folder, and on Windows Velopack stops what runs from it — work web and the PTY host that owns every Claude. The app copies `cli/` to `~/.work/runtime/<version>/` (temp name, then rename), writes `~/.work/runtime/current`, and starts work web from there; old copies go once nothing runs from them (Windows: a folder with an open file can't be renamed) beyond the newest two.
- **`work` / `wd` on PATH**: launchers in `~/.work/bin` run `runtime/current`; that folder is APPENDED to the user's PATH (`path_setup.rs`: Windows HKCU registry, raw/unexpanded, + WM_SETTINGCHANGE, at install, update and every start, removed on uninstall; macOS/Linux a marked profile line), so an npm-installed `work` stays first. Claude hooks stay `work hook …` through PATH.
- **Updates** (`updates.rs`): GitHub Releases (`GithubSource`), a minute after start and every 6 h; downloaded, applied by Velopack on the next start. The first run also registers the Claude plugin (the package's postinstall, in the background).
- A dev build (no `cli/`) and `WORK_DESKTOP_CLI=path` run the `work` on PATH instead.

§ The pack id `WorkDesktop` and bundle id `hr.moberg.work-desktop` are permanent: changing either orphans every installed copy.
