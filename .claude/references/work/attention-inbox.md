# Attention inbox

**Work's hooks ride with the Claudes work starts, never the user's settings** (`SESSION_HOOKS`, `core/agents/session-hooks.ts`): one per turn edge — UserPromptSubmit → `work hook turn-start`, Stop → `work hook turn-end` (`runTurnHook`: pending comments for Claude first, then the checkpoint nudge and the status record, side by side — one `work` start per turn edge instead of three) — plus Notification → `work hook status-notify`, and the status line (Usage, below). Claude's are a settings file of work's own, `~/.work/claude-settings.json` (`agents/claude/session-settings.ts`), handed to each Claude work starts as `claude --settings <it>` (`AgentLaunch.sessionTool`, `sessionToolFor`): put in the spec itself (`spawnSpecFor`, `assistantSpec`: a PTY host from before this build — it outlives updates — starts them with it too; the dev server names the file the installed work wrote, `write: false`), applied again by a current host at every spawn, restore and restart (`PtyRegistry`, so a restore entry from before gets it; never twice), and by `work tree --no-host` / `resume` / `recent`; Claude Code adds hooks from it to the user's and the project's (measured). Every command names the work that wrote the file by its path (`workCommand`, `core/platform/work-command.ts`: node and its `bin.js`, or the desktop app's `~/.work/bin/work` launcher for its runtime copy; never a bare `work`), rewritten when it changed. § Reported: work web wrote them into `~/.claude/settings.json` (often a dotfiles symlink) and each account's, so every Claude on the machine ran them with whatever `work` its PATH found — an old `npm link` that knew no `turn-end` printed its usage as a Stop hook error on every turn of another project's Claude. Now nothing is written there for good; work web's start (lean too) takes out what older builds installed (`removeRetiredAgentSetup`, `commands/web.ts`: `events.removeInstalled(RETIRED_HOOK_OWNERS)` in every account's settings, and the wrapped status line given back), writing only a file that had some. § **An update loses no turn** (`core/agents/hook-migration.ts`): Claude Code reads its settings live, so a session's Claude started before the update — no `--settings` of its own — would lose its hooks the moment they went. While one runs (`agentsOnOldHooks`: in a work session, started before this work web — `LiveAgent.startedAt` — or run by the PTY host whenever it started (`ptyPids`: an older host restarting an entry it kept starts it again with no flag), its command line, `listProcesses`, without `--settings <claude-settings.json>`, `startedWithSessionHooks`; one that can't be read counts as old) the hooks stay as `events.bridge` writes them: the session file's commands word for word, under the retired owners (`BRIDGE_OWNER`), so the old Claude runs the right build and a new one, seeing the same handler twice, runs it once. Looked at every 2 minutes (`HOOK_MIGRATION_EVERY_MS`) until every agent's are `removed`; idle sleep and a current host's restarts give those Claudes their own (with a host from before, `work pty-host --restart` ends the bridge sooner; until then the bridged hooks run the right build). A Claude started by hand in a worktree runs none of them: its status still comes from Claude Code's own state and the transcript (below), but no comment delivery or per-turn checkpoint. The status part maps the cwd to a session (`findSessionForCwd`, group-root aware), apply the event (`applyStatusEvent`: prompt → working+seen; stop → idle+unseen with the transcript's last assistant line; a Notification matching `permission|approval` → needs_input) to state.db `session_status`, then nudge `POST /api/status-changed`. The server notifies only on a real transition (`notifyKindForTransition`) and broadcasts `sessions-changed`. Where it notifies follows presence (`server/presence.ts`): each dashboard tab POSTs `/api/presence` (session shown, visible, focused, may notify) on change + a 15 s heartbeat (45 s TTL, `sendBeacon` goodbye). A focused tab on that session → nothing; a tab that can notify → SSE `notify` (browser Notification, click-to-jump, `use-presence.ts`); otherwise the desktop toast. `statusHooks` always run. Read-side `effectiveStatus` decays a 15-min-quiet "working" to idle and treats transcript activity after a permission prompt as answered (no hook fires on approve), and an idle session whose transcript has a turn's message (yours, a `!` command or its output, Claude's, a tool result — `lastTurnEntryMs`, not Claude Code's own durations/away summaries/PR links) after its last turn ended (`turnEndedAt`, set by Stop) as working: `!` commands and Claude's turn on their output fire no prompt hook, so such a session read grey while it worked. `sessionStatusView` (`core/status/turn-activity.ts`) is what every caller uses; it reads the transcript tail only when it was written after the turn ended, cached by size + mtime. Opening a finished session marks it seen. Inbox order (`core/status/attention.ts` `inboxRank`/`compareInbox`): needs input (oldest first) → done-unseen (oldest first) → needs you (what it owes you: replies to post, review threads, its PR) → working (newest first) → quiet. The Inbox page (`InboxTab`) lists only the first three, one row each with one action (Allow / Deny, Review, Open; Snooze, Mark seen and Terminal on hover), and ends with one line on the rest (`inboxRestParts`: "1 working, 3 quiet, 2 snoozed — they're in the list on the left."); working, snoozed and waiting sessions are the rail's, and "2 snoozed" / "1 waiting on others" open a short list (until when, with Unsnooze; what each waits on). **Review comments**: a session whose open PRs have unresolved review threads whose last word isn't yours (the PR watch's `openThreads`, summed into `SessionWire.openReviewThreads` by `reviewThreadsOf`) is one of the things it owes you (`owedToYou`, its pink badge: "2 threads"), as are reply drafts to post (`SessionWire.replyDrafts`); either puts it in the Inbox's **Needs you** section (`inboxRank` 2, `owedInInbox`, whatever its Claude is doing — its row's icon says that) and the badge (`wantsYou`), until they're answered or posted. A change in that count broadcasts `sessions-changed`.

**Notes are handed over whenever a hook fires** (reported: a session's first message said notes were attached and they came a turn later): `computeHookOutput` used to return nothing when the session's conversation file hadn't been written in the last five minutes, or wasn't there yet — every nudge into a quiet Claude and every new session's first prompt — so the notes went out at that turn's Stop. The hook firing is itself an agent in the folder: there is no such check now.

**What corrects the hooks** (an audit found each of these wrong once):
- **Claude Code's own state wins when newer** (`withLiveClaude`, `core/status/session-status.ts`): every running Claude writes `~/.claude/sessions/<pid>.json` with `status: busy|idle|waiting` (+ `waitingFor`, `statusUpdatedAt`; read by `live-agents.ts`). Busy → working, waiting → needs input, idle ends a working / needs-input record — the hooks miss turns (a work web restart, an Esc, a Stop that handed Claude more work), that file doesn't. With no Claude running for a session anywhere (process list read, no PTY of ours), working / needs input is over at once. One case runs the other way: a turn that ended (Stop: idle) while Claude Code stays busy, with a background agent it started writing since (`conversation.backgroundWorkSince`: Claude's `<conversation>/subagents/agent-*.jsonl` written after the turn's end, its `.meta.json` saying `requestShape: "background"`), handed its work to that agent and reads working (shown as **In background**, with what the agent is); the agent's end comes back as a new turn. One started for the turn (its meta written in the minute before the turn ended) counts before its first write after, and one quiet for 60 minutes (`AGENT_QUIET_MS`) is taken as done — Claude Code saying busy is still required. **A background command** (reported: two sessions running tests in the background read Idle): Claude Code's state `shell` — no turn, its prompt free, a command it started with `run_in_background` (a build, tests, a dev server) still running — keeps the state idle (so Done and the "review" badge still work; newer than a working / needs-input record, that turn is over) and marks it `background: { what, command: true }`, shown as **In background** too (`displayStatus`: an idle row with the mark, never Idle or Asleep); `what` names the newest one by its description, else its command's first line, "and N more" (`backgroundCommandNames`, `openBackgroundCommandInfo`, `agents/claude/background-commands.ts`: the transcript tail's answer kept per file size and mtime, since the session list asks while it runs). Idle sleep stays away on that word alone, and `summarizeAgents` ranks it between waiting and idle.
- **Notifications by `notification_type`**: `permission_prompt` / `elicitation_dialog` → needs input; `idle_prompt` (a minute after it stopped, with no Stop: an interrupt) ends a working / needs-input record, seen. The message regex is only the fallback.
- **A Stop that delivered comments** (`decision: block`) records `continue` (still working), not a false "Done"; the real Stop comes later. A Stop always starts its own `since`, and one with no prompt hook before it is stored with `prevState: working`, so you are notified.
- **"Answered"** (needs input → working) counts only a turn's transcript entry (`lastTurnEntryMs`: not slash-command echoes, compaction, away summaries or exit lines), and decays after 15 min like working.
- **Seen** only while the window is visible and focused (`useLooking`, `DashboardApp.tsx`).
- **Two sessions on one folder**: `findSessionForCwd` picks the non-archived one, then the one whose branch is checked out, then the latest — not the oldest.

**Getting a status on screen, always.** Three independent paths, so none gates it:
- **The hook's nudge**: `POST /api/status-changed`, which broadcasts `sessions-changed` FIRST and does its bookkeeping (diff stats, scope, conversation copy) after replying (`setImmediate`).
- **The change counter**: `session_status` writes bump `rev:sessions` (db triggers, schema v3), and the 1 s poll broadcasts even when no nudge arrived.
- **File watches**: transcripts and `~/.claude/sessions` (Claude Code's own state). Plus the 10 s tick for time-based changes.

Every broadcast drops the sessions cache. The SPA refetches at most 400 ms after the first event of a burst (`coalesce` throttles: a debounce kept the list stale while any Claude wrote), and again whenever its event stream (re)connects. `watchLoop` (`server/loop-watch.ts`) reports a blocked event loop (≥ 1 s) with the slowest request, in the log and the Activity panel (`server`) — and with the slowest synchronous command the server ran itself in that window ("; it ran: git worktree remove … (23.8 s)"; `core/platform/sync-work.ts`: the sync spawn wrapper and the process listing note what they ran and how long, `timedSync` / `noteSyncWork`, taken every window so one from a quiet window is never blamed later; reported: 105 of a day's 126 stalls had no slow request, so nothing said what blocked).

§ Keep `/api/sessions` and `/api/status-changed` free of slow synchronous work: everything, statuses included, waits behind a blocked loop.

§ WHEN adding an attention state or signal, extend `applyStatusEvent`/`effectiveStatus` and `core/status/attention.ts` — the SPA imports the latter directly, so keep it free of imports.

**In review (the PR's stage).** Where a session's pull request stands, in a word and a line (`core/pr/pr-stage.ts`, pure, shared with the SPA and the demo): `prStageOf` over the PR watch's last check (`gh pr view` also reads `reviewDecision`, `ShipPr.reviewDecision`), the most pressing open PR of a group — conflict, checks failing, changes requested, draft, waiting for review, checks running, approved (behind or blocked), ready (approved, checks passing, nothing blocks the merge; only when every open PR is), merged. Across branches (session-branches.ts: Claude moved on after a PR merged): per repo the stage reads the newest OPEN PR of the checked-out branch and the other recorded ones (`stageRepos`: else the checked-out branch's own, whatever its state — never another branch's merged or closed one: a repo's own checkout on main read "PR #55 · merged" from a branch it was on a month before), so the new PR shows instead of the old merged one; the others are `earlier` — folded under it in the PR tab ("earlier · feat/x"), out of the rail's pills, those merged over `EARLIER_SHOWN_MS` (30 days) ago left out. `SessionWire.prStage` (`prStageWire`, `session-wire.ts`) carries it with its `key` (the stage and each PR's head) and `seen`. A PR waiting on others (`STAGE_WAITING`) says "in review" quietly in the rail's slot (`waitingOnOthers`) and keeps it out of the Inbox (the closing line counts it); one that wants you (`STAGE_WANTS_YOU`: ready to merge, a conflict, failing checks) is in its pink badge ("merge", "conflict", "CI") for as long as it stands, and in the Inbox's Needs you section (`prWantsYou`) and the badge until you open it or Mark seen at that stage (`POST …/seen {prStage}` → `pr_watch_seen` key `stage:<key>`; a new head or stage brings it back). The PR watch's broadcast compares each check with the last (`createStageTracker`, `stageNews`): a change shows (`sessions-changed`), and moving into a wanting stage notifies (kind `pr`) — never the first sight after a start. A snooze "until it changes" includes a wanting stage's key (`statusKey`). The session header shows a pill per PR (`PrStageChip`, each with its own stage — `PrStage.prs[].kind` — and linked to its PR: "#212 · waiting for review", a group's "backend #12 · ready to merge") in place of the plain PR numbers; the rail shows them as pills too, and its tooltip the line. ⋯ → Send a prompt… has **Open a pull request** (title and description from the conversation, the Jira key, ready for review) beside **Review your changes**.

**Snooze.** "Not now" for a session that wants you (`core/rail/snooze.ts`, pure; per session in state.db `session_snooze`, schema v5, purged with the session): 2 hours, until tomorrow 9:00 (this morning when it's still before 6), until a time of your choosing (Snooze until…, `SnoozeUntilDialog`; typed as `work snooze --until` takes it: `parseWhen`, at most 30 days ahead, `snoozeUntil`), or until its status changes (`statusKey`: Claude's state + since, and the waiting review threads). While it holds (`snoozeActive`, applied in `sessionWire` → `SessionWire.snoozed`), `inboxRank` puts it in a last section of its own (6), so it leaves the Inbox, its count, `n` and Review all; a timed one also holds its notifications. From the rail's right-click menu (and a Sessions row's ⋯) and Snooze on each Inbox row (on hover) (`POST`/`DELETE /api/sessions/:id/snooze`).

**Review queue.** "Review all" on the inbox's Done section walks the finished, unseen sessions one by one (`state/review-queue.ts`). The order is fixed when the queue starts, since opening a session marks it seen and would otherwise reshuffle the rest. Each opens on its **Last turn** diff (`DiffView startOnLastTurn`, applied once per session), a done row opened from the inbox does too, and `n` means "next in the queue" while you're in it (`ReviewQueueBar`).

**Kept conversations + search.** Claude Code deletes its transcripts after `cleanupPeriodDays` (30 by default); work keeps its own copy in `~/.work/conversations/<session id>/` (`core/conversations/conversation-store.ts`) for as long as the session exists, so "what did we do about X?" reaches back as far as you like. Disk only — nothing of it is held in memory. A transcript only grows, so a sync copies just the new bytes, written at the source's own offsets (two syncs at once — a turn's and the sweep's, or `work search` beside work web — write the same bytes to the same place); a source smaller than the copy was replaced and is copied whole; a copy is never deleted when its source goes. Syncs: a session 5 s after its status hook (`onStatusChanged`), and every live session a minute after start and every 30 minutes (Activity panel, kind `conversations`). Archived sessions aren't synced (their Claude is stopped; the archive has the rest). `searchConversations`: every word in one message (yours or Claude's) or an archive's written summary; an archived session reads its archive first (from before the store too), a live one its copy, each falling back to the other; most recently active first, 20 sessions, 3 snippets each. The Sessions tab shows hits while you filter ("In conversations": open, or Restore an archived one). A copy whose conversation has been quiet two days is gzipped by the sweep (`compressQuietCopies`, `PACK_QUIET_MS`; about tenfold), keeping its time; search reads `.gz`, and a sync whose source went on unpacks it first. The folder goes with the session on delete (`sessionStatePaths`).

**Overlap warning.** Two live sessions that change the same file of the same repository will conflict when the second merges; the dashboard says so while both are in progress ("⚠ Same files as chore/deps-update", in the session header; a ⚠ with the files on hover in the Sessions table). The diff-stat cache's background pass (`computeChanges`, `core/diff/diff-stat.ts`) also collects each repo's touched files since the fork from `origin/HEAD` (committed + uncommitted + untracked), keyed by `--git-common-dir` so every worktree of a repo shares one key. `/api/sessions` pairs them with the pure `findOverlaps` (`core/diff/overlap.ts`), which costs no git of its own. The demo uses the same function on its diffs.

**Context per session.** "Context 62%" in the session header's ⋯ menu (and in the header from 70%; "84% full" beside the name in the Sessions table, only past 70%): how full the session's Claude conversation is, from the newest main-thread assistant message's `usage` in its newest transcript (prompt = input + cache reads + cache writes, plus the reply; `core/conversations/context-usage.ts`). The window is 200k, or 1M for a `[1m]` model id, a model with 1M as it comes (Opus 5: `claude-opus-5-5` at 190k is 19%, as Claude Code's own line says — not 96%), or usage past 200k (`claudeContextWindow`). It re-reads a transcript's 64 KB tail only when its size/mtime changed. Amber from 70% and red from 90%, with a hint to start fresh. Token counts only: cost is left out because prices aren't in the transcript.

**Answering permission prompts from the inbox.** The Notification hook stores the tool call the prompt is about (`request`: the transcript's newest unanswered `tool_use`, `agents/claude/permission.ts`), and the inbox shows it (`Bash npm test`) with Allow / Deny for sessions running in the PTY host. `POST /api/sessions/:id/answer` types Enter (Yes) or Esc (No) into the PTY, and records an `answered` event. § It only types after `checkDialog` passes on the host's plain-text screen (`GET /ptys/:id/screen`, `PtySession.screenText`): the permission dialog is showing, it is about the request the user was shown (command start or file name), and "1. Yes" is highlighted. Otherwise it refuses with the reason and types nothing. Keep that check in front of any new keystroke path. The screen route is additive, so there's no protocol bump: an older host answers 404, which shows as "answer it in its terminal".

**Follow up from the Inbox** (asked for: the Inbox said a session was done, and the only way to say "now also do X" was to open it): a Done row has **Follow up** beside Mark seen and Snooze. It opens a panel under the row (`InboxFollowUp`, one at a time): what its agent last said, in full and rendered (`GET …/last-reply`, the row itself shows only that reply's first line), and a box for your words — Enter sends, Shift+Enter adds a line, Esc closes. Send goes the way a prompt from the session's menu does (`sendPromptToSession`: a published general comment, typed into a terminal the dashboard owns or delivered on its next turn, never over what is in its prompt box), then the row is marked seen; a send that fails says why and keeps your words.

**A session's own review, finished** (asked for: a review takes minutes, you start it and go elsewhere, and nothing said it was done): a review that became ready — or couldn't be prepared — and that you haven't looked at is something the session owes you, a new `OwedKind` `review` (`reviewWantsYou`, `owedInInbox`), so it reads the same everywhere the owed list is read: the Inbox's **Needs you** section (its row says the review's line — "Review ready: Fix first · 3 stories · 7 notes", `localReviewLine` — opens on the Review tab, and has its own Mark seen), the rail's badge ("review ready"), the Inbox count. The session's row carries it (`SessionWire.localReview`: status, seen, line; `createLocalReviews.row`, which reads a stored review once and keeps only its line — the sessions list asks often and a stored review is large). The Review tab's button says "preparing…" while it runs and "ready" / "failed" until you look (`reviewTabMeta`). § It is seen when the Review tab shows it, or by Mark seen: `POST /api/sessions/:id/review/seen` — a POST, never the GET that reads it (§1.5). `seen` is kept with the stored review; one kept from before it was recorded counts as seen, so an update announces nothing old. A finish also sends a `notify` event of kind `review` ("<session>: review ready"), whose click opens the Review tab. One being prepared wants nothing of you. Pull request reviews are not announced this way: they are prepared for every open PR, and a row each would be noise.
