# Git hosts (`core/hosts/`: GitHub and Azure DevOps)

work talks to where a repo's pull requests live through a `GitHost` (`hosts/types.ts`), the way it talks to an agent through an `AgentAdapter`. Two are built in: GitHub's (`hosts/github/adapter.ts`, over `gh` and the user's `gh auth login`) and Azure DevOps' (below); `registerHost` adds one (the fake-host suite's). **A repo's host is its origin's** (`hostForRepo(path)` → `hostForOrigin`: config `gitHosts` names the host of an origin's hostname no adapter claims by its URL — for a host that can work with such a server, e.g. one registered at run time; GitHub Enterprise needs none: an unclaimed origin is asked as GitHub; `gh pr …` and `gh repo …` follow the repo's folder, `gh api` needs `--hostname`, which work passes (`ghApi`, `hosts/github/server.ts`: below), its PRs listed per repo (the one search is github.com's) —, else the adapter whose `matches(origin)` claims it, else the default, GitHub, as before hosts: `gh` itself says whether it knows the repo). A group's repos resolve one by one, so a group can mix hosts. What goes through it: the PR list (`fetchAllPullRequests` groups repos by host, each host's `list`; GitHub's is the one GraphQL search plus `gh pr list` elsewhere, `hosts/github/pr-list.ts`), a branch's PR for Ship and the PR watch (`prForBranch` → `PrLookup`), create, merge with the head guard, a PR by number (Start from a PR), a PR's state (Blocked by: `blockedPrState`), a gone branch's merged PR (branch tidy), review feedback, a PR's whole discussion for the Reviews tab (`discussion`: threads with side, place, outdated and resolved and every comment, submitted reviews, conversation comments — read only; GitHub's one GraphQL query in `hosts/github/review.ts`, Azure DevOps' threads and reviewer votes through two `az devops invoke` GETs, `discussionOf`; cut by `core/hosts/discussion.ts`), who you are (`viewer`, per host: the watch asks each host its repos are on), review threads (`threads.now/live/isResolved/reply/resolve`, a thread routed by its id's shape — `hostOfThread`; `isThreadId` takes every host's), rate-limit words (`rateLimited`: the watch rests on the host that refused), commits a host wrote itself (`hostCommit`: left out of a day's work), and the CLI Welcome checks (`cli`). The wire keeps its shape, in GitHub's vocabulary (`mergeStateStatus: 'DIRTY'`, `reviewDecision`): another host maps its words onto it. A `host` field says where a PR or repo is (`PullRequestInfo`, `RepoShipState`, `SessionCi.repos[]`, `PrToStart`) — **absent for GitHub**, so a row from before hosts and a GitHub one read the same. Who you are is asked of each repo's own host (`prWatchHostDeps`, `core/pr/pr-watch-hosts.ts`, what ci-routes wires: `viewerLogin` per host id and origin server, asked in the repo's folder — on a GitHub Enterprise server its login isn't github.com's —, review feedback, API-limit words; each repo's login is on its check, `SessionCi.repos[].viewer`, which the PR tab tells yours by — `SessionCi.viewer` is one repo's, kept for older readers). **Which GitHub server** a repo is on is asked of gh, never guessed from the name (`githubServerArgs`, `hosts/github/server.ts`: `gh repo view --json url` in the repo — gh resolves SSH aliases through `~/.ssh/config` and only to a host it's signed in to; an origin naming github.com isn't asked; cached per folder and origin, a failed lookup for 5 min), and every `gh api` call of the adapter goes through it (`ghApi`: who you are, the review read, thread read / reply / resolve, a review, a GitHub Enterprise list's "mine"): `--hostname <server>` off github.com, so a dotted alias of github.com (`git@github.com-work:`) is github.com and a dotless GHE host (`ghe`) is itself; a server that can't be told asks nothing (a review then is refused as never sent, not held in doubt). Two github.com accounts behind two aliases both read as gh's active one (their PRs then read as theirs: the safe way), so the PR watch (`pr-watch.ts`) imports no host and stays pure for the demo; a host that can't say who you are leaves its PRs neither yours nor theirs — nothing of them goes to Claude until it can tell (review threads, failing checks and conflicts are held, each said in Activity as a warning), unless the review read itself says who you are (its own `viewer`, asked on the repo's server), which settles it: yours, or theirs (shown, never handed over). GitHub's read answers nothing without a viewer, so there a repo whose viewer is unknown stays held, said in Activity; with review comments off, or a PR not open, nothing settles it. **What agents are told** comes from the host too: `commandsFor(host)` (`hosts/commands.ts`, pure, with each host's table — `hosts/github/commands.ts`) gives a PR's view / diff / checks / checkout / create commands and the host's name, for the PR watch's CI and review notes, `workOnPrPrompt`, Start's `prPrompt` (SPA); the default prompts and the assistant's instructions name no host. Pure readers the SPA shares: `hosts/links.ts` (`parsePrLink`, `threadHostId`) and `hostName`. Not behind it: work's own updates (`core/updates/`), which are where work is published.

**Azure DevOps** (`hosts/azure/`, #65): over the `az` CLI with the azure-devops extension and the user's own `az login` (argv only; nothing stored). `origin.ts` (pure: the `dev.azure.com`, `visualstudio.com` and SSH origins → `org/project/repo`; PR links `…/_git/<repo>/pullrequest/<id>`; thread ids that carry where they are, `AZT_<org/project/repo, base64url>_<pr>_<thread>`, since Azure DevOps numbers threads per PR — read back only when the org URL is `https://dev.azure.com/<org>` or `https://<org>.visualstudio.com` and the id round-trips as an origin, and `threads.repoOf` names its repo so `liveOpenThread` refuses one not on the session's repos before `az` is asked anything; org, project and repo names are held to Azure DevOps' own rules plus no `% & ^ !`, `azureNameOk`, else the origin isn't Azure DevOps'), `map.ts` (pure: its JSON in work's words — votes 10 / 5 approve, −5 / −10 ask for changes, required reviewers must all approve; build policies are the checks; `mergeStatus: conflicts` → `DIRTY`, a blocking policy not met, `failure` or `rejectedByPolicy` → `BLOCKED`, `queued` / `notSet` → `UNKNOWN`; an open PR has no `updatedAt` (its creation date never moves, and the PR watch would believe its threads unchanged for good), so its threads are read every check; active / completed / abandoned → OPEN / MERGED / CLOSED; threads fixed / closed / wontFix / byDesign are resolved; Azure's system comments left out; a commenter counts as `MEMBER`: Azure DevOps has no association, and only the organisation can comment), `adapter.ts` (`az repos pr list / show`, `az repos pr policy list` — a failed one is an error, never a clean PR with no checks —, `az account show` for who you are — unknown, a repo's list is incomplete, never empty; through `az devops invoke` — the REST API as you — creating a PR (title and description in the body, into the repo's default branch), threads, replies, resolve, a review comment as a new thread on the line at the iteration whose source commit the review read (`iterationAt`; none: nothing posted), and the merge, completed with `lastMergeSourceCommit` so Azure DevOps refuses it when the PR moved: the head guard; merged only when its answer says `completed` — a queued completion is said, not counted; free text only ever goes through a temp `--in-file`, route values are checked (`routeValueOk`), and az's reason is its first line that isn't a WARNING, the throttling one wherever it is (`azReason`); `prByNumber` refuses an answer from another repo: Azure DevOps numbers PRs per organisation). **On Windows `az` is `az.cmd`**, a batch file cmd.exe would parse twice (a `"` with `&` ran a command; a line break cut the arguments): the runner starts its Python directly (`launchFor`, `core/platform/batch-launch.ts`: a batch file whose `"%~dp0…python.exe" -IBm <module> %*` line is carried over — only that line: az.cmd's `SET AZ_INSTALLER=MSI`, which only records how az was installed, doesn't run), by its full path on PATH (never the working folder), and refuses cmd.exe's special characters for any other batch file. Welcome checks the azure-devops extension (`az extension show --name azure-devops`, the host's `cli.requires`) before `az account show`, which passes without it. A PR's code is `refs/pull/<id>/merge` (its first parent the target, its second the PR's head, `prRefIsMerge`): a review reads and comments at the head. Its list says nothing of size, so the review queue's size limit applies only after a fetch. Throttling (`TF400733`, 429) rests Azure DevOps in the watch like GitHub's limit (only that host). Welcome lists `az` only when a repo is on Azure DevOps. `tests/core/hosts/azure.test.ts` drives Ship, the PR list, the PR watch, reply drafts, blockers and Start from a PR through it on a real repo, `az` answered from hand-made fixtures. The demo's `payments` repo is on Azure DevOps.

§ Nothing outside `core/hosts/github/` runs `gh` (`gh.exe`, by its path too) or reads or writes a github.com URL, nothing outside `core/hosts/azure/` runs `az` or names Azure DevOps' addresses (each host folder — any folder under `core/hosts/` with an `adapter.ts`, found by the test — must have its words listed there), nothing but the registry (`hosts/index.ts`, `commands.ts`, `links.ts`) imports a host's own folder, statically or by `import()`, a host's folder never imports another's, and nothing every session is told by default (the assistant, the saved prompts, the skills) names a host (`tests/architecture/hosts.test.ts`, reading whole files through `tests/architecture/source-scan.ts`: a wrapped call, an escaped `github\.com` (or `github\\.com` in a string), a dynamic `import()` and JSX text in a .tsx file count; work's own updates and the demo's made-up world are the listed exceptions). The demo's and the SPA's pure imports are checked all the way down (`loadedBy`), not one level. WHEN adding something that asks a host, add it to `GitHost` and GitHub's adapter, and to the fake host in `tests/core/hosts/fake-host.test.ts` — which drives the PR list, Ship, the PR watch and its stage, reply drafts, blockers and Start from a PR through a made-up host, and a group on two hosts, with no GitHub anywhere.
