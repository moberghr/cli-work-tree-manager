# PR watch (CI strip, fix-CI, auto-archive)

`core/pr/pr-watch.ts` is pure policy with injected I/O; `server/routes/ci-routes.ts` wires it (sessions = not archived, touched in 30 days, path exists; `shipPreflight` for facts; `tell` = POST a published general comment, so delivery reuses the comment path; told-keys in state.db `pr_watch_seen`, per session). `work web` full mode sweeps every 180 s, 3 at a time, single-flight. § GitHub allows 5000 API points an hour and work shares them with your own `gh`: when gh answers "rate limit" (`RATE_LIMITED`) the watch keeps the last state (never "no PR"), acts on nothing and asks that host nothing for 10 min — per host: a session on another host is checked as ever (a resting host's repos aren't asked, `preflight`'s `resting`, and a session with one keeps its last check); the sweep itself rests only when every session is on a resting host; a failed review lookup keeps the last count for that PR. `/api/prs` is one shared `createSharedFetch` (`server/shared-fetch.ts`, 2 min, stale-while-revalidate) for every window — per-request `gh pr list` over every repo, on each window's interval and each sessions change, spent the whole limit. And it is ONE GraphQL search (`fetchAllPullRequests`, `core/pr/pr.ts`: `PR_SEARCH_QUERY`, about one point): your open PRs and those asking your review by name, mapped to aliases by each repo's origin (`githubRepoOf`); a repo not on github.com (or every repo, when the search fails) is listed the old way, `gh pr list` there. Per sweep the watch asks gh only about repos whose branch was pushed (or that had a PR it knows of: `askGh`, `shipPreflight`), re-reads a PR's review threads when its `updatedAt` moved, or after `THREADS_RECHECK_MS` (10 min) while some are open (resolving a thread doesn't move `updatedAt`, and a thread resolved on GitHub stayed open here), and runs one check per session at a time (a refresh joins the sweep's). Someone else's PR (`ShipPr.author` ≠ you, `viewerLogin`: one `gh api user` per server) — a session working on it or reviewing it — is only watched: its threads are its author's (not counted, not handed over) and its failing checks aren't sent to Claude unasked. It tells Claude once per `session:repo:headSha` when checks fail, and when a PR turns conflicting (GitHub's `DIRTY`; `conflictMessage`, keyed `session:repo:conflict:headSha`, so a push that conflicts again is told again; config `prWatch.fixConflicts: false` opts out): merge `origin/<base>` in (`ShipPr.baseBranch`, gh's `baseRefName`) — a merge, never a rebase or force push, since the branch is pushed — resolve, build and test, push; a conflict that takes a choice is `git merge --abort` and `DECISION NEEDED`. Someone else's PR is theirs, as its CI is. It archives (`archiveSession`: conversation kept, worktree removed when safe) — never a session on a repo's own checkout (`ownCheckout`: you go on working there after its PR merges), nor one you asked to keep (`WorktreeSession.keepAfterMerge`: right-click → **Keep after its PR merges**, `work keep`, `POST /api/sessions/:id/keep {keep}` → `setSessionKeep`, `history.ts`; reported: a session was archived before the release it was to make after its merge; Activity says `KEPT_ON_REQUEST`; Ship's merge leaves it too; `SessionWire.keepAfterMerge`, the rail tooltip's "kept after its PR merges"; it stays until you turn it off — **Archive after its PR merges** — or archive it yourself; **a Restore of a session archived for its merge sets it** (`archivedForMerge`: archived by the PR watch or Ship's merge, `ship-routes.ts`), and any Restore counts as entering it (`setSessionArchived` moves `lastAccessedAt`: un-archiving a session whose folder was kept didn't, so the next sweep read its PR as merged after you last entered and archived it again — reported); the rows show a dashed **keep** mark (`KEEP_TITLE`, the rail's second line and the Sessions table)) — when every repo is `done` — or merged at the checked-out commit with only uncommitted files left, which the archive saves for Restore (`archivable`; unpushed commits or another commit checked out still keep it, and the Activity note says which) — and its Claude isn't working or waiting for you, and a merged PR is this work — it merged after the session was last entered, or its head is the checked-out commit and the session has been left alone a day since it was entered (a Restore or `work tree` onto the merged tip isn't re-archived at once; `shouldAutoArchive`: `gh pr view <branch>` also returns a PR merged long ago for a reused branch name, which has another head). Keys are recorded only after the note was delivered (`tellThenRecord`), so a failed send is retried. `GET /api/sessions/:id/ci` (cached, refreshed after 60 s) and `POST …/ci/fix` feed the PR tab's sections (`PrTab`). Ask Claude to fix sends the PR it was clicked on (`{url}`, `clickedPrUrl`; `fixNow(id, url)`): that PR only, whoever opened it — you asked; with none (an older dashboard), only your own failing PRs (`yoursIn`), never someone else's. What it has acted on (CI heads, review comments, baselines) is kept per session in state.db `pr_watch_seen` (`core/pr/pr-watch-store.ts`, removed with the session), and its last check of each session in `pr_watch_state` (schema v10, `createCiStore`, shape-checked by `isSessionCi`): read once when the watch is made, written when a check changes what it knew, so a restarted work web shows each session's PRs at once instead of after its first sweep reaches it (15 s, then three sessions at a time). Review feedback rides the same sweep: `core/pr/pr-review.ts` fetches threads (with `isResolved`), reviews and conversation comments in one `gh api graphql` call (`{owner}`/`{repo}` filled by gh from the cwd). `newFeedback` raises unresolved threads whose last comment isn't yours, keyed by that comment, and reviews/comments by others posted after the PR was first seen (a baseline, so old discussion isn't replayed). They go to Claude as one note. When the conversation is past `CONTEXT_WARN` (70%, `readContextUsage`) the review and CI notes end with `subAgentHint`: hand the mechanical fixes to a sub-agent, keep decisions and reply drafts in the main conversation (the note stays with the branch's own Claude, which remembers why the code is as it is). Trusted: reviewers with write access (`TRUSTED_ASSOCIATIONS`), plus the review bots in config `prWatch.trustedBots` (default `DEFAULT_TRUSTED_BOTS`: `copilot-pull-request-reviewer`, `github-actions`; GitHub gives bots no association, so they were never sent before). **Automated review**: each thread in the note carries its id (`[thread PRRT_…]`), and the PR watch records it (`rememberSent`, state.db `pr_replies`, `core/pr/pr-replies.ts`); `work pr reply` also takes a thread the watch's last check lists open for the session (Ask Claude to reply hands one over as a plain note), and failing both, the thread as GitHub has it now (`draftReply` → `liveOpenThread`: on an open PR of this session — its repo, from the branch a checkout of it has — not resolved, its last word not yours; the same rule as the watch's list, so a reply is never stuck on a stale check) — and one answered before and open again since starts over. The watch looks at a session used in the last 30 days: entered with `work tree` or its agent wrote (`watchable`; entry alone dropped a session worked in daily from the dashboard). If the session's Claude isn't running anywhere, it is started in the PTY host with `WAKE_PROMPT`, resuming its conversation, and the UserPromptSubmit hook attaches the note (`wakeForNote`, `ci-routes.ts`; config `prWatch.wakeClaude: false` turns it off) — CI-fix notes wake it too. Claude plans, changing nothing (a reviewer can be wrong): per thread, what it would change or why it would leave it, and a reply drafted with `work pr reply` as it will read once done (`reviewMessage`; its instructions come before the quotes, so a long round's cut can only lose quotes — a 4 KB cap once cut them, and Claude drafted in the chat). Once you say yes in the conversation it makes the agreed changes, commits, pushes and posts the replies itself with `work pr post <thread…>` (resolving each; `--no-resolve` leaves it open) (`postDrafts`: the drafts as they stand, your dashboard edits included). The PR tab (`PrTab`, each PR's section: `useReplies` + `ReplyList`) shows each draft under the reviewer's comment, editable, with Post & resolve / Post / Discard; open threads with no draft are listed under it too (`GET …/replies` → `waiting`: the PR watch keeps each open thread, `SessionCi.repos[].threads` from `openThreadsOf`, minus the drafted ones), with the comment, a link, and Ask Claude to reply (a published note asking for a plan and a `work pr reply` draft, nothing changed); more than two fold under their heading, with one Ask Claude about all N (`askToReplyAllPrompt`), so an "unresolved review comment" count always has something to open (`POST /api/sessions/:id/replies/:thread/post` → `gh api graphql` addPullRequestReviewThreadReply (+ resolveReviewThread), `-f` raw strings, argv only). Right before posting, `postReply` reads the thread as GitHub has it now (`threadRefusal`: one `gh api graphql`) and refuses when its last word is already yours — a reply would answer yourself (reported: a PR author's Claude answered his own comment) — or it was resolved since, or GitHub can't say; and who you are unknown (`viewer` empty) hands nothing over (`newFeedback`, `openThreadsOf`). § Anything on GitHub is in your name, so a reply goes out only on your yes: your Post click, or Claude's `work pr post` after you agreed in the conversation — told so by the note, and never pre-allowed (not on `ASSISTANT_ALLOW`), so Claude Code asks you before it runs. Claude writes to GitHub in no other way. A thread raised again (a reviewer answered) starts over. The inbox's Review comments row says how many replies are ready (`SessionWire.replyDrafts`). A turn whose message has a `DECISION NEEDED:` line (`DECISION_MARKER`, `attention.ts`) becomes `needs_input` in `applyStatusEvent`. § Claude is told not to write on GitHub except `work pr post` on your yes; keep it that way, since that's the user's voice.

**Every branch the session worked on** (session-branches.ts): the preflight also looks at each repo's recent other branches (`watchBranchOptions`, `pr-watch-hosts.ts`: last checked out within 30 days, at most `MAX_WATCHED_BRANCHES` (5) per repo, newest first) — their facts (`OtherBranchState`, `RepoShipState.otherBranches`) and, from their host, their PR when pushed now, pushed once (`RecordedBranch.pushed`: origin's copy deleted after a merge), or already known; never a resting host. The check carries `SessionCi.repos[].branch` and `otherPrs` (newest first, `otherPrsOf`, `core/pr/branch-work.ts`, pure), shape-checked in `pr_watch_state`. § A session is never archived — by the watch or by Ship's merge (its preflight with the listed PRs, `shipPreflightWithListed`) — while another branch has commits not pushed, a PR open, or a PR its host couldn't tell of (`workElsewhere`: `autoArchiveVerdict` says which; `mergeSelected`'s `allDone`): a branch whose PR merged at its tip leaves nothing behind. Ship acts on the checked-out branch as before; its dialog lists the other branches' state (`otherBranchFact`).

**A session's PR list** (`core/pr/session-prs.ts`; reported: a branch made, pushed and left within one turn was never recorded, so its PR never showed — nor one Claude opened on the docs repo — and a failing PR on a branch not checked out was never fixed): every PR a session made or worked on, kept in state.db `session_prs` (schema v13, purged with the session; `{prs: [{url, number, repoId, branch?, sources, firstSeen, final?}], scanned?}`, `cleanSessionPrs`). Sources: the agent's conversation (`AgentConversation.prLinks`: Claude Code writes a `pr-link` line for each PR its session makes or looks at, `agents/claude/pr-links.ts`), read from the new lines the conversation copy appends (`syncConversation`, a line split across its 4 MB chunks carried over) and once over the whole kept copy for a session from before (`scanned`); and every PR the watch finds on a branch (`withListedPrs` → `sightings`). The watch's preflight (`watchPreflight`, `pr-watch-hosts.ts`, what ci-routes wires) looks each listed PR its branches didn't find up by its link (`GitHost.prForRef`: `gh pr view <url>`; Azure DevOps `az repos pr show --id` on the link's org, refused when #N is another repo's) — in its repo (`RepoShipState.listedPrs`, read as `otherPrs` by `otherPrsOf`) or, when the session doesn't have the repo, `ShipPreflight.elsewhere` / `SessionCi.elsewhere` (the stage and the PR tab read it as a repo of its own, `stageInputOf`; labelled "another repo"). A merged or closed one keeps that last look (`final`) and is asked no more; a host that rests or fails keeps the watch's last look, else `unknownPrs` (holds the archive, never read as gone — a resting host with no last look too). **The watch acts on every open PR** (`prsOfPreflight` / `prsOfCheck`): failing CI, conflicts and review feedback for the checked-out branch's PR, the other branches' and listed ones, and those in other repos (no review read there: no folder to read it in); yours or theirs per PR (`prKey`: repo + link). A note about a PR on a branch not checked out names it ("PR #3657 on fix/culture (not checked out: fix/probe is)") and says how to get there (`placeOf`, `placeLines`: stash, `git switch`, push, switch back; another repo: its own checkout); the CI note also says a check failing outside the code (a 5xx, a dead runner) is run again, not fixed. The PR tab shows each PR's branch when its repo has two open (`branchShown`).

**Which failed checks count** (`core/pr/required-checks.ts`; a repo's list is set in its settings, Repos → Settings…): the host's own list wins — GitHub's required checks (`gh pr checks --required`, asked only when a check failed; `blockingChecks`, `pr-ops.ts`), Azure DevOps' blocking build policies (`checksOf`) — marked `ShipPr.checksRequiredByHost`. Where the host requires none, config `prWatch.requiredChecks` (repo alias or `owner/name` → check names, `cleanRequiredChecks`) names them (`countedChecks`, applied in Ship's preflight and to the listed PRs: `withRequiredChecks`); with neither, every check counts. A failed check that doesn't count is `ShipPr.optionalFailing`: not red, not in the Inbox, never asked of Claude, shown grey in the PR tab ("1 optional check failed: …", `OptionalFailing`).
