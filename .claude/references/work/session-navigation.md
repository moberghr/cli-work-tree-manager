# Session navigation (right-click, Ctrl+P, pins, Alt+1…9, fork, stacks, time)

**The top bar** (`TopNav.tsx`) is short: Inbox (its count), Sessions (Now / Today, and Clean up, are its views), Start (Repos & groups under it), Jira; then Tasks (`TasksPanel`: the to-do list in a small panel, `g t` opens and closes it), Ask, the Activity dot, the version (`v2.0.0`, a button: `HelpMenu`, updates, what's new, shortcuts) and the theme. Old `#/tasks` links land on Sessions. The rail is beside every page.

**The Sessions table** (`SessionsTab`) has six columns — Status, Session, Project (the repo or group), Summary, Changes, Active — and no buttons on a live row: the row opens the session, ⋯ on hover (or a right-click) opens the rail's menu for it. **Live · Archived · All** in the header (remembered; `ArchiveScope`, a "Show archived" tick from before reads as All): Archived lists only the archived sessions, none folded, each row with **Restore** — bringing one back is what that list is mostly for; its time column is when each was archived (an archived row's in All too: the last thing that happened to it; its last activity on hover), and its pill says who did it (`ArchiveRecord.archivedBy` → `SessionArchiveInfo.by`, `archivedByOf`, `state/archive-view.ts`: `you` — Archive, its key, the bulk bar —, `shipped` — Ship's merge —, `pr-merged` — the PR watch —, `cleanup`; none on an archive from before it was recorded), as does the session header's archived pill. Filter, rail filter, grouping, sort and Select several are one View ▾ popover; then Clean up and New. Grouped by age, the older sessions are a "Show N older" link (not in Archived), and a heading shows only when two tables do.

**Keyboard shortcuts** (`state/shortcuts.ts`, pure: the one list): `?` shows them all (`ShortcutsHelp`, a popover). Anywhere: `c` New worktree, `n` next that wants you, `j`/`k`, `Alt+1…9`, `Ctrl+P` or `/` (the switcher, one line in the list), `Ctrl+K`, `g i/s/d/w/r/c/t`. On the open session (`SESSION_KEYS`, `sessionActionFor`; Shift matters: `n` is next, `⇧N` Notes): `1`/`2`/`3`/`4`/`5`/`6` its tabs (Terminal, Diff, PR, Code, Branches, Review — its own changes read as a review, see Reviews), `e` Archive / Restore, `z` Snooze… (the snooze items in a menu), `b` Blocked by…, `.` its ⋯ menu, `p` Send a prompt…, `r` Catch me up, `⇧N` Notes, `⇧S` Ship…, `⇧T` Open in a terminal, `⇧R` Reconnect its terminal, `o` editor, `y` copy branch, `f` Fork…, `⇧D` dev server, `⇧Del` Delete…, `F2` Rename; in the diff `]`/`[` comments. `runSessionKey` runs each with the same function as its button (DashboardApp's `menuActions`, the rail menu's); what the header owns (its menu, Ship, notes, prompts, catch-up, terminal, dev server) goes to it as a `work:session-action` event. Menus show each item's key (`hint`). WHEN adding an action, give it a key in `SESSION_KEYS` (a test refuses a key already taken) and its menu item the hint.
§ The keyboard shortcuts stop while a dialog or a menu is up (`modalOpen`, `state/modal-open.ts`: a menu owns the arrows, and a key would act on what's behind it), not for a popover: the Tasks, Activity, legend and shortcuts panels carry `data-popover`, close on Esc or a click elsewhere, and leave the shortcuts working. Mark a new popover so.

**The session page** (`SessionDetail.tsx`) shows little until something matters. Header: one row — its status and how long (`StatusLine` with `summary={false}`: the summary line stays the rail's tooltip and the Sessions table's; reported: nobody read it there), target / branch (and your name for it, never the automatic one), the branches chip, one button — Archive, or Restore — and ⋯ (`state/session-header-menu.ts`, pure: Reconnect terminal, Open in terminal, Ship…, Catch me up, Timeline, Send a prompt…, Notes, Start/Stop dev server, Rename, Delete…; how full the context is at the bottom; an archived session gets only Catch me up, Timeline, Notes, Rename, Delete). Under it, a row only when a chip says something (`.wd-session-strip:empty` hides it) (behind, merged parent, stack, blocked, overlap, two Claudes or one in an outside terminal, context from 70%, PRs, a running dev server, a note, "Away 3d · Catch me up"). What waits on you on GitHub — reply drafts, threads with no reply, failing CI — is one "Needs you" line (`NeedsYouBar`, from the session row: `prNeedsLine`, no fetch) with a button into the PR tab — nothing unfolds over the terminal. Tabs: Terminal, Diff (its file count; opens on Since you looked when Claude finished a turn after your last look; every comment of the session is in its sidebar — every repo's, another repo's labelled and a click switches to it, and with an empty diff the list fills the sidebar (`CommentsPanel`); the general note shows even with nothing changed), PR (`PrTab`, `#/s/<id>/pr`, key 3; there while the session has a PR or anything about one — `prTabButton`: "PR · #212 waiting for review", "PRs · 2", a badge for open threads and failing or conflicting PRs): every pull request of the session, one section each (`prSections`, `state/pr-tab.ts`: each repo's from the PR watch, plus a second PR from the branch only the PR list knows), what wants you first and open, merged ones folded; each with who opened it (`PrSection.author`: the PR watch's `ShipPr.author`, else the list's), its stage, checks (failing ones linked, Ask Claude to fix), Ship…, and its review threads and drafts (`useReplies` + `ReplyList`, one fetch for all); on top one Ask Claude for every trusted thread with no reply across them; no PR yet: Open a pull request (the saved prompt). Code (`CodeView`, `#/s/<id>/code`, key 4): the session's files, read only — the tree of what git lists (tracked, and new files not ignored; a group's repos as folders beside the group folder's own Markdown files — nothing else there: no git says what's ignored), folders folded until opened (`indexFolders`, `state/code-tree.ts`, pure: built once per listing — a repo can have tens of thousands of files), a filter over every file (`filterEntries`: every word in the path; Enter opens the first; its matches as a list or in their folders — List | Tree, per browser), **Changed · N** (only the files changed on the branch, as a tree; with a filter, among them; per session for the page) — a tree of some files has its folders open (`codeSidebar`, `openFolders`), and the open file with its highlighting (none past 8,000 lines), no wrapping. **Open in editor** on the open file's header sends it to config `editor` (`code` by default) through the session's `POST …/open-editor` with `{repo, path, line}`: the server finds it by `codeFilePath` (the same checks as reading it; never a path from the browser) and `editorArgs` (`core/platform/launch.ts`) opens it in the worktree's window at the line you're reading (a Ctrl+T pick's, else the top one on screen) — VS Code and its kin `--goto file:line`, JetBrains `--line N`, Sublime `file:line`, any other editor the file alone. A file changed on the branch (uncommitted, or committed since it left its base) has a dot, a folder the count under it, and the file "Changed on this branch · See the change" (to the Diff). A file Claude changes while it's open is staged, not swapped: "File changed · Reload". The open file and folders are kept per session for the page. `core/worktree/code-browse.ts` (`GET /api/sessions/:id/files`, `GET …/file?repo=&path=`, `code-routes.ts`): git runs off the event loop and a listing is shared for 3 s; a file is read only when the listing has it (nothing outside the worktree, no `..`, no link out, nothing git ignores like `.env`), at most 2 MB, a binary one named not shown. The demo lists each repo's changed files (their new side) and a few every project has (`demo-code.ts`). **Search the code** (Ctrl+T in a session, from any tab — a terminal too, caught in the capture phase; in a browser tab, which keeps Ctrl+T, the Code tab's button), as Visual Studio's: one box (`CodeSearch`, the switcher's look) for types and members by name, files by path, and lines with the text in them, across a group's repos; asked 180 ms after typing stops, an older search aborted (git stops with it); Enter opens the place in the Code tab at its line, marked (`goto`). `GET /api/sessions/:id/code-search?q=` (2 letters at least): text is `git grep -F` over what the Code tab lists (smart case: all lower case = any case; at most `MAX_TEXT_HITS`, 300), names are a declaration index per repo (`core/worktree/code-search.ts`: one `git grep` for lines that may declare something, read by `declarationOf`'s per-language patterns — C# types / members with an access modifier / properties, TS/JS, Python; a fast reading, not a compiler's), kept in memory, prepared once (`prepareSymbols`: names lower-cased and split) and rebuilt in the background a minute after (the old one answers meanwhile). Names match exact, prefix, a word's start, inside, then the starts of its words (`nameScore`, `startsOfParts`: `GPJ`, `AccKeys`, `acckeys`), types before members (`matchSymbols`); the pure half is `code-symbols.ts`, which the demo uses over its files. Measured on a 5,000-file C# repo: a text search ~0.2–0.5 s, the index 0.7 s for 41,000 declarations, a name lookup 3–40 ms. Timeline (with the work time) is ⋯ → Timeline, at `#/s/<id>/timeline` with no tab of its own. Old `…/comments` links open the Diff, `…/chat` the Terminal (`dashboard-route.ts`). What the header opens (Ship, notes, a menu, catch-up) belongs to one session: `SessionHeader` is keyed by its id.

A rail row's right-click menu (`state/session-menu.ts`, the shared `RowMenu`): Rename (F2), Archive / Restore, Keep after its PR merges (or, once kept, Archive after its PR merges: see the PR watch), Open in terminal, Open in editor, Copy branch name, Delete… (the usual dialog). An archived session has no Open (Restore first). Outcomes and failures show in a `Toast`. Moving to another session (the rail, `n`, a Sessions table row, a notification) opens it on its Terminal tab, whatever tab the one you left was on and finished work too (`hopTo`, `DashboardApp.tsx`); only the review queue, Today and a conversation hit open a diff. j/k keep the tab (`walkTo`): landing on a terminal would take the keyboard, and the next j would be typed into Claude. **Ctrl+P** opens the quick switcher (`QuickSwitcher`, `state/quick-switch.ts`): nothing typed, the sessions used last; typed, the sessions with every word somewhere in their name, branch, repo, folder, summary or Jira key (`sessionMatches`), names and branches starting with it first, archived last. It is caught in the capture phase like Ctrl+K, so it works from inside a terminal (where it replaces the shell's Ctrl+P) and keeps the desktop app's print dialog away. **`/`** opens it too (`useQuickSwitcher`; it was the rail's search box, which repeated this), but not while typing in a field or a terminal (its input is a textarea, so `/` in Claude reaches Claude) and not over a dialog or a menu (`modalOpen`).

**Bulk actions** (Sessions table, View ▾ → Select several, which shows the checkboxes): tick rows (or "select all shown" per table) and the bar acts on them — Archive / Restore / Snooze / Send a prompt / Delete — each through the same call as the one-session button (`BulkActions`), three at a time (`state/bulk.ts` `runBulk`), with progress in the bar and one outcome line (`bulkSummary`: what was refused, and why). Archive and Delete never force: a session with work waiting, or a worktree with uncommitted / unpushed work, is refused and stays ticked. Delete asks first, and a delete is one at a time per session: a second request while one runs (a row's own Delete during the bulk one) gets the first one's answer (one with other options, forced or session-only, is refused instead), and "unknown session" from a delete counts as deleted in the SPA (`removeWorktree`). A prompt goes as a published comment (`sendPromptToSession`), like Prompts ▾ and `work broadcast`.

**Catch me up** (the session header's ⋯ menu, `core/conversations/catch-up.ts`): a few sentences on where a session stands — done, left, anything waiting on you — written by the summarising agent (`runInternal`, no tools: the transcript can contain anything) from its last 7 days of conversation (`catchUpTimeline`: your prompts and Claude's last message before each, the newest ~14k characters), its status and its uncommitted size. Cached in memory until the transcripts grow; `GET /api/sessions/:id/catch-up` only reads the cache (§1.5), `POST` writes it. After two quiet days the status line offers "Away 3d · Catch me up".

**Behind main** (`core/stacks/behind-main.ts`): per session, in the background (`BehindCache`: 10-min TTL, two at a time, a broadcast when it changes), each repo's commits behind `origin/HEAD` and whether merging it would conflict (`git merge-tree --write-tree`: nothing touched), as of the last fetch → `SessionWire.behind` (the furthest repo; any conflict). The session header shows "↓ 34 behind origin/main" from 10 commits, or any conflict, with **Update from main** (`POST /api/sessions/:id/update-from-main`): refused while its Claude works or waits on you, or with uncommitted changes; fetch, then rebase a branch never pushed, or merge main into a pushed one (a rebase would need a force push, which Ship doesn't do); a conflict is aborted at once (the worktree as it was) and "Ask Claude to resolve" sends the session a prompt to do it. (The older `POST …/rebase` rebases on the detected parent without fetching and leaves a conflicted rebase in place; the dashboard no longer uses it.)

**A rail row** (`SessionRail.tsx` draws it; what it shows is `state/rail-row.ts`, pure): two lines, the same four places on every row. Line 1: the name — your title whole, else the branch with its type prefix up to the first `/` (`feat/`, `fix/`) muted (`railName`, `.wd-dash-rail-prefix`), so the eye starts at the slug; cut at its end when narrow — and at the right always a time (`railTime`: how long in its state while its agent asks or works, in that state's colour; else when it was last used; quiet when snoozed), or `archiving…` / `restoring…`. Line 2: the project (and `· branch` when you named it), cut with an ellipsis; at the right one status (`railStatus`: `snoozed` first (what it owes meanwhile is in the hover), else what you owe — `review +2`, `merge`, `CI`, in the owed badge's colours —, else `in review`), then `keep` when kept, then the PRs: one dot each in its stage's colour (the tone its pill has elsewhere; a draft a ring), at most five then `+N` (`railPrMarks`, `RailPrMarks`, `.wd-rail-pr-mark`); hovering a dot says `repo #number · stage`, a click opens the PR without selecting the row. The status, keep and dots never shrink, so a long project is cut rather than pushed out; line 2 is a badge's height on every row. The PR numbers are in the row's tooltip (`railDetails`: "PRs api #12 · waiting for review, …"). The Sessions table, the Inbox and Ctrl+P keep the numbered pills. The rail's header is the view switch (Mine · State, below), the status legend (`?`) and New worktree (`+`): no search box (Ctrl+P or `/`).

**Pins and sections** (rail, `core/rail/rail-layout.ts`, pure, shared with the SPA and demo): pin a few sessions to the top, or put them under your own headings. Right-click a row → Pin to top / Move to “…” / Take out of / New section…, or drag a row into another group or onto a heading. The rail reads Pinned, then your sections in your order (empty ones too, so you can drop into them), then Other. Rows keep the rail order inside each group, and pinned wins over a section. The rail order is your drag order (`applyManualOrder`, `core/rail/session-order.ts`); sessions you haven't dragged come above it, newest created first (they're what you're starting on; by project name, a new one landed below an older one), and with no drag order at all the rail is by project, then most recently entered (`stableSessionOrder`). **Older**: sessions not entered in 14 days and not running (`railSessions`) are one more heading, `Older` with its count, last (`railGroups`, `OLDER_GROUP`); it starts folded, the opposite of the other headings, and unfolds like them (remembered in this browser: the stored list of folded headings holds `older:open` once you open it). A pinned session and the selected one stay in their own groups however old. Older is not a section: a drag onto its heading, or across its edge, places nothing. Right-click a heading to rename it, move it up or down, or remove it (its sessions go back to the rest). Folding a heading is per browser (localStorage); everything else is in state.db for every window: the section list in `meta` (`ui:rail-sections`), each session's place in `rail_place` (schema v6, purged with the session). Routes: `GET /api/rail`, `POST /api/rail/sections` (one change, add / rename / move / remove, applied to the list as it is, so two windows never overwrite each other), `PUT /api/sessions/:id/rail`, broadcasting `rail-changed`. An empty Other heading stays as a drop target once everything is placed. The Sessions table shows them too: 📌 or the section name on each row, a Rail filter (in View ▾) (pinned / a section / in none), a "rail section" grouping, and the bulk bar's Rail ▾ (Pin, Unpin, Move to a section, Out of their section). **Alt+1…9** opens the rail's first nine rows as shown, from anywhere, a terminal included (capture phase), but not while typing in a field. j/k walk the rows exactly as the rail shows them (it reports them, `onShownChange`: headings folded or not, Older among them).

**The rail's views** (`state/rail-views.ts`, pure): a switch in the rail's header, **Mine · State · Project** (the shared `Segmented`, as tabs, left of `?` and `+`). **Mine** is the rail as described above (pins, sections, your order). **State** groups the same rows, drawn the same way, by what each needs now (`stateGroupOf`): **Needs you** (not snoozed, and its agent asks for input or you owe it something: the owed badge — a turn to review, replies, merge, CI), **Working** (working, in background, active, archiving or restoring), **Idle** (every other current session; one whose PR waits on others too, its row says `in review`), **Snoozed** (snoozed, whatever else is true of it), then **Older** as in Mine, except that an older session that needs you is under Needs you, not folded away there; a heading with no sessions is left out (`stateGroups`, keys `state:<group>`). Inside a group the order is Mine's (`railSessions`: your drag order, unplaced first), so a row keeps its place among its neighbours and moves only when its state changes; pins and sections group nothing there, a row's color bar is still drawn, and the selected session stays in its group however old. State is read-only for placement: nothing drags, Alt+↑/↓ does nothing, there are no section headings or their menu; a row's right-click menu is unchanged (Pin, Move to, Color change Mine; New section… switches to Mine to name it there). Its headings fold like Mine's, in the same stored list of folded headings (their `state:` keys never meet Mine's; Older's `older:open` is shared). Alt+1…9 and j/k follow the rows of the view that is on: the rail reports them, and j/k's order before it has is `groupsForView` with the stored view — the same function the rail draws from. The choice is per browser, `work-web:rail-view` in localStorage (`readRailView`: anything else, or storage that throws, is Mine). **In a narrow rail the switch is a dropdown** (reported: its labels ran past the rail's edge): below 260 px of header (a container query on `.wd-dash-rail-header`, `rail-head`; the default 248 included) the three labels give way to one button naming the view with a ▾ (`wd-dash-rail-view-pick`, `aria-haspopup`), which opens the shared `Menu` with the three, the one on checked and a hint beside each (`RAIL_VIEWS[].hint`); `?` and `+` stay on its row.

**The Project view** (`projectGroups`, keys `project:<name>`; `projectOfGroup`): **a card per project** (asked for: headings and rows read alike, and the repo's own checkout was hard to find; chosen from mockups — A of a card each, cards only for projects with worktrees, or the heading as the main session). The card is drawn from the list's own items (`wd-rail-pcard` on the heading's and its rows' `li`, `-head` on the top, `-end` on the last; a folded card's heading closes it), so keys, Alt+1…9, j/k and the hover card are as in the other views; `wd-rail-pcard`, not `wd-rail-card`, which is the hover card's. **Its top**: a fold caret, the project's name in its own words (not small capitals; `wd-rail-pcard-name`) — a click opens the repo's own checkout (`cardHome`: the session whose path is the configured repo's, `SessionWire.baseCheckout`, `isBaseCheckout` in `session-wire.ts`; the most recently entered of several), else folds — the count and `+`. **Its rows**: the own checkout first (`baseFirst`), marked with a house (`HomeIcon`), then the rest in Mine's order. **Colors**: the project's color (config `colors`, `layout.projectColors`) is the card's left edge (`--rail-pcard: var(--tag-<color>)` on each piece), in place of a bar on every row; a row draws its own bar only for a color of its own that isn't the project's (`places[id].color`); a project with none is a plain card. Mine and State still draw a bar per row. Before the cards, it was one heading per project (a session's `target`: its repo, or its group's name, never the group's member repos), in alphabetical order whatever the case, each with its count and a `+` at its right that opens New worktree with that project chosen (`onNewWorktree(project)` → the dialog's `initial.target`); then **Older** as in State (the selected older session and one that needs you stay under their project, so a project with only old sessions has no heading). Inside a project the order is Mine's; placement is off as in State. Its rows are one line (`wd-dash-rail-item-compact`): icon, name, the one status, the PR dots, the time. The heading says the project, so the row doesn't; `keep` and the branch of a session you named are in the card. **The card** (`RailCardView`, content from `railCard` in `rail-row.ts`, pure): hovering a row for `CARD_WAIT_MS` (350 ms, so moving down the rail shows none) or focusing it with the keyboard (`:focus-visible`) shows a card beside the rail, in place of the row's `title` tooltip, which Project rows and their dots don't have (two hovers would cover each other): the name whole, project · branch, its state with the agent's last line, every PR (not five) with its title and stage, then what the tooltip says elsewhere (the branch its checkout is really on, what it is stacked on, how far behind, its automatic title, what you owe, snoozed until, notes, kept, account, color, Alt+N; `railDetails` with `prs: null`, since the card lists them). A PR's title comes from the dashboard's PR list (`prsFor`); one only the PR watch knows has none. The card is `role="tooltip"`, the row points at it (`aria-describedby`), and it is read-only (`pointer-events: none`): a PR opens from its dot. It goes when the pointer or focus leaves (the pointer leaving another row leaves the focused row's card), on Esc, a click, a right-click, a scroll of the list (a pending one too), a change of view, a rename, and when the rows shown change under it (it is placed where its row was; a row that unmounts fires no leave). It is `position: fixed` at its row's top, moved up or left when it would pass the window's bottom or right edge (the narrow-screen drawer). The heading's `+` is 16 px with a 24 px hit box (`::after`), so a near miss doesn't fold the group. Known limit: the pointer cannot move onto the card (it is not hoverable). Mine and State keep the tooltip and have no card.

**Colors** (`RailPlace.color`, `RAIL_COLORS`: Finder's six, red · orange · yellow · green · blue · purple): a mark you put on a session that moves nothing, so a group of yours stays visible wherever its sessions are, pinned or in a section, and in the other lists too. In the rail it is a 3 px bar down the row's left edge, in the list's gutter (`wd-dash-rail-colored`): no status icon is a bar and its spot never changes, so it can't be read as a status (a square beside the status icon could: a red tag next to a red "!"), the active row is a tint rather than a border, and neighbours of one color join into one block. Where a row has room — the Sessions table, Ctrl+P, the Inbox — it is a small square before the name (`ColorMark`). The name is in the rail row's tooltip ("Color: Orange"), the square's, and for screen readers, so the color is never the only cue. Each has a light and a dark shade (`--tag-<color>`, `tokens.css`). Set from the rail's right-click menu (the Color row: six swatches and No color, `colorSwatches`, `state/rail-menu.ts`; a menu row of swatches is `MenuSwatches` in `RowMenu`), the bulk bar's Rail ▾ (the color the ticked sessions share is marked, `sharedColor`), or `work color`; the Sessions table's View ▾ has a Color filter once one is used. Stored with the place in `rail_place` (no schema change: a row is kept while it is pinned, in a section or colored — `applyPlacePatch`, `asRailPlace`), so it goes with the session, survives a drag into another group (`placeForGroup` leaves it) and a removed section; `PUT /api/sessions/:id/rail {color: <color> | null}`, on the demo too.

**Fork** (right-click → Fork…, `core/sessions/fork.ts` + `fork-routes.ts`, `POST /api/sessions/:id/fork`): a new branch and worktree from where the session is. Each repo starts from the branch its checkout is on (`forkBases`), from its last commit; uncommitted files stay behind, and the dialog says so. It refuses an archived session, its own branch name, an invalid name, a name that already exists in any repo (that would check out the existing branch rather than fork), or a detached HEAD. The worktree is created first, so a bad name fails before the slow part; then the catch-up summary is written (`catchUp`, cached when fresh), and the new Claude starts with `forkPrompt`: where it came from, "work only in this worktree", the summary, then your instruction. A summary or start that fails is reported, and the fork stays. From a terminal: `work fork <branch>` (the same `forkSession`, then attaches like `work tree`). § The summary is given rather than the conversation: a copied transcript carries the original worktree's absolute paths, and its Claude would go on editing files there.

**Stacked sessions** (`core/stacks/stack.ts`, pure; `stack-sessions.ts`, `stack-sync.ts`): a session made from another live session's branch, by a fork or `work tree … --base feat/x`, is stacked on it. Nothing new is stored: the parent is found from the recorded `baseBranch` / `baseBranches`, in the same project and on that branch. A group counts only when every repo shares the base. Mainline names, `origin/…` refs, archived sessions and a repo's own checkout are never parents. `SessionWire.stackedOn` / `stackedChildren` drive the session strip's `StackChip` ("⤷ on feat/x · 2 stacked on this", which opens the parent) and the rail tooltip. Behind and Update from (`behind-main.ts`) measure a stacked session against the parent's **local** branch (`refs/heads/<parent>`, nothing fetched; `Behind.stacked`), and it is shown from one commit behind. After a turn ends (`onStatusChanged` → idle), the stacked sessions involved (the children of the one that finished, or itself when stacked) are checked. A child is brought up to date (`syncStackChild`: rebase if never pushed, else merge) only when its Claude is neither working nor waiting, nothing is uncommitted in any repo, and merge-tree says it merges cleanly. The status is asked again right before each repo is changed, since a turn may have started while git looked. A group is all or nothing: if a later repo fails, the ones already updated are reset to the commits recorded first (they were clean). Sessions made from each other's branches form a cycle, and none of them gets a parent. The orchestration is `syncStacksAfterTurn`, tested in core, which web-server only wires. Its Claude is told by a published note, since files may have changed under it; a note that fails to post shows as a warning in Activity. Anything else is left alone with the reason in the Activity panel (`stacks`), and the chip offers it. Config `stacks.autoUpdate: false` turns that off. Session actions have CLI twins (§ core is a library): `work update` (`updateSession`), `work catchup`, `work snooze`, `work pin`, `work section`; with no `<target> <branch>` they act on the session for the current folder (`commands/shared/session-arg.ts`). Their writes reach an open dashboard through state.db's change counters (schema v7: snoozes, notes and blocks bump `rev:sessions`; pins and sections `rev:rail` → `rail-changed`). The demo shows a stack by the same rule (`feat/invoice-pdf` stacked on `feat/invoice-export`, and any fork). **When the parent merges** (`stack-retarget.ts`): its session archived, AND its archive says merged (a MERGED PR, or its branch deleted as merged into main; `mergedParent`). An archived parent that never merged doesn't count, since moving onto main would drop its work from the child. The child then shows "⤷ was on feat/x — merged" with **Move onto main** (`POST /api/sessions/:id/retarget`). That runs `git rebase --onto origin/<main> <fork point>`, replaying only the child's own commits: main has the parent's in another form after a squash merge, so a plain rebase would replay them. The fork point (`forkPoint`) is not simply the merge-base with the parent's tip, because a parent rebased or amended before it merged shares only an older commit with the child, and replaying from there would bring its old commits back. If the parent's tip is in main (a real merge), it's a plain `git rebase <main>`. Otherwise it's git's `--fork-point` (the parent branch's reflog, which survives a rewrite), or the tip if the child is built on it (`parentTipFor`: the branch, or the tip its archive recorded). If neither works, it refuses and says so (ask its Claude). Before each repo is changed, the status is asked again (`stillOk`), for the button and for Update from main too. Repos with different mainlines keep per-repo bases (`setSessionBase`). The automatic move needs git 2.40 (`merge-tree --merge-base`); on older git it never runs, and the button still works. The demo shows one (`feat/tax-report` on the merged `feat/tax-rates`). A pushed child isn't rewritten: main is merged in. It's all or nothing across a group, refused while its Claude works or with uncommitted changes, and a conflict is aborted. Afterwards its base is main (`setSessionBase`), so it is no longer stacked. It happens by itself after the child's own turn (`retargetIfMerged`, in `syncStacksAfterTurn`) and when the parent is archived (`onArchived`, a listener in `session-archive.ts` that every archive path calls, then `retargetChildrenOf`), when `merge-tree --merge-base` says it goes cleanly, and its Claude is told. If the parent was rewritten and git can't find the fork point (`handOff`), the child's Claude is asked to do it (`ontoMainPrompt`, once per parent tip), and the button's result offers Ask Claude.

**Time per session** (`core/conversations/work-time.ts`, pure; `work-time-source.ts`; `GET /api/sessions/:id/time`): how long a session's Claude worked, from its transcripts, approximately. The time between two lines counts when the later one is Claude's (its message, or a tool result coming back), at most `STEP_CAP_MS` (15 min) each, so your reading and typing don't count, and neither does a permission prompt left for hours. The source reads each transcript once, then only the bytes appended since, a megabyte at a time with a pause between. A file that shrank, changed without growing, or starts differently was rewritten and is read again; an incomplete last line waits for the next read. At most 400 files are kept, the least recently asked about going first. Several transcripts of one session working at once count that time once (`mergeSteps`). The Timeline's `WorkTimeChip` shows "⏱ 1h 20m" with a per-day tooltip and refreshes at most once a minute. With config `jiraWorklog` (`site`, `email`, and an API token in `JIRA_API_TOKEN`, or `tokenEnv` / `token`), **→ PAY-12** next to the chip writes the latest day's work to the session's Jira issue as a worklog through Jira's REST API (`core/jira/jira-worklog.ts`; `acli` has no worklog command). It is rounded up to a quarter hour, and only what isn't logged for that day yet is written: state.db `worklogs` (v7, purged with the session) records it. The token never reaches the SPA. `GET`/`POST /api/sessions/:id/worklog`, `work time --log`. A click copies a worklog line (the latest day's work in the last two weeks, usually today's, rounded up to a quarter hour, with the Jira key; never a lifetime total; a failed copy says so): work can't write Jira worklogs itself, since `acli` has no worklog command. The Today digest counts it too (`DigestSession.workedMs`, "~1h 20m of Claude work", also in `work digest`), from the same transcript reads as its prompts.

**Timeline** (⋯ → Timeline, `#/s/<id>/timeline`; `core/conversations/timeline.ts`, pure, also used by the demo; `timeline-source.ts`; `GET /api/sessions/:id/timeline`): how a session got where it is, newest first by day. It shows when it started, your prompts (the last 30 days of its transcripts, at most 8 MB each), its turns (checkpoints, with names already written; a size-only name says so), its commits since it left `origin/HEAD` (per repo, at most 100), its PRs (the PR watch's last look) and when it was archived. A read: git log and merge-base, the transcripts, the cache; it runs no Claude and refreshes when the conversation moves.

**Blocked by** (`core/rail/blocks.ts`, pure, also used by the demo; `session-blocks.ts`, `block-routes.ts`): a session waits on another session or a GitHub PR. Set it with right-click → Blocked by… (`BlockedByDialog`), the ⛔ chip in the session strip (× stops waiting on one), or `work block`. While it waits, `inboxRank` puts it in "Waiting on others" (7), out of the Inbox and its count; a question from its Claude (needs input) still shows. A session blocker is done when that session is archived or deleted; a PR blocker when it is merged or closed. Waiting on a session that (perhaps through others) waits on this one is refused (it would never end). The sweep (`sweepBlocks`, every 3 min in full work web, also after an archive and when a block is added; Activity kind `blocks`) asks `gh pr view <url> --json state` about the PRs, clears each block whose blockers are all done (removing only the ones it found done, so one added meanwhile keeps the session waiting), and notifies you by presence like every notification (`notify` from `mountStatusRoutes`, kind `unblocked`). It rests 10 min when gh reports GitHub's limit. It also tells the session's Claude (`unblockedPrompt`, a published comment). State: state.db `session_blocks` (v7, purged with the session), `SessionWire.blockedBy` (only what isn't done), `POST`/`DELETE /api/sessions/:id/blocks`.

**Notes** (`core/rail/session-notes.ts`, `note-routes.ts`): your own scratchpad per session — what you decided, what to tell the reviewer, what's next — not part of Claude's conversation. ⋯ → Notes opens it (and 📝 Notes in the status line, when it has some) (`SessionNotes`: saved after a pause in typing, a pending save kept when it closes), Send to Claude hands it over as a published comment, the rail row's tooltip says it has notes (`SessionWire.hasNote`), and `work note` reads/sets/appends from a terminal. state.db `session_notes` (v7, purged with the session); `GET`/`PUT /api/sessions/:id/note` (at most 20 000 characters).
