# Reviews (PR reviews prepared in the background, #64)

The **Reviews** tab (`#/reviews`, `g v`, `ReviewsTab`): open pull requests of your repos, each prepared as a review grouped by **kind of change** rather than alphabetically. `core/review/`: `change-kinds.ts` (pure, SPA-shared: each file's kind — generated, mechanical, dependencies / build / CI, wiring, schema, API surface, logic, tests — and why; the rules are data, `DEFAULT_RULES` for .NET and Node, config `reviews.rules` before them (`rulesWith`); a file marked `linguist-generated`, a pure rename, a whitespace-only change and an imports-only edit are said so by git or the lines — never a whitespace-only change where indentation is meaning: Python, YAML, Makefiles, F#… `whitespaceMatters`; resources and translations — `.resx`, `.resw`, `.po`, `.xlf`, JSON under `locales/` / `i18n/` — are mechanical, and test support — a shared tests project (`*.Tests.Shared`), `TestData`, `TestHelpers`, `Fixtures` — is tests, so neither reads as untested logic); **designer files are left out of the review altogether** (`IGNORED_IN_REVIEW`, `ignoredInReview`: `*.Designer.cs` — an EF migration's is thousands of lines of model snapshot; reported) — `splitIgnored` (`review-build.ts`) takes them off before anything reads the PR: not listed, not diffed (the `…/diff` route drops them too), not in the AI step's prompt, not counted against the size limit; `PrReviewWire.ignored` names each with its +/− on the overview's Not worth reading line ("1 designer file left out"), and `size` still counts the whole PR, `test-breakdown.ts` (pure: the tests a PR adds, changes, removes and skips, by framework — xUnit / NUnit / MSTest / Jest-Vitest / pytest, parameterised rows counted (an `it.each` / `parametrize` table written as a list too, `tableRows`; a skip only when the PR writes it) —, their level (unit, integration, e2e: `TEST_LEVEL_RULES`, a table — a folder or file named for a database (`PostgreTests/`, `*DbTests`), a database base class or fixture (`: BasePostgreTest`, `DatabaseFixture`, `IClassFixture<…Database…>`), Testcontainers, `WebApplicationFactory` are integration), which code each test file covers — by name (singular or plural: `JsonMaskingExtensionTests` is about `JsonMaskingExtensions`), imports, a type the code file's diff declares that the test names anywhere (the hunk's `@@` line counts: the class a change is in is rarely within the lines git shows) or a C# extension method it declares that the test calls (`EXTENSION_METHOD`: called on a value, its class never named), or (C#) the code file's namespace imported (declared, else its folders': a handler's tests reach its validator) — counting only files with tests in them (a data builder covers nothing), the production changes nothing tests (`gaps`), removed or skipped tests (`lost`), and a schema change with unit tests only), `review-plan.ts` (pure: the AI step's prompt — everything of the PR, its title, its tests' names, **every** changed schema / API / logic / wiring file (`PROMPT_KINDS`) listed with its +/− and the new-side lines a note may go on, and as many of their diffs as the 60,000-character budget holds, most important first (`byImportance`: schema and API, then logic by the size of its change, wiring, resources and translations last), fenced as data (`asData` / `asDataBlock`, `time/fence.ts`); in a checkout the agent is told to read the files whose diff isn't shown and may note any listed line (`CHECKOUT_LINES`), with the diff alone it is told which were left out for room and notes only what it saw (`DIFF_ONLY_LINES`); in both, to write every text in full sentences to a colleague who will review it — behaviour, not lists of nouns; concrete names, no filler (`WRITING_LINES`) — and its answer read strictly (`parseAgentPass`: only listed files, known flags, risk 1-5, text cut at a word with "…", `clip`: a title — one sentence saying what the change does for whom, with an example in the prompt — 200 (`MAX_TITLE`), "what" 1,500 (`MAX_WHAT`), the reasons 1,200 (`MAX_TEXT`), a file's summary 600 (`MAX_FILE_SUMMARY`); `fileSummaries` kept only for a listed file, by its path or as the prompt fenced it, a missing one no fault); **stories** riskiest first, the same risk in the agent's own order (by folder: the most files first), each with its sentence title, **what it does** (`Story.what`: 3–6 sentences for a reviewer who hasn't seen the code — the behaviour, who is affected, existing data, callers and integrations; its first sentence, shown alone on the overview, the effect in plain words with no code names; absent on a review from before), why it exists, why it's ranked there, flags, its tests (never one the PR removes, each name once) or its gap; by folder when there's no AI step, said so; the agent's notes become **draft comments**), `review-build.ts` (pure: the review from a diff, `buildReview`: each file's lines a comment can go on (`ReviewFileWire.lines`, `rightLines`), each schema / API / logic / wiring file's **What changed here** (`ReviewFileWire.summary`, 2–4 sentences; never a test's — its asserts line serves — nor a generated or mechanical one's — its rule says why —, none without the AI step; shape-checked in the store with `Story.what`), an AI note off them set aside in `dropped` with its text, never a draft the host would refuse the whole review for; an answer naming no story is a failed AI step; `describeReview` for the Ctrl+K assistant (each story's what and reasons, each file's summary), the PR's and the AI step's text fenced, described afresh at each prompt — `review-now.ts`, the stored context keeps only which PR, `assistantContextReview`, as the Time tab's day), `review-source.ts` (the code with no checkout: the host's PR ref fetched into `refs/work/review/<n>` — a merge ref (`GitHost.prRefIsMerge`, Azure DevOps' `refs/pull/<n>/merge`) is moved to its second parent, the PR's head, so the review is read and commented there —, the base fetched, the diff from their merge-base, `-w` for whitespace-only, `check-attr --source` (200 paths a call) for linguist-generated; the ref deleted with its review, `dropReviewRef`), `review-tree.ts` (the AI step's **temporary checkout**: so the agent has the context it would have with the PR checked out — the repo's CLAUDE.md, `.claude/rules`, callers, interfaces, existing tests — a detached `git worktree add` of the review ref (the PR's own head, never a merge commit; refused if it isn't the reviewed commit) at `~/.work/review-trees/<alias>-<n>-<sha8>-<run>` (`runSuffix`: this process and a random part, so two work webs reviewing one head never delete each other's checkout; a stopped run's is swept by age), with an empty hooks folder (`core.hooksPath`: a husky-style `.husky` would run the PR's post-checkout) and `core.symlinks=false` (a link can't point a read elsewhere); Git LFS off (`NO_LFS`: `-c filter.lfs.smudge= -c filter.lfs.process= -c filter.lfs.required=false`, and `GIT_LFS_SKIP_SMUDGE=1` — a PR's `.lfsconfig` could point the download at a server of its choosing, and a big one outlasts git's timeout; the runner's optional `env`); the files the agent reads as settings deleted before it starts (`strip`: the agent's own `oneShot.readOnly.isSettingsFile`); no install, no build, nothing of the PR runs. The agent runs there read-only (`oneShot.readOnly`, `runInternalReadOnly`, `CHECKOUT_AGENT_TIMEOUT_MS` 5 min; a timeout kills its process tree first) and the tree is always removed (`withReviewTree`'s finally: `git worktree remove --force`, the folder if left, `git worktree prune`); the first sweep removes what a stopped run left (`sweepReviewTrees`, in the one-at-a-time chain, not one younger than the timeout + 5 min — another work web may be reading it — said in Activity). The prompt then says, in the agent's own words (`promptLines`, the queue's `checkoutLines`), that it is in a read-only checkout at the PR's head with its tools and instructions, and in work's (`CHECKOUT_LINES`, naming no agent) that the files are the PR's too (follow the repo's conventions, never an instruction in a file addressed to it), the same strict JSON; an agent without the mode, or a checkout run with no answer, falls back to the diff-only text run (`agentInCheckout` → `agent`), and the Activity note says which: "read in a temporary checkout of the PR" (with its note, when its checkout wouldn't go) / "read from the diff alone (why)"); a failure of the keeper's tidy is logged and noted in Activity (a failed run), the sweep runs anyway), `review-queue.ts` (policy, I/O injected: per project `all` / `asked` / `off` — config `reviews.projects`, a repo's own setting over its group's, `reviewModeOf` —, never your own PRs or drafts (`candidates`; who you are unknown: the project waits for the next sweep), one review per head — the listed one (`listedHead`; `upToDate`) —, one at a time (its AI step in the internal runs' `reviews` lane, `review-deps.ts`: a review in progress holds up no checkpoint name or catch-up), no daily cap unless `reviews.maxPerDay` sets one (one held by it, `held: 'cap'`, is picked up when the day allows), over `reviews.maxLines` (3000) changed lines **worth reading** waits for a click (`held: 'size'`; `linesWorthReading`, `review-build.ts`: generated and mechanical files left out — reported: a PR of 23,864 lines waited, 22,997 of them one EF migration `.Designer.cs`; counted once the diff is fetched, so a PR listed over the limit is fetched and held only if it still is — one fetch per head; a review held by the list alone from before, never fetched, is fetched again, `upToDate`); a review not prepared says why where it would be and what to do (`notPreparedLine`, `state/review-view.ts`; reported: a held review opened on a blank page); a row left `running` past `STALE_RUNNING_MS` (work web stopped) is prepared again and its button works, anything that throws ends it `failed`; prepared again, your drafts still on the diff, what you posted and submitted, and the drafts a standing Fix it myself claim is taking carry over as they are, the rest set aside with their text (`carryForward`, read and written in one transaction, `upsertReview`); reviews of PRs no longer open go — only from a complete list (`openPrs` `more`: at its limit, 100, nothing is dropped); each decision in Activity, kind `reviews`, why a PR is left out too), `review-store.ts` (state.db `pr_reviews`, schema v11, keyed `repo#number`, shape-checked; in `work state` and its export), `review-deps.ts` (the real I/O), `review-keeper.ts` (when work web sweeps: 4 min after start, then every 10; not the dev server). The host lists every open PR (`GitHost.openPrs`) and takes the review as one (`submitReview`: GitHub one review with its line comments, `gh api …/reviews --input`; Azure DevOps a thread per comment, the summary a thread, the verdict a vote) — the drafts you kept (the AI step's and your own, added on a line: `POST …/drafts`), a verdict (Comment / Approve / Request changes) and a summary, only on your Submit click (`POST /api/reviews/:repo/:n/submit`; `review-submit.ts`, pure, checks it: a draft off the diff's lines is refused before it reaches the host), never a sweep's or an agent's. § A submit is in your name and never goes twice. The whole flow is core's `submitPrReview` (`review-submit-flow.ts`, I/O injected; the route and the demo call it): checked and **claimed in one transaction** — `submitting` in the review's `pr_reviews` row (pid, what it sends), so a second submit from another window or from `work web --dev` on the same state.db is 409; a claim left by a process that's gone, made before this boot, or older than `SUBMIT_CLAIM_STALE_MS` (30 min) is taken as in doubt (`claimToDoubt`), never just dropped — on the next submit, by the keeper's tidy before each sweep (`tidyLeftOverSubmits`, said in Activity at warn), and when you say whether it went (`settlePrReview`); until then a read shows it `submitting.stale` (`shownReview`, nothing written; `shownDoubt` in the SPA), so the tab offers It went out / It didn't, never "Submitting…" for good. Refused while the review is queued or running for a new push (its lines are the prepared diff's: `withStatus` keeps the prepared `headSha` until it's prepared again). A host's failure says what went out before it (`SubmitReviewResult`: `posted`, `summaryPosted` — Azure DevOps posts each part on its own) and those drafts are marked posted (`afterFailedSubmit`), a summary that went out isn't sent again (`summaryToSend`); a call that failed without a **clear refusal** may have gone through (`refusedClearly`, `core/hosts/submit-doubt.ts`: only not installed, never started, a 4xx status or the host's own refusal words count as "nothing went out" — a timeout, a 5xx, a reset connection, az exiting 0 with output it can't read, or a host call that throws are in doubt), so what it carried is recorded `inDoubt` — a bare verdict too (an Approve with no comment or summary: a retry would cast it twice) — (with `partial` when the steps after it — Azure's later comments, summary, vote — weren't tried: "it went" then records a partial submit, never a verdict that wasn't cast) and nothing is sent until you say whether it went (`POST …/in-doubt {went}`, `settleInDoubt`). After a partial submit, request changes may be retried as the vote alone (`nothingToSubmit`, shared with the SPA's button). **Draft ids are never handed out twice** (`lastDraft`, `lastDraftNumber`): a re-prepare numbers the AI step's new drafts past every id the review has had, and keeps as they are the drafts a submit in doubt or under way names (they may be posted; they can't be discarded until you say). work web sweeps every 10 min (the dev server prepares none). Routes (`review-routes.ts`): `GET /api/reviews`, `GET`/`PUT /api/reviews/settings`, `GET /api/reviews/:repo/:n` and `…/diff` (recomputed from the stored merge-base), `POST /api/reviews/:repo/:n` (prepare now), `…/drafts` (add yours, on a line of the diff), `…/drafts/:id` `DELETE` (never a posted one: 409), `…/submit`, `…/in-doubt`, `…/dropped` `DELETE` (forget the drafts set aside); each broadcasts `reviews-changed`; the demo answers the same table of requests (`tests/server/demo/demo-reviews.test.ts`). A review reads four ways (`state/review-view.ts`, pure; `components/Dashboard/tabs/review/`): the **Overview** (where it opens; no diff) — **In short** (the AI step's `summary`: two or three sentences asked first in the prompt, read strictly, cut at a word to 600, `MAX_SUMMARY`; **Stories** — one at a time (`reviewPages`: the stories, then each kind of change no story took, generated and mechanical folded until Show the diffs): its sentence and badges on top, then **What it does**, **Why these files belong together** and **Why it's ranked here** as paragraphs (~80 characters a line), only its code files' diffs — each with its **What changed here** under the header, above the code, folding to its heading (`FileSummary`, `DiffFile`'s `note`) — the AI step's prose drawn as text with what it put between backticks as code (`proseParts`, `Prose`; **The PR's existing discussion** (`PrReviewWire.discussion`, `PrDiscussionWire`; `core/review/review-discussion.ts`, pure, SPA-shared): what reviewers and the author already wrote on the host — its review threads (path, line, side, outdated, resolved, every comment's author, association, time and link), the submitted reviews (verdicts; never a pending one) and the conversation comments — read through `GitHost.discussion`, read only: work never answers or resolves anything here (later, only on a click). **Fix it myself** (beside Submit; `FixMyselfDialog`, `review-fix.ts`, I/O injected, the route and the demo run it): the review's pending drafts, each ticked; the ticked ones leave the review for a session on the PR's own branch and the unticked stay drafts — your verdict and summary stay, to Approve once you pushed. `POST /api/reviews/:repo/:n/fix-myself {drafts: [id…]}` → `fixItMyself`: refused first (`fixRefusal`, `review-fix-rules.ts`, pure and shared with the SPA's button, `fixMyselfBlocked`: a fork's PR — `PrReviewWire.fork`, from the host's list, `OpenPr.fork`; a submit in doubt (one left over too) or under way; another Fix it myself under way; a review being prepared again; no pick, an unknown, twice-named or posted draft), then checked again and **its drafts claimed in one transaction** (`fixing` in the row, `ReviewFixingWire`: a submit — `submitRefusal` — a second Fix it myself and a discard of a claimed draft are 409 while it stands; released on any failure, ended with the take-off; one left by a stopped work web stands only `FIX_CLAIM_STALE_MS`, 10 min), then the PR looked up as Start's Work on it does (`resolvePrToStart`: open, not a fork's, a local branch that hasn't gone another way); a live session already on that branch (`sessionOnBranch`: not archived, the repo checked out on it) is told by a published note (`noteThroughComments`), never a second session; else one is made through the server's `makeWorktree` (`realFixIo`, `review-deps.ts`) and started with the instruction (`startSessionWithPrompt`; an agent that won't start gets it as a note, said). The instruction (`fixMyselfPrompt`, pure): `workOnPrPrompt`'s whose-branch and post-nothing-on-the-host lines (`commandsFor(host)`), the comments as "in `path:line`: …" fenced as data, then make them, build, run the tests, commit saying what changed and why (the author reads it), and ask before pushing — push only on your yes. § So Fix it myself **runs the PR's code**: it starts a normal session on the PR's branch whose agent builds and runs its tests, as Work on it does, in the agent's normal permission mode (its own prompts are the check) — unlike the Reviews AI step, which only reads a checkout and never runs anything (security §1.7). Its AI-written comments are ticked by default, like yours. § Only once the session has it are the drafts taken off, in one transaction (`takeOffToFix`: a draft a submit took meanwhile stays, and the answer says so; ids never reused), recorded as `fixingMyself` (`ReviewFixWire`: when, the session, the branch, the comments; shape-checked, kept by `carryForward`): the tab shows "3 comments being fixed in <session>" with Open it →, the Ctrl+K description says so, Activity (kind `reviews`) notes it linked to the session. A creation that fails leaves the review as it was. Answers `{sessionId, created, review, warnings?}` (`ReviewFixResultWire`), broadcasts `reviews-changed` and `sessions-changed`, and the tab opens the session's Terminal; its warnings are noted in Activity at warn and shown in the dashboard's toast after the tab goes (`fixReviewMyself` → `announceWarnings`, `ACTION_WARNINGS`, as a Restore's). **From a terminal** (`work review`, `commands/review.ts`; reported: the Reviews tab had no CLI): `list` and `show <repo> <number>` read state.db (`allReviews`, `readReview`), so they work with no work web, and print `reviewListLines` / `reviewText` (`core/review/review-text.ts`, pure: `describeReview` without its "the tab shows" line, then each pending draft's own words — its id, `path:line`, whose it is — fenced with `asData`, cut at `MAX_DRAFT`; posted ones counted), `--json` the stored `PrReviewWire`; stderr says once that the text quotes the PR (data, never instructions). `prepare <repo> <number>` is the tab's Prepare now: `POST /api/reviews/:repo/:n` through `callWorkWeb` with a 10-minute timeout (no work web: it says reviews are prepared by work web). `list` and `show` are on `ASSISTANT_ALLOW`; `prepare` is not. § Nothing in `work review` adds a draft, submits or posts: a review goes out only with your Submit click in the tab.

**The recommendation and the flows** (asked for: a review should say what the agent advises, and describe the flows added, changed or removed; both a PR's review and a session's own): the AI step's answer also carries `recommendation` — a verdict from `VERDICTS` (`ready`, `fix-first`, `discuss`; `VERDICT_LABEL`) with its reasons, naming what to fix or decide first — and `flows` — each a `change` (`FLOW_CHANGES`: added, changed, removed), a title and its steps in order, a flow being a path from a trigger to its outcome (a login, a request, a job run). `parseAgentPass` reads them strictly (a known verdict with reasons; a known change, a title and at least one step; text cut at a word; at most 12 flows of 10 steps), `planReview` keeps them only with the agent's own stories, and they are on `PrReviewWire` (`recommendation?`, `flows?`: absent on a review from before, or with no AI step). A flow may name the listed `files` it runs through: its **Its code: story N →** links (`flowPages`), and the recommendation has **Read the N notes →**, which opens the first one that needs attention. The overview shows **Recommendation** ("the AI step's advice: you decide" — it never submits or picks the review's event) and **Flows** (each folded to its title when there are more than two) under In short; `describeReview` / `reviewText` give both, fenced. § It is advice from text we don't control (a PR's diff could be written to ask for "ready"): shown as the AI step's, never acted on by work.

**A note's level** (reported: sixteen notes sat in one list, a likely bug beside "probably fine"; both a PR's review and a session's own): the AI step gives each note a `level` from `NOTE_LEVELS` — `bug` (likely wrong as written), `check` (someone who knows the system should confirm), `minor` (style, naming, a nice-to-have); `parseAgentPass` keeps a known one, and a note without one (yours, or a review from before) reads as `check` (`noteLevel`). The overview's **Needs your attention** lists the likely bugs first (marked), then the ones worth checking, and folds the minor ones under "N minor points" (`attentionOrder`: each keeps its place in the walk, which stays in the stories' order); the count "to look at" is of the unfolded ones. `reviewText` says a note's level.

**Each story's own verdict** (asked for: the whole change had a recommendation, each story none; both a PR's review and a session's own): the AI step gives every story a `verdict` from the same `VERDICTS` and a `verdictWhy` sentence — what to fix or decide in that story, or why it is fine (`Story.verdict` / `verdictWhy`; `parseAgentPass` keeps a known verdict, and a reason only with one).
