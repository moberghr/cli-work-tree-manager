# Session Tracking

`core/sessions/history.ts` stores worktree sessions in state.db's `sessions` table (one row per `target + branch`). The `tree` command calls `upsertSession()` before launching Claude; `remove` calls `removeSession()` on success. The `status` command reads history + live git info; `recent` lists sessions sorted by last access.

**Session identity & state.** The id is `sessionIdFor` (`core/sessions/session-id.ts`: sha1(target:branch), 12 hex). The branch is the one it STARTED on, and names its folder; its name is separate — `title` (`--name`, the New worktree dialog's Name, F2 / Rename later), the rail's label when you gave one. Claude (or you) may switch the worktree to another branch: ship, the PR watch and the diffs read the checked-out branch from git; `onOtherBranch` (HEAD files, no git: `core/git/git-head.ts`) shows it; re-entering uses the folder as it is; archive records it (`heads`) so Restore of a removed worktree checks that branch out again. **A session's branches** (`core/sessions/session-branches.ts`; reported: a PR merged, Claude made two new branches from origin/dev in the same worktree with a commit each, and the session showed only the one checked out — the webhook work looked gone): every branch each repo has been on is recorded per session in state.db `session_branches` (schema v12, purged with the session; `{repo, name, firstSeen, lastSeen, from?, gone?, merged?, pushed?}`, shape-checked by `cleanBranches`), so nothing asks git each time. Written in one `tx()` at each turn's end (`runTurnHook` → `recordBranchesFor`: HEAD files, no git — `checkedOutBranch`; a branch new to the record gets `from` from its own reflog's first line, `branch: Created from origin/dev`, `core/git/reflog.ts`), when work checks a branch out (`setupWorktree`, re-entry, Restore, Update), and once for a session from before (`backfilled`: `backfillSessionBranches` reads each checkout's `logs/HEAD` — `checkout: moving from X to Y` — with the session's own branch, in the background, `createSessionBranches`); lastSeen is rewritten only when it moved 10 min (`LAST_SEEN_STEP_MS`), at most 30 kept per repo. **Facts** per branch (`core/stacks/branch-facts.ts`: exists, its tip, `origin/<name>` there, commits its base — origin/HEAD — lacks, commits origin lacks, merged = pushed with none of its own) are read in the background beside behind-main (`BranchFactsCache`: 5-min TTL, two sessions at a time, a broadcast on change; never on /api/sessions' path); what they find is kept (`noteBranchFacts`: `gone` from when it was first seen deleted, `merged`, `pushed` once). A merged branch deleted `GONE_SHOWN_MS` (3 days) ago drops out of what's shown (`branchHidden`), and so does one merged or deleted that isn't checked out and was last checked out `DONE_SHOWN_MS` (30 days) ago — merged as the wire shows it, so one with work of its own again stays —, kept in the record. `SessionWire.branches` (`branchesWire`: the checked-out ones first, then newest; each with its facts and its PR from the PR watch's last check) only when a repo has been on more than one; the header's **N branches ▾** chip (`BranchesChip`, `branchesChip`: amber while one holds work not pushed; its list is `BranchesLine`, `state/branches.ts`: commits, not pushed, the PR pill — a click shows that branch in the Diff tab — and the way to the **Branches** tab, `BranchesTab`, `#/s/<id>/branches`, key 5, there only with more than one branch: per repo each branch with what's known of it, the turns taken on it and when, its commits folded, Show in Diff — `branchTabRows`; reported: three header lines before the tabs), `work sessions --json` and `work status` (`sessionBranchesNow`: looked at with git there and then), and the Ctrl+K description (`branchesText`, `core/sessions/branch-view.ts`). `prsForSession` matches the dashboard's PR list on any recorded branch. **A session's repos.** A session owns its repo list: `WorktreeSession.repos` (aliases, one per `paths` entry, same order), recorded when it is made and by Add a repo. Everything that acts on an existing session — teardown, archive, Restore, fork, clean-up, branch tidy, move, the dev server, checkpoint clean-up, stack retarget, the Repos page's live counts — reads it through `sessionRepos` / `sessionAliases` (`core/sessions/session-repos.ts`), never the group's config, so a session can hold a repo its group doesn't name and keep one its group lost. A row from before (no `repos`) is read as it always was: a group's from config `groups[target]` matched by folder name (else the folder's own name, `guessed`), a single repo's by its target — and it stays such a row: re-entering or restoring it writes no list (it goes on following its group's config, a repo the group gets later set up as before); only Add a repo records one, and refuses a row with a `guessed` folder. A list that is there but doesn't line up with the paths (a damaged row) is matched by folder name, never replaced by the group's config. A recorded repo no longer in the config isn't set up, is said, and stays on the row with its folder (teardown leaves it, `false`); a fork of such a session is refused. § A writer never drops a repo added meanwhile: `upsertSession*` apply the caller's folders over the row as it is in their transaction (`setOwnRepos`: recorded pairs the caller didn't know of stay; `upsertSessionWithPort` too, re-entry's writer), and `work resume` / `work recent` only mark the session used (`touchSession`), never writing back a list read before their picker waited. A group is only the starting set of repos. A **folder session** is `isGroup` (a group's, or a new session made with `sessionFolders`, recorded as `isGroup` with `repos: [alias]`): Claude runs in the folder (`dirname(paths[0])`), every group code path applies. The wire carries both (`SessionWire.repos` via `wireRepos` — config read only for a group's row from before, cached by the file's stat —, `SessionWire.folder`; both absent from an older server): the session header shows a folder's repos ("backend · frontend · docs", `headerRepos`, `state/add-repo.ts`) and `prsForSession` matches the session's own repos when the row has them (else the configured group members, as before).

**Add a repo** (⋯ → Add a repo…, `⇧A`, also the rail's right-click menu — a folder session not archived, `canAddRepo`; `AddRepoDialog`: your enrolled repos from `/api/projects` not in it yet, `addableRepos`, an optional base; `work add-repo`): `addRepoToSession` (`core/worktree/add-repo.ts`) checks the repo out into the session folder on the session's branch (the branch the repo has, else a new one from the base, else from the repo's own checkout's branch, as `work tree` makes one), records it (`appendSessionRepo`: `paths`, `repos`, `baseBranches`, in one `tx()`), rewrites the folder's instructions block (`writeSessionInstructions`, one import per repo in the agent's own syntax — `AgentAdapter.instructionsImport`, Claude's `@<repo>/CLAUDE.md`; an agent without one keeps its file as it is) and carries the Diff tab's turn history over (`migrateScope`, `core/diff/scope-migrate.ts`: the checkpoint manifest, `refs/wd/<old>/*` in every old repo and the `scope-<old>` comment store move to the new paths' hash; an old turn reads the new repo as its HEAD). § The move loses nothing: under both manifests' locks, refs are copied in one `git update-ref --stdin` transaction per repo (undone everywhere if one fails), the manifest written, and only then the old refs and manifest deleted; turns the new scope took meanwhile give way to the old ones (a checkpoint is a whole snapshot); an unreadable manifest or a comment id clash is left as it is, and said (`problems`). A checkout that can't be recorded is removed again, branch and all. What went wrong once the repo was in (the checkout's own warnings, the turns, the instructions file, telling its Claude) is `AddRepoResult.warnings` / `AddRepoWire.warnings`, shown in the toast; the add stands. An add records how the folder's file is made (`instructions`: `summary+imports` for a group's copied summary with the block after it, else `imports`), so a Restore — whose worktree went with its file — makes it the same way. Refused, changing nothing (`addRepoRefusal`, `core/worktree/add-repo-rules.ts`: pure, shared with the route, the CLI and the demo): an unknown session (404), an invalid alias or base (400, one starting with `-` too), an unknown alias (400), an archived session, a single repo's worktree in the old layout, a row from before with a folder no repo of its group has, a repo already in it, a folder of that name already in the session folder (409). `POST /api/sessions/:id/repos` (`session-repo-routes.ts`, `AddRepoWire`) answers the quick refusals itself, lets go of the old scope's watch before the add and again after it (a status hook meanwhile may have opened it under the old paths), runs git in a child (`addRepoInChild`, `core/worktree/add-repo-child.ts`, over `runWorkChild` like `createInChild`: `work add-repo … --session-id= --in-process --json`, its refusals with their status; one add per session at a time, and in the same queue as creations keyed by the repo's alias, `keyedQueue`; killed after 5 min with `git worktree prune`, the answer naming what it left), broadcasts `sessions-changed`, and tells the session's Claude by a published note (`addedRepoNote`, through `noteThroughComments`, `server/session-note.ts`) — nothing restarts: it already sees the folder. `work tree --here` from a folder session's checkout (an added repo too) resolves to that session (`folderSessionAt`, `resolve.ts`). The demo has the same route (`scenario.addRepo`).

Everything per-session beyond history is a row keyed by that id — `session_status`, `comments` (store = id), `comment_deliveries`, `pty_sessions`, `pr_watch_seen`, `dev_runs` — plus the dev log file; `removeSession` (and `work status --prune`) purge it all via `purgeSessionState` (`core/sessions/session-store.ts`) → `purgeSessionRows` (`core/platform/db.ts`), so a re-created session never inherits old state.

§ WHEN adding per-session state, add its table to `purgeSessionRows` (`core/platform/db.ts`), or its file to `sessionStatePaths` (`core/sessions/session-store.ts`). Its diff scope's checkpoints are keyed by the hash of its paths, not its id: `removeSession` clears them (`clearSessionCheckpoints`, from the base checkouts — the worktree may be gone), archive and the dashboard's delete drop the scope's watch (`releaseSessionScope`), and a scope keeps at most `MAX_CHECKPOINTS` (200; the oldest after Initial go, refs too).

**Finding work web.** `core/platform/web-discovery.ts` owns `web.url` / `web.pid`. The files outlive the process and PIDs get reused, so `work web --stop` kills only after `/api/context` answers with the recorded pid (`probeWeb`); `webServerResponds` is liveness only. The PTY host has the same rule (`/health` + token + pid). `/api/context` also carries `build` (`core/platform/build-stamp.ts`: the entry file's mtime): a full `work web` replaces a running server whose build differs from its own, or that predates stamps, since a server that outlived a rebuild reads state and serves routes as they were then (a September dashboard showed no sessions after the SQLite move and 404'd on new routes). `wd` and `--lean` never replace. § Two can still start at once (a restart racing the desktop app's watchdog, which starts one when none answers): every 20 s a work web runs `discoveryCheck` — the one web.pid doesn't name, when the named one answers as itself, stops (leaving the discovery files, which are the other's); with nothing live recorded it writes itself back. A duplicate once kept an old build in the desktop app for hours and doubled the GitHub API use. **How it ended** (`core/platform/web-life.ts`): a work web writes `~/.work/web-life.json` (pid, version, start, a 20 s beat) and, on every way out it sees (a signal, `--stop`, a duplicate retiring, `exit`), how it ended. The next start finds one that vanished without saying (`previousEnd`: killed, a crash below Node, the machine) and logs it with its last beat; the desktop app logs each child's exit status (`spawn_collected_as`, `desktop.log`).
