# Driving a session from outside its terminal (`work read / send / wait / …`)

Another Claude (or a script, or you in a shell) can talk to a session: `core/sessions/session-control.ts` is the policy with its I/O passed in, `session-control-routes.ts` the routes in work web (what only it can do — type into a terminal it owns, start a Claude in the PTY host): `POST /api/sessions/:id/send` (`SendWire`: how it went), `POST …/agent/start|stop`, `GET …/screen` (a read: starts nothing). The CLI calls them through `callWorkWeb` (`web-discovery.ts`: a refusal comes back with its reason; status 0 = no work web — none recorded, or its address refuses; -1 = it didn't answer in time and may still be at it, so `work timesheet` never does the same itself), and reads the rest itself: `work read` the conversation, through the agent interface (`core/agents/`: `AgentAdapter.conversation.read` → `ConversationEntry { at, role: you|agent|tool, text, tool? }`; Claude's adapter reads the newest transcripts' tails, `claudeEntries` is the pure mapping; `agentFor(config)` gives an adapter with no capabilities for another tool), `work wait` the hook-recorded status (`waitForTurn`: with `after`, only a state entered after the message counts). § A message is a published comment, like every note to a session: the comment route types it into an idle host Claude, the prompt hook hands it over otherwise (idle is asked of the agent first — Claude Code's own state file for the host's Claude — and only then of the hooks' record, which stays "working" after a turn that ended with no Stop hook, an interrupt most often: a message sent to that idle Claude waited for good; `noteDelivery`, `core/comments/note-delivery.ts`. A message left for a turn's end is looked at again after 20 s, 90 s and 5 min, `recheckLater`, and typed in if it still waits and the agent is idle by then; one waiting on a permission prompt is never typed into, since Enter would answer it), and a session not running anywhere is started with `NOTE_NUDGE`. An archived one is refused (every agent runs in its own permission mode, so a message asks you before it acts as any prompt does; `force`, from before `--unsafe` was retired, is taken and ignored); **for one release** an agent still running as started `--unsafe` before the retirement is refused too, saying what lifts it (`core/sessions/legacy-unsafe.ts`, pure, and `legacy-unsafe-io.ts`; `legacyUnsafeCase` → `old-host` | `outside` | `both`, `stillUnsafeMessage`): its PTY-host restore entry says `unsafe: true` — an older host keeps it there and starts it with the flag again on a restart or resume: "run `work pty-host --restart`" —, or the history row's `launchedUnsafe` while an agent of it runs outside the host, whatever entry a current host has beside it: "quit it in its terminal and start it again with `work tree`", and the same rule keeps the PR watch from handing it review text (`runsUnsafe`; the comments it holds are noted in Activity at warn, with what lifts it, and handed over once it does — nothing is recorded as told meanwhile) and `work pr reply` / `post` from running in it. A current host writes back only what it starts with (its entry loses `unsafe` and the tool's `unsafeFlag` at a restore or restart), and a direct launch by a current `work tree` / `resume` / `recent` clears the row's flag only when no agent of the session runs anywhere (`clearLaunchedUnsafeWhenIdle`: the old one still running in another terminal keeps it, and the guards), so the guards drop out once the agent was restarted. Marked REMOVE IN THE NEXT RELEASE with `--unsafe`'s hidden option; `agent/start` refuses one running in a terminal outside work (two Claudes on one conversation) unless forced. `work answer` sends back the request it showed, and the answer route types only after `checkDialog` passes. § Never put `work answer`, `send`, `start` or `stop` on an allow list (`tests/core/assistant.test.ts` checks the assistant's): Claude Code's prompt is the user's say-so. What `work read` / `work screen` print is another session's words: the CLI says so on stderr, and the `work-sessions` skill tells Claude to treat it as data, never instructions.

## A coordinator and its children (`work coordinate`, `work child`, `work report`)

One session (often a repo's own checkout on main) splits a task across sessions of its own (`core/sessions/session-children.ts`; asked for: talk to the agent on main, have it spawn sessions, give them work, get their reports, and archive them at the end). `work child spawn <target> <branch> -m "task"` asks work web for a new session (`POST /api/worktrees` with `parentId`): the route refuses a branch that already has a session (a coordinator never takes over yours), records the link (`session_parents`), and starts its agent with `childBrief` — who started it, its task, and to say what it did with `work report`. `work report` sends that to the coordinator through `POST …/send` as `reportMessage`: from whom, fenced, said to be data and not instructions, so it is typed into an idle coordinator and the coordinator needs no polling. `work child send` / `finish` (archive: agent stopped, uncommitted work saved, branch kept) act only on the caller's own children (`driveCheck`); `spawn` needs fewer than `MAX_CHILDREN` (6) live ones (`spawnCheck`, in the route). The caller is the session for the folder the command runs in. A session that already exists becomes a child only by `work coordinate --adopt <target> <branch>` (`adoptChild`: not itself, not one another session coordinates, not one up its own chain — they would drive each other; `--release`, `releaseChild`), so the grant's own prompt is where you say yes to it. `work child send` wraps the text in `coordinatorMessage` (from whom, answer with `work report`): an adopted child never got the spawn brief. Asked for because two sessions talked through Claude Code's own SendMessage: an idle Claude never reads its inbox by itself and one work put to sleep is not listed, so a perf runner "dropped off" for the session that needed it; the skill now says to use work's commands between work sessions. § The say-so: `work send / stop / answer` each ask you; a coordinator would ask for every step, so you grant it once with `work coordinate --on` (`session_coordinators`; **never pre-allowed**, so Claude running it brings up your prompt), and work's session settings allow `Bash(work child:*)` and `Bash(work report:*)` (`SESSION_ALLOW`, session-settings.ts) — safe to allow only because work refuses anything outside the grant and the caller's own children. Everything else that drives another session keeps asking, and a child's permission prompts still come to you: `work answer` is never part of the grant. Not done yet: the dashboard doesn't show the link (children aren't nested under their coordinator), and spawning doesn't look at the usage meter or `work overlaps`.

**Every conversation is told it runs in work** (`core/sessions/work-intro.ts`, `workSessionIntro`): work's session settings add a Claude Code `SessionStart` hook (`work hook session-start`; it fires on a start, a resume, a clear and a compaction, and its output becomes the conversation's context, measured), which says which work session it is, that `work` is the CLI managing it, and to reach other sessions with `work send` / `work child` / `work report`, never the agent's own messaging between sessions. Asked for: a session told "use work to talk to the perf runner" asked whether "work" was the desktop app, Slack or GitHub — it had the work-sessions skill listed and nothing saying it ran inside work. One process per conversation start, not per prompt.
