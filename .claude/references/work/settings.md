# Settings (work's settings and each repo's)

`#/settings` (`g ,`, the version menu's Settings; `SettingsTab`) shows and changes work's settings from config.json by section, each saved as you change it (a switch or a choice at once; a number, a line or a list — one entry a line, never split at commas: a glob has them — when you leave it or press Enter, only when it changed); a setting written by hand shows Reset (back to its default, the key taken out) — not one work needs (`required`: the worktrees folder) —, and every one says its default and when it takes effect if not at once. Each value is held to the rule config.ts reads it by (`SETTING_PATTERNS`: issue keys, project keys, a `customfield_…`, an agent id, a variable's name — loadConfig drops what doesn't match, so the page refuses it), and the folders as `work init` takes them (`~` expanded, full paths, the worktrees folder made, a folder to scan there); a repo's origin is shown without its sign-in (`originShown`). A repo's own settings (`#/repos/<alias>`, Settings… on its row of the Repos page; `RepoSettings`): which failed checks count (`prWatch.requiredChecks[alias]`), its dev server command (`devCommands[alias]`), its reviews (`reviews.projects[alias]`), with its folder, origin and host. `core/settings/settings-schema.ts` (pure, shared with the SPA and the demo) is the one list — each field's path, section, label, help, kind (`bool`, `number` with a range and maybe 0 for off, `text`, `list`, `choice`), default (the one work uses: a test compares the time and trusted-bot defaults) — and `checkSetting` / `checkRepoSetting` check and tidy a value (`null`: back to the default). `core/settings/settings-admin.ts` reads config.json as raw JSON and returns only the schema's paths (`readSettings`: a token beside them never leaves; no field is a secret — a token is named by its environment variable) and writes one setting at a time through repo-admin's `editConfig` (its lock, atomic, unknown keys kept; an object a removal leaves empty goes too, `setValueAt`). Routes (`settings-routes.ts`, given a `SettingsSource`): `GET`/`PUT /api/settings` (`{path, value}`), `GET`/`PUT /api/repos/:alias/settings` (`{key, value}`); 400 with why, 404 for an unknown setting or repo; each broadcasts `settings-changed` (a repo's `repos-changed` too). The demo keeps a pretend config.json in memory by the same rules (`demo-settings.ts`). What has a page of its own (repos, groups, accounts, which PRs are reviewed) or doesn't fit a field (saved prompts, status hooks, the agent's flags, the port range, git hosts, the Time tab's hints, holidays and vacation) isn't on it, and the page says so (`SETTINGS_ELSEWHERE`). § WHEN adding a setting a user would change, add it to `SETTINGS` (with the default work really uses).
