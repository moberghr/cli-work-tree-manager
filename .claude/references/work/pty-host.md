# PTY host (sessions that survive restarts)

Claude PTYs are owned by the **PTY host** (`work pty-host`, hidden), a detached localhost process — not by `work web`. `work web` (via `core/pty/pty-pool.ts`) and `work attach` are clients: restarting/rebuilding `work web` or closing a terminal only drops a view. Discovery: `~/.work/pty-host.json` (pid, port, random token; every request carries the token, plus a Host-header check). **The Terminal tab connects straight to the host** (reported: typing lagged in the app while `work attach` in Windows Terminal — the same host, no work web — was smooth; every keystroke and echo waited on work web's event loop, which stalls now and then): it asks work web `POST /api/terminals/:id/ticket` (`terminal-routes.ts`: the "running elsewhere" check unless `force`, `ensurePty`, then `terminalTicketUrl` → the client's `ticketUrl` → the host's token-authed `POST /tickets`), and connects to the host's attach address with a **one-time ticket** (`core/pty/terminal-tickets.ts`: for that one terminal, from the page's own origin — only a page on this machine, `isLoopbackOrigin` —, within `TICKET_TTL_MS` (30 s), used once and burnt on any mismatch); the token never leaves work web. `openTerminalSocket` (`api/terminal-socket.ts`) is the tab's socket either way: a host from before tickets (`HOST_FEATURES` `tickets`; `work pty-host --restart` gives it), an older work web, the demo (`{fallback: true}`), a failed request or a direct connection the host turned down go through work web's relay (`/ws/sessions/:id/terminal`, `terminal-ws.ts`) as before; "elsewhere" and a refused start reach the tab as the relay would have said them. The corner's tooltip says which way it connected (`cornerBadge`'s `route`). Live sessions are mirrored to the restore list (state.db `pty_sessions`); on host start they are respawned with `--continue` (the "restored" flag), so a crash, `--restart` or reboot picks up where you were. A PTY that exits on its own is forgotten after 5 s (not immediately — at Windows logoff the children die just before the host); an explicit kill (worktree delete) forgets it at once. Several clients may attach to one PTY; the one used last sets its size — resized or typed in (tmux's `window-size latest`; each connection keeps its own grid, `pty-host.ts`; a terminal's own replies — focus in/out, answers to queries — aren't typing, `isTerminalReply`, or every attached client answering a query would pull the size its way): with the last resize alone, opening a session in the app shrank the PTY to the app's grid and a terminal attached by `work tree` stayed drawn for that size while you typed in it. An explicit kill (`work stop`, archive, delete, idle sleep) tells the attached clients it ended (`kill` keeps the exit subscribers until the process is gone), so a Terminal tab offers Enter to start it again instead of a screen that takes no input; a start that fails (the connection closes before the screen came, the server's error said) shows why and tries again after 3, 10, 30 and 60 s, with Try now (`state/terminal-start.ts`), never a "Starting Claude…" left for good; ⋯ → Reconnect terminal (⇧R, `state/terminal-reconnect.ts`) opens a new connection whatever state it's in.

**Idle Claudes sleep** (`core/pty/idle-sleep.ts`, a 5-minute sweep in full-mode `work web`): a host PTY with **no client attached** (`PtyInfo.clients`), that has **printed nothing** for `sleepIdleAfterMinutes` (config, default 10, at least 5; 0 = never; `PtyInfo.lastOutputAt` — an idle Claude prints nothing, a working one redraws its spinner), and isn't the assistant, is stopped (`disposePty`) — only when it is truly idle (`stillAtWork`, `sleepPlan`; the I/O in `core/pty/sleep-checks.ts`): the status the dashboard shows isn't working or waiting on you, Claude Code's own state for the process isn't busy (a background agent) or waiting, no background command its conversation started since the process began is still running (`backgroundCommands`, Claude's `openBackgroundCommands`: a `run_in_background` call with no `<task-notification>` — read from any line, queued or delivered — nor `TaskStop`), and nothing runs from its folders (`runningFromNames`: a dev server, a watcher); a check that can't tell keeps it awake, and the Activity panel says why each one stayed. Stopping a Claude stops what it started. It stops holding memory, and opening the session resumes the conversation: the stop is recorded (`markAgentStopped` → `SessionStatus.stoppedAt`, also by `work stop`), so the Terminal tab's "running in another terminal" check (`claudeElsewhere`, `lastStop`) ignores the turn that ended just before — what held the minimum at 30 minutes. The dashboard's terminal deck (`TerminalDeck`) keeps up to 5 terminals connected for instant switching, but one hidden for `DECK_HIDDEN_MS` (10 min) lets go (`pruneDeck`), so its Claude counts as unattended and can sleep — with the app open all day, the five most recent Claudes otherwise never slept. `clients`/`lastOutputAt` are additive: a host from before reports neither, and then nothing sleeps.

**Heartbeat and latency.** The pool's 2 s list request is the host's heartbeat (`hostBeat`, `core/pty/pty-pool.ts`). `core/pty/host-health.ts` (pure) reads it as ok, slow (an answer over 1.5 s) or not answering (none for 11 s; a busy host counts as a host). `GET /api/pty-host/health` serves it, a `host-health` broadcast goes out when it changes, and the dashboard shows `HostHealthBanner` only when it isn't ok. The host outlives updates, so `/health` also says which release it runs (`work`, `PtyHostClient.workVersion`, read once per host; `''` from a host from before): one other than this work web's (`HostHealth.outdated`; dev builds never compare) shows too. A host that's older or not answering gets **Restart it** (`hostNeedsRestart`; `POST /api/pty-host/restart`, `pty-host-routes.ts` → `restartHost`, the `--restart --force` path: stop — killed when hung and still ours —, then start; sessions come back with `--continue`; refused on the dev server). Each terminal start is timed (node-pty's spawn is synchronous and holds the whole host): over 5 s is a warning. Config `useBundledConpty` (Windows) starts terminals on the ConPTY node-pty ships (`conpty.dll` + `OpenConsole.exe`, Windows Terminal's) instead of Windows' own, whose start hung a host once (`conptyOptions`, read at each start; off by default, node-pty calls it experimental; the desktop app's staged CLI keeps both files). The Terminal tab measures a keystroke in two parts (`LatencyMeter`, `state/keystroke-latency.ts`): its echo arriving (key sent → next output: browser → work web → PTY host → ConPTY → Claude and back) and it on screen (key sent → the first frame xterm drew after the echo; it was once the last frame before the output went quiet, which a working Claude's spinner — a redraw every ~100 ms — never is, so it read the spinner: measured echo 6–18 ms, "on screen" 366 ms), each the median of the last 20 and the slowest of most of them (the 90th percentile, so a stall shows). The corner shows the on-screen time — "⌁ 41 ms", "(210 ms)" beside it when the slow ones are much slower — with both parts in its tooltip (`cornerBadge`), amber from 100 ms. **The debug log has it too** (a tooltip can't be copied): every 10 s while there's something, and when the tab closes, the tab posts each keystroke's two times and every freeze of the window while it is the one shown — a long animation frame (`observeLongFrames`: Chromium's `long-animation-frame` with the scripts that ran, else `longtask`) — to `POST /api/terminal-perf` (`TerminalPerfLog`, `state/terminal-perf.ts`; read strictly by `cleanPerfReport`, `core/pty/terminal-perf.ts`), which writes one `terminal-perf` line to `~/.work/debug.log` (`perfLine`: echo and on screen as median / p90 / max, each freeze with its time, length and what ran; the demo takes and drops it). That's where to look first when typing feels slow. The terminal draws with WebGL; a lost context (GPU reset, sleep/resume) falls back to the DOM renderer, which is slow with a busy Claude, so the corner then says "DOM" and it tries WebGL again after 2 s, 10 s and 60 s (a try that fails counts as a loss), staying on DOM at the fourth loss in 10 min (`WebglRecovery`, `state/webgl-recovery.ts`); each swap refits the grid, since the renderers measure a cell differently. Measured (2026-10): a working Claude sends ~14 frames/s at ~1 KB/s; even 4 MB into five deck terminals at once kept the page at 60 fps with no long task — drawing isn't where time goes.

**The environment of a restored session.** A restore spawns with the host's environment, not the launching shell's: `env` is one-shot and never stored (it can hold secrets). Config `hostEnv` (none by default; e.g. `["JAVA_HOME", "PATH"]`) names variables to keep: their values from the shell that started the session go into its restore-list entry (`keptEnv`, `keepEnv` in `pty-host-protocol.ts`), and a restore — or a respawn without a shell, from the Terminal tab — runs with the host's environment plus those. Names that look like secrets or carry them (`*TOKEN*`, `*SECRET*`, `*PASS*`, `*KEY*`, `*AUTH*`, `*_PAT`, `DATABASE_URL`, `*_URL`, connection strings, …) and values with a password in a URL (`scheme://user:pass@`) are never kept, whatever the config says.

**Status for a tool with no hooks.** For a session whose PTY runs another tool (`aiCommand`, e.g. opencode; `PtyInfo.tool`, additive), nothing reports turns, so `statusFromOutput` (`core/pty/output-status.ts`, pure) reads one from the host's `lastOutputAt`: working while it printed in the last 10 s, idle after (seen — output can't tell a finished turn from a question). It applies only when no hook status exists, in `/api/sessions` (the pool's refresh) and `work sessions`.

**Restarting agents** (`core/pty/agent-restart.ts`; `agent-restart-routes.ts`, `work restart`): a Claude keeps the binary it started with, so after Claude Code updates itself the running ones are on the old version. One whose process started before its tool's file was installed (`installedAt`: the file its command runs on PATH, `findOnPath`, through links; the newest of mtime and ctime, since npm unpacks with an old mtime) is outdated (`outdatedPtys`; a host from before `tool`, or a tool not on PATH: never). `GET /api/agents` lists them; the dashboard says so in the version menu (a dot on it) and a card in the update card's corner (`AgentsRestartCard`; Later per install time), both naming the sessions (`outdatedNames`: as the rail names them, the waiting ones last and marked "after its turn"; a name opens its session), and `POST /api/agents/restart` (`{outdated}` / `{ids}` / `{all}`) restarts them: idle ones at once, one working or waiting on you when its turn ends (`createRestarter`: `turnEnded` from the status hook, after `TURN_END_GRACE_MS` — the Stop's own hooks run as its children —, and every `QUEUE_RECHECK_MS` while anything waits; busy = Claude Code's own state for the process (busy / waiting: a permission dialog prints nothing; the assistant has no hook status), `shownState`, or a terminal that printed in the last 10 s; one restart per session at a time, shared (the route counts one mid-restart as running); one Activity run per request, kind `agents`, and a schedule while anything waits; wording in `restart-view.ts`; the dev server lists but restarts nothing). An old process that won't stop within 3 s ends the session as a stop does, never a second agent beside it. It runs with the environment the session started with (`Entry.env`, the host's memory only; never in the restore list). Install time (`installTime`): the later of the file's mtime and creation, npm's fixed 1985 date counting as neither (its change time then), never the change time alone (a chmod). A restart is the host's `POST /ptys/:id/restart` (`registry.restart`): the process stopped and started again in place with `--continue`, the attached terminals kept (not told the old one ended), so a Terminal tab or `work attach` carries on. Additive, no protocol bump: an older host answers 404 and the pool stops and starts it instead (`restartPty`).

**Halt and resume** (`registry.halt` / `resume`; `POST /ptys/:id/halt` | `/resume`, additive, an older host answers 404): halt stops the agent but keeps the session — its entry, restore record and attached terminals (not told it ended) — so something can change under it before it starts again; resume starts it in place with `--continue` and an optional `agentEnv` (`EnvDelta`), so the terminals carry on. A halted session is resumed by itself after `HALT_RESUME_MS` (5 min: a move of a big folder across volumes takes a while; said at warn) on its pre-halt spec should nobody ask, and a host restart restores it as any session (on its old spec too). A switch of Claude account is the user: halt → move the conversation folders → record the account → resume on its environment; when the resume finds it no longer halted (started again meanwhile, by the timer or a restore), the switch restarts it in place on the new environment (`client.restart(id, {agentEnv})`; not running: started fresh; an older host: stopped and started) and says so in its outcome (`RESTARTED_AFTER_AUTO_RESUME`; see Accounts, under Agents). **Host features**: `/health` answers `features` (`HOST_FEATURES`: `agentEnv`, `halt`; additive, a host from before answers none), which the client asks once per host (`PtyHostClient.features`); the pool refuses what an older host would silently drop (`OLD_HOST_ACCOUNTS`: "the PTY host is from before Claude accounts: run `work pty-host --restart`") — a spawn of a session on a named account (one already running there is only attached to; the Terminal tab shows the reason), a resume carrying an environment, and a switch of account before anything is halted (`accountSwitchRefusal`). A host that can't be asked in time is given the benefit of the doubt.

§ Only a refused connection (`ECONNREFUSED`) means no host; anything else — a timeout, a reset, a hang-up — is a BUSY host, never a missing one (a hung host resetting connections once read as gone, and a second host started every Claude again beside the first): `findHost` retries with a longer timeout, then throws `PtyHostBusyError`, and every "should I start one?" path treats that as running (a second host restores every session again).
§ WHEN changing the host wire format, bump `PROTOCOL_VERSION` (now 2: the restore list moved into state.db; a v2 host adopts a `pty-sessions.json` written by a v1 host that outlived the upgrade — `adoptLegacyRestoreList`) — the host outlives rebuilds, so clients must detect an old one and tell the user to `work pty-host --restart` rather than misbehave.
§ WHEN spawning into a PTY, let `resolvePtyCommand` (`core/pty/pty-session.ts`) build the command — never `cmd.exe /c <tool> <args>`: unescaped, `&`/`|`/`%` in a prompt or path run as commands on Windows. On Windows it starts the program PATH gives (`programFor`, `core/platform/batch-launch.ts`; never one in the worktree, a missing one throws "<name> not found on PATH"), and judges batch-ness on the file that really starts: an extension-less path (`C:\npm\claude`, `where`'s first line) is the `.cmd` beside it, as Windows and cross-spawn would start it. It runs a batch file that starts a Node script — npm's `claude.cmd` — as node on that script (`nodeShimOf`; a Python module's shim as its Python), so the prompt is plain argv; the node is the shim's own node.exe, else PATH's when that is a real program, else work's own (`process.execPath`, `nodeFor`) — never a version manager's `node.cmd` (cmd.exe again: `"&echo X&"` ran through it). Any other batch file goes through cmd.exe only with arguments free of its special characters (cmd.exe parses them twice: `"&echo X&"` ran, a line break cut the rest), and its first prompt is typed in once it's up instead (`typeWhenSettled`: after its first output and `PROMPT_SETTLE_MS` of quiet, at most `PROMPT_WAIT_MS`, once, never after it ended, through the agent's `input.submit`). `work tree --no-host` (`launchAi`) goes through `launchFor` the same way and refuses such a prompt.
§ WHEN starting a program by its bare name, go through `core/platform/spawn.ts` (cross-spawn; it resolves the program itself) or name it `programPath('git')` for child_process (`core/platform/program-path.ts`). On Windows every lookup by bare name — node-which in cross-spawn, libuv, cmd.exe — tries the working folder first, so a `git.cmd`, `gh.cmd` or `git.exe` committed at a worktree's root (someone else's branch, opened by Review or Work on it) ran in place of git. `programPath` is the absolute file on PATH (absolute PATH entries only; a hit kept per PATH and checked on use, a miss never kept) or, when there's none, a path that fails as not found — said as "<name> not found on PATH" (`explainNotOnPath`: the spawn wrapper does it, an `execFile` site whose error is shown calls it). App Execution Aliases count (`isProgramFile`, `find-on-path.ts`: `wt.exe`, `winget`, the Store's `python` / `pwsh` in `%LOCALAPPDATA%\Microsoft\WindowsApps` are reparse points `stat` answers EACCES for; a hit `lstat` sees and that isn't a folder is one), or Windows Terminal looked not installed. A name with a path in it is resolved against the start's cwd with PATHEXT, as Windows would. A start the caller answers about waits for it (`whenStarted`, `core/platform/started.ts`: Open in terminal says why wt.exe didn't start, never ok). The user's own shell command lines (dev servers, status hooks, `work run`) are the exception — and run with `shellEnv` (`core/platform/shell-env.ts`: `NoDefaultCurrentDirectoryInExePath=1`, so cmd.exe takes a bare name from PATH, never the worktree; a branch's own script runs by its path, `.\scripts\dev.cmd`); only tool runs get it — not what you work in: the editor (`openInEditor`, `openVSCode`, Open in editor), a URL (`openUrl`) and Windows Terminal (node's spawn) keep cmd.exe's usual lookup, since their own terminals and tasks would inherit the switch (the spawn wrapper's `keepCwdLookup: true`, taken off before cross-spawn sees it); the spawn wrapper sets it for any other `shell: true` start, and for any program that resolves to a batch file (`BATCH_FILE`, `onPathOnly`; the PTY's `resolvePtyCommand` returns it as `env` for the `cmd.exe /d /s /c` it builds): cmd.exe runs that file in the worktree, and a bare name inside it (a non-shim `gh.cmd` calling `probex`) would otherwise run the branch's `probex.bat` (`tests/core/platform/batch-cwd-lookup.test.ts`: real cmd.exe, through the spawn wrapper, the CommandRunner and the PTY's command). `tests/architecture/program-path.test.ts` checks every start (named, default and namespace imports, `require`, dynamic `import()`, `promisify`; cross-spawn's loads; `pty-session.ts` may hold cross-spawn for its one `_parse`; each shell-command file by the one expression it starts; `shell: true` with `shellEnv`), with self-tests of the check.
§ WHEN starting any process, give it `windowsHide: true` (or `false` with the reason: a window that is the point, a program sharing this terminal), and start a background program `detached: detachHere()` — POSIX only (`core/platform/process.ts`): on Windows a process with no visible console gives each console program it starts a window, so a run of them blinks across the screen, and a detached one has no console at all, which `windowsHide` can't fix (measured; the editor's `code.cmd`, the toast's PowerShell and `cmd /c start` all flashed). Only `spawnDetachedWork` (work's own servers, whose children are all hidden) stays detached. `tests/architecture/windows-hide.test.ts` checks both; the tests' own calls get `windowsHide` from `tests/setup/hide-windows.ts`.
§ WHEN adding a path that spawns Claude for a session, go through `spawnSpecFor` + the host, not `new PtySession` — otherwise that session won't survive restarts or be attachable.
§ A Claude launched directly in a terminal (`--no-host`, config `launchViaHost: false`, or from before 2.0 made host launches the default) is invisible to the host, and the Terminal tab must not put a second one on its conversation: `claudeElsewhere` (`server/terminal-ws.ts`) infers one from a transcript write in the last 5 min, a working/blocked status, or a Stop in the last 30 min (the turn's end, `turnEndedAt`, else `since` — never `updatedAt`, which opening the session moves when it marks it seen), and the tab then explains (with the `--host` hint) instead of spawning; `?force=1` spawns anyway. Quiet longer than that is unknown, and spawning — which resumes the conversation — is what the tab is for.

**Status icons.** Every view shows a session's status as one icon per `DisplayKind` (`StatusIcon.tsx`: "!" disc = needs input, check disc = done (the Inbox's Done section only: everywhere else a finished turn you haven't looked at is the second signal, below), turning arc = working, the same arc in teal = in background (its turn ended and a background agent it started is still at it — its prompt free; `background`, from `EffectiveStatus.background` / `SessionAttention.background`: the state stays `working`, so the Inbox, ranks and notifications don't change; `what` is the agent's own description, in the rail's tooltip), grey arc = archiving / restoring, grey "z z" = asleep (its Claude stopped while idle by idle sleep or `work stop`, and not run since: `SessionWire.asleep`, `isAsleep`, from `SessionStatus.stoppedAt`; opening it starts it again), ring = idle, pulse = active, ring + dot = open, moon = stale), coloured as the old dots were; it keeps the `wd-rail-dot wd-rail-dot-<kind>` class names views and tests find a status by. **Two signals** (reported: a session with a reply to post read Idle and stayed out of the Inbox): the icon says only what its Claude is doing; what waits on *you* about it is the second, `owedToYou` (`core/status/attention.ts`: a finished turn you haven't looked at (`turn`, first — reported: Done took the icon, so an asleep or idle Claude read blue), replies to post, review threads with no answer, a PR conflicting, failing its checks or ready to merge), shown as a badge in the rail's right-hand slot — blue "review" for a turn (`owedClass`, `wd-rail-slot-owed-turn`), pink for the rest ("1 reply", "2 threads", "merge", "CI", "conflict", "+1" for more; all of them in its tooltip, `owedBadge`, `session-view.ts`), beside the status in the Sessions table, as the header's Needs you line (`prNeedsLine`, the same list with each PR named, a turn left out: it's GitHub's) and in `work sessions` (`view.needsYou`). Whatever its Claude is doing. With none, the slot says how long, or "in review" (`waitingOnOthers`) when its PR waits on reviewers or checks. A rail row is the same two lines for every session, the open one too: icon, name and that slot; then its project (and branch, when you named it) and a pill per PR, right-aligned (`RailPrPills`: `#212`, coloured by that PR's stage — green ready, red conflict / failing / changes asked, dashed draft, purple merged: a group whose backend merged while its frontend is in review shows both, the stage's `prs` listing merged ones after the open; a click opens the PR; from the PR watch's stage, else the dashboard's PR list — the watch holds one PR per repo (`gh pr view <branch>`), so a second PR from the same branch, into another base, is added from the list as a plain pill, there and in the header: `prsBeyondStage`, `pr-stage.ts`; the list is matched by the session's branch or one a repo of it has checked out now, `prsForSession`). Where it stands is the session header's; the rest (until when it's snoozed, what it waits on, where its PRs stand, notes, where its Claude runs) is in the row's tooltip (`railDetails`); never the +/− lines, which are the Diff tab's.

**Status without hooks.** A session whose Claude has not taken a turn since the dashboard's hooks went in shows transcript activity only (`displayStatus`, `state/session-display.ts`): Active ≤ 30 s, Open ≤ 5 min, Idle within a day (`recent`), Stale after that. "Last active" everywhere is `lastActiveAt`: the newest of the hook update, Claude's last write and the `work tree` entry.

**Never asleep with nothing to resume** (reported: a session started with a prompt on a second account stopped at Claude Code's "do you trust this folder?", was put to sleep five minutes later, and came back empty — the prompt gone and nothing said): idle sleep's promise is that opening the session brings its Claude back with its conversation, so a Claude whose session has no conversation yet stays awake (`SleepChecks.resumable` → the agent's `resumeLaunch(session).hasConversation`; `stillAtWork` answers `NOT_RESUMABLE`, which the Activity note shows). It never had a turn: it sits at a first-run question, or still holds the prompt it was started with. It costs a Claude's memory until you look at it; losing a prompt silently costs more. The Ctrl+K assistant is started afresh by design and sleeps by the other rules.
