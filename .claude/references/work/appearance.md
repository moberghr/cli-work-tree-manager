# Appearance (app theme, terminal theme, font, size, line height)

The page's colours are one setting, `theme` in config.json, on the Settings page's Theme section (App theme): `system` (the default: follows the OS, `prefers-color-scheme`), `light`, `dark` (today's Primer palettes), `midnight`, `dracula`, `tokyo-night`. Absent or unknown is `system`. `core/settings/app-theme.ts` (pure, imports nothing, shared with the SPA: `SPA_SHARED`) holds `APP_THEMES` (id, label, `base` light or dark, and `terminal`: the palette the app theme maps to) and `resolveAppTheme(value, osDark)`, which gives `{ id, base, terminal }` (`id` is never `system`). `tokens.css` has the colours: the light block, the dark block, and a `:root[data-app-theme='<id>']` block per named theme that redefines every colour token the dark block defines (`tests/web/theme-tokens.test.ts` holds that, and that each reads at 4.5:1 on its `--bg`). The named themes are dark-based: the store stamps `data-theme="dark"` (so highlight.js, diff.css and `color-scheme` stay dark) plus `data-app-theme="<id>"`; light and dark stamp only `data-theme`. `diff.css`'s three GitHub-dark surfaces (`--empty-bg`, `--ln-bg`, `--status-binary-bg`) are `--code-bg` / `--hover`, so a named theme re-colours them. `loadConfig` reads `theme` and keeps it only if it is one of the ids (as for `terminal`, § WHEN adding a key the Settings page writes, read it in `loadConfig`).

In the SPA `state/appearance.ts` is the one store for the page (it was `state/terminal-style.ts`): the settings' values when the page has them, the localStorage cache (`wd:theme`) and the OS scheme (a `matchMedia` listener, followed under System). It derives the resolved app theme and the terminal style, stamps `data-theme`, `data-app-theme`, `--term-bg` and `--term-fg` on `<html>`, and tells subscribers only on a real change. It exports `useTerminalStyle()`, `useAppearanceUpdates()` (the page's one subscription), `useAppTheme()`, `setAppTheme(id)` and `toggleAppTheme()`. `ThemeProvider` is a thin adapter over it and keeps its API (`theme` = the base, `explicit`, `setTheme`, `toggle`), so `ThemeToggle` and `App.tsx` did not change. The top-bar button flips light and dark from the current base; in work web it writes `theme` to config.json (`saveSetting`) and the page updates at once, in `wd` (no settings API) it writes localStorage, the browser's own choice, as before. Which one is the page's answer, not its view: `ThemeProvider` (at the root of every view) asks for the settings once, and a page whose settings answer keeps its theme in config.json — the dashboard and work web's diff, review and file pages alike; `wd`'s server says 404, and the theme stays the browser's. A save is the truth only once answered: a read that crosses it (another save's `settings-changed`, a double click) keeps the theme chosen, the page settles from the save's answer (the PUT returns the settings), and the cache is written then, so another tab — told by the `storage` event, which on a page whose theme is a setting reads config.json again (a diff page has no event stream) — never reads it before config.json holds it.

No flash: localStorage `wd:theme` caches the app theme (in work web it mirrors config.json; System or absent removes it), and the inline boot script in `index.html` paints from it before first paint, for a named theme with `data-theme="dark"` + `data-app-theme`. The `--term-bg` / `--term-fg` defaults in `tokens.css` are the base's (light: GitHub Light's `#ffffff` / `#1f2328`; dark: `#1e1e1e` / `#d4d4d4`) and each named theme's palette, so a terminal's frame never shows the wrong colour before the settings arrive. Upgrade: a light or dark choice made with the button before the app theme was a setting was per browser; in work web config.json's value (System until set) now wins, and one click on the button sets it again. `wd` keeps the browser's choice.

## The terminal

Every terminal in work web (a session's, the Ctrl+K assistant's, an account's sign-in: all `PtyView`) draws with one style, set on the Settings page's Theme section and kept in config.json: `terminal.theme` (Match the app, the default: `app`; or Default dark, Midnight, Dracula, Tokyo Night, GitHub Light), `terminal.fontFamily` (a font installed on the computer: work ships none), `terminal.fontSize` (8–32, default 13) and `terminal.lineHeight` (1–2, default 1). `terminal.colors` (hand-written in config.json only, listed in `SETTINGS_ELSEWHERE`) changes single colours over the theme, by xterm's `ITheme` names (`background`, `foreground`, `cursor`, `cursorAccent`, `selectionBackground`, the 16 ANSI colours `black` … `brightWhite`), each `#rgb` or `#rrggbb` — `#rrggbbaa` for `selectionBackground` only (xterm draws the others opaque, and a see-through background would leave the terminal's frame see-through over the page). `app` (also absent or unknown) is the palette the app theme maps to: light is GitHub Light, dark is Default dark (today's `#1e1e1e`, so a dark user sees no change), midnight, dracula and tokyo-night their own; a palette id overrides the app. `resolveTerminalStyle(values, colors, follow)` takes that palette as `follow`. With nothing set on a dark app the terminal looks as it did before themes: Default dark is today's `#1e1e1e` / `#d4d4d4` with xterm's own Tango colours, and the font is today's Cascadia stack.

`core/settings/terminal-style.ts` (pure, imports nothing, shared with the SPA: `SPA_SHARED`) holds the themes' full palettes and `resolveTerminalStyle(values, colors, follow)`, which turns the Settings page's values (by path, as `SettingsWire.values` has them) into what xterm takes, field by field: one that doesn't fit is its default, the others stand. The user's fonts go first, each name trimmed and put in quotes of its own (`fontList`: a stray quote, `"Hack`, would otherwise void the whole CSS list, today's stack with it; a generic family like `monospace` stays bare), and today's stack after them, so a name that isn't installed falls back. `readSettings` (`settings-admin.ts`) sends the colours as `SettingsWire.terminalColors`, only the ones `checkTerminalColors` keeps and only when one does; nothing else of `terminal.colors` leaves config.json. `loadConfig` reads `terminal` too (`TerminalConfig`: its fields by type, the colours that fit), though work web never reads it from there: `saveConfig` writes the typed config, so a command that saves config.json (`work config remove-repo`, `add-group`, `remove-group`, `work init`) would otherwise drop it — and a colour that doesn't fit is dropped by such a save, as other hand-written keys are. § WHEN adding a key the Settings page writes, read it in `loadConfig` for the same reason. The schema can't import the theme module (it is import-free), so the font's pattern is written twice (`TERMINAL_FONT_PATTERN`, `SETTING_PATTERNS.fontFamily`) and a test holds them equal.

In the SPA, `state/appearance.ts` holds the one style the page's terminals share. `DashboardApp` holds the page's one subscription (`useAppearanceUpdates`; one per terminal would read twice per change): it asks for the style as the page starts, so it is in before a terminal's first replay and the terminal is fitted once, at the user's size (until then, and if the read fails, it is today's look; a failed read is asked again by the next terminal to mount), and again on `settings-changed` and when the event stream (re)connects (a change sent while it was down, or a first read that failed while the server started). One read at a time, and its subscribers are told only when the style really changed (an unrelated setting refits nothing). It sets `--term-bg` / `--term-fg` on `<html>` (defaults in `tokens.css`), which the terminal's surroundings paint with (the pty host and its viewport, the Connecting… cover, the start-failure cover, the assistant's body, the deck's slot, the sign-in box), so a light theme has no dark frame; the covers' text is a `color-mix` with `--term-fg` that is exactly the old colour on the default theme. § A style change never reconnects: `PtyView` builds its Terminal from the style it has, and a later change sets xterm's options on the open terminal, refits, and resizes the PTY only when its columns or rows changed — as a window resize does (the client used last sets the PTY's size, pty-host.md); the connect effect does not depend on the style. A terminal hidden in the deck sends nothing and refits when shown.

Claude Code draws with its own colours, picked by its `/theme`, inside whatever background the terminal has: on GitHub Light, switch Claude Code to a light theme too (the Theme setting's help says so).
