# Start from a ticket or PR

**Start** (`#/start`, `StartTab`; old `#/prs` links land here) is where new work comes from: New worktree and Repos & groups on top; your open pull requests and the ones waiting for your review (`waitsForYourReview`: someone else's, your review asked for by name — gh's `reviewRequests`, `PullRequestInfo.reviewRequested`; a team's request isn't known — and not reviewed yet) — each row with Start (the New worktree dialog, filled in; Review for someone else's PR, whose prompt (`prPrompt`) asks Claude to read, try and say what it would comment, and to commit, push or post nothing) or a link to the live session already on it (`sessionForIssue`: its Jira key or its `feat/<KEY>` branch — `sessionIsForIssue`, `core/jira/jira-prompt.ts`, the Jira watch's rule too; `sessionForPr`: its branch, in its repo or one of its group's — `prsForSession` with the configured members, `/api/projects`), **Work on it** beside Review (someone else's PR, on their branch: what you push lands in it; disabled for a fork's, whose branch isn't on origin — `PullRequestInfo.fork`), the repo as its own column, a quick filter by repo over both lists (a chip per repo with its count, several at once, none = all; `repoCounts`, `inRepos`; remembered per browser), and a PR's state in a word (`prState`: Merge conflict — `PullRequestInfo.conflicting`; checks no longer read FAILURE for a conflict — Checks failing, Approved…). It uses the dashboard's one PR list (no poll of its own). **Jira** (`#/jira`, `g j`, `JiraTab`) is its own tab: the issues assigned to you (workflow order, done ones left out), each with Start or a link to its session, and the checkbox that starts newly assigned issues by themselves (the Jira watch). A missing `gh` or `acli` is one quiet line. Start, Jira, Repos and Welcome scroll their pane, the header staying put; Repos has "← Start".

§ In work web, worktrees are made in a child process: `createInChild` (`core/worktree/setup-child.ts`) runs `work tree <target> [branch] --setup-only` (bases, Jira key and name as flags) and reads the result back from the history. This covers New worktree, Fork, the Jira watch, and Restore of a removed worktree. `setupWorktree` runs git synchronously (fetch, pull, worktree add), and done in-process it held up every request — terminals and status hooks too — for as long as the network took. A failure returns the child's own error lines; a success its warnings (`--setup-only` ends with a `work-setup-warnings […]` line, `setupWarningsOf`; `CreateResult.warnings`), which New worktree and Restore show in their toast (Restore's through one event, `RESTORE_WARNINGS`, `api/client.ts`, so every Restore button shows them). Routine lines aren't warnings: a worktree already there on re-entry is `info`, the base repo not on main/master/dev a `detail` note. Values go as `--flag=value`, and a project, branch or base starting with `-` is refused first (`invalidRequest`), since the child would read it as a flag. Creations in one project run one at a time, and the same one asked twice gets one answer (`oneAtATime`). A child killed for taking too long is followed by `git worktree prune`. The CLI and tests use `createInProcess`, which gives the same answers. WHEN adding a path in work web that creates a worktree, go through the server's `makeWorktree`.

**Start from a pull request…** (New worktree, under the project) takes a PR's link or its number in the picked project: `GET /api/pr-start` (`resolvePrToStart`, `core/pr/pr-start.ts`: the repo matched by its origin, `gh pr view`; refused when not open or from a fork) fills in the repo, its branch and `workOnPrPrompt` (`core/pr/pr-ref.ts`, pure: whose branch it is, get up to speed and wait — or do your instruction —, post nothing on GitHub), and says whose branch it is while project and branch still match; a link picks its own repo, a bare number the picked project's, and the project and prompt wait while it looks. A local branch of that name that has gone another way than the PR's (a force-push) is refused, not opened on (`localGoneOtherWay`). `work tree --pr` is the same lookup (a target beside a link must hold it), and sends the PR's context only to a new session. A fork's PR is reviewed on `review/pr-N` (`prPick`), its prompt saying `gh pr checkout N --detach`.

The New worktree dialog's project field is a type-to-filter combobox (`ProjectPicker`: every word must match a name, a group's repos or a folder; ↑/↓, Enter, Escape). Its branch is optional for a repo: left empty, `POST /api/worktrees` opens the repo's own checkout on the branch it has — the same `openBaseCheckout` (`core/worktree/worktree.ts`) as `work tree <repo>` with no branch (pull, one session per checkout). A group still needs a branch, and a base needs one too.

The New worktree dialog asks two things: the project, and "What should Claude do?" (empty: just the worktree). The branch is suggested from that text (`suggestBranch`, `state/branch-suggest.ts`, pure, no agent call — a one-shot Claude run takes ~10 s to start, too long for the dialog: a Jira key or link → `feat/<KEY>`; a pasted exception → `fix/<its-name>`; a question or investigation (why…, check…, provjeri…) → `tmp/`; failure words → `fix/`; a leading kind word → that kind; else `feat/`; then up to three words of the first line with text, without URLs (their last named part kept), ids, code, filler, pronouns, helper verbs and small words, English and Croatian; a prompt with nothing to name it by gets `<kind>/work-MMDD-HHmm`, so with a prompt there is always a new branch). The branch field starts empty and the suggestion is only its placeholder (`branchPlaceholder`): typing names your own, with nothing to delete first; left empty with a prompt it is the suggestion, with none the project's own checkout. A pick that names one (Jira's `feat/<KEY>`, a PR's branch, a task's `todo/…`) fills the field. § `work tree` checks out a branch that exists and reuses a session of that name, so the dialog asks `GET /api/branch-check` (`checkBranch`, `core/worktree/branch-check.ts`; the demo answers from its sessions) as you type and again right before creating: a suggestion that's taken in any of the project's repos or by any session of it (archived too) gives way to the first free name (`firstFreeBranch`: `-2` … `-9`), and a branch you typed that exists says what Create will do with it (check it out, open its session, restore it). A name git refuses blocks Create. A name and a base branch are under "More options", whose folded label names what's set in it (`moreLabel`); Ctrl+Enter in the prompt creates. The prompt is what Jira and PR picks pre-fill (`state/start-prompts.ts`: the issue key, summary and link; for a PR, failing checks or requested changes). With a prompt, `POST /api/worktrees` starts the session's Claude in the PTY host with it as the first message (`ensurePty(id, {initialPrompt})`) and the dashboard opens its terminal. § If the session's Claude is already running (the worktree existed), the prompt is queued as a published comment for its next turn, never typed into the terminal. A start that fails still returns the created worktree, with `startError`.

**The branch the repo's own folder is on** (reported: New worktree with "main" answered "Branch 'main' is already checked out in a worktree at <the repo>", while `work tree <repo>` opened it): a branch can be checked out in one place, so naming that one means the repo's own checkout, the same as naming none — `ownsBranch` (`core/worktree/own-checkout.ts`: a single repo, never a group; the branch read from the HEAD file), applied where a creation is asked for (`commands/tree.ts`, which the server's child runs, and `createInProcess`), unless a `--base` is given (a fork of a branch that exists is refused as before). The dialog says so as you type (`BranchCheck.ownCheckout` → `branchNote`: "main is the branch the project's own folder is on: Create opens it there (no new worktree)"), so a prompt can start a session on the repo's own folder: type its branch.

**No branch name says where it lands** (reported: a session started with the name empty landed on a feature branch the repo's own folder had been left on, when main was meant): `GET /api/projects` gives each repo the branch its own folder is on now (`projectList`, `ownBranch`, read from the HEAD file), and the dialog says under the empty field "No branch: opens <repo>'s own folder, which is on <branch> now (no new worktree). For another branch, type its name." (`ownFolderNote`). work never switches the branch of a repo's own folder.
